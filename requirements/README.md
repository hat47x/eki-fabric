# EKI Fabric 要求文書の読み方

このディレクトリは、EKI Fabricが満たす製品要求と、安全性を検討するための正本です。脅威モデル、Workerに求める保証、構成案を比べる品質特性もここにまとめています。

ここにあるのは、アイデアの一覧ではありません。EKI Fabricは最初の全体構成を設計基準として定めましたが、要求は具体的な実装方式から独立して扱います。要求文書では、次の点を確かめます。

- 何を守る必要があるか
- どのような失敗や攻撃に耐える必要があるか
- どの範囲まで保証できるか
- 成り立つ複数の案を、何で比べるか

## まず全体像を知りたい場合

要求文書に入る前に、[はじめてEKI Fabricを読む方へ](../docs/for-readers.md)を読むことをおすすめします。

この案内では、業務端末の余剰資源を使う理由を説明しています。また、ClientやWorkerを無条件には信用しないことと、悪意ある参加者を想定しながら一時参加者を受け入れることの両立も、背景から説明しています。

## 文書ごとの役割

### 製品要求

[PRODUCT_REQUIREMENTS.md](PRODUCT_REQUIREMENTS.md)が、EKIの製品要求を定める正本です。

製品要求では、たとえば次の性質を定めています。

- 特定のOSSや言語に依存しないこと
- 業務端末では、利用者を最優先すること
- ネットワークの負荷とデータの局所性を考慮すること
- 悪意のあるClientやWorkerを前提にすること
- Browserや一時的なWorkerの離脱を、通常の状態として扱うこと
- アドホック参加者や複数の組織を受け入れられること
- 組織間連携（Federation）で、識別情報（Identity）の名前空間を取り違えないこと
- 成果物（Artifact）の取り込みと展開の処理にも、資源の上限を設けること
- 制御系（Control Plane）の内部でも、不要な全権限を一か所に集めないこと
- 多数の計算資源を回収する処理（reclaim）が、大量の再試行（retry）を引き起こさないようにすること
- 電力、発熱、機器の安全を、Resource Policyに含められること
- Compute Grantや資源提供実績を扱えること
- 副作用を持つTaskを、無条件には再実行しないこと
- 実行ごとに結果が変わり得るAI処理について、確認できない正しさを誇張しないこと

製品要求では「何を満たすか」を定めます。NATS、SPIFFE、WASMのように「何を使って実現するか」は、原則として、この段階では決めません。

### 脅威の想定

[THREAT_MODEL.md](THREAT_MODEL.md)は、想定する攻撃者と、安全上の不変条件を定める正本です。

匿名の攻撃者に限らず、次のような主体や状況も想定します。

- 正規のCredentialを持つClient
- 改変された公式Worker
- 多数のIdentityを作るSybil operator
- 侵害されたValidatorやVerifier
- 悪意のあるArtifact
- 侵害されたControl Planeのcomponent
- Federationの設定のすり替え

脅威モデルでは、あらゆる攻撃を防げると仮定せず、次の点を確認してください。

1. どこまでを、EKIの保護の対象にしているか
2. 何を、明示的な信頼基盤として置いているか
3. どの信頼基盤まで壊れた場合は、保証の対象外なのか
4. 単一の主体、Credential、componentが、許された境界を越えて被害を広げられないか

### 実行端末に求める保証

[ASSURANCE_MODEL.md](ASSURANCE_MODEL.md)は、Workerを`trusted / untrusted`の二択にせず、観点ごとに保証を読み分けるための文書です。

「企業が管理する端末だから安全」「匿名だから危険」とだけ判断すると、確認できていることと未確認のことを取り違えます。

現在は、少なくとも次の観点を区別しています。

- Identity
- Execution Environment
- Confidentiality
- Result Integrity
- Independence / Failure Domain
- Operational Reliability History
- Resource Measurement
- Verification Authority
- Evidence Freshness / Revocation

ある観点で保証が強いからといって、別の観点まで保証されたとはみなさないことが重要です。

### 受け入れ場面

[ACCEPTANCE_SCENARIOS.md](ACCEPTANCE_SCENARIOS.md)では、具体的な利用、攻撃、離脱の場面に要求を当てはめ、矛盾や不足を探します。

新しい要求を増やすためだけの確認項目ではありません。具体的な場面に当てはめ、現在の要求だけで必要な判断ができるかを確かめます。

扱う場面には、社内のEndpoint pool、悪意あるClientやWorker、Sybil、Browser Worker、Federation、Compute Grant、非決定的なAI、Artifactの展開、Control Planeの部分的な侵害、大規模なreclaimがあります。

### 品質特性

[QUALITY_ATTRIBUTES.md](QUALITY_ATTRIBUTES.md)は、Requirementを満たすArchitecture候補を比較するための品質特性を定めています。

セキュリティか処理能力の一方だけを最大にする案は選びません。Endpointの利用者への影響、ネットワークの効率、回復のしやすさ、相互運用性、運用のしやすさ、電力と機器の安全などを並べて、両立しにくい条件の関係を確かめます。

ここに挙げる測定項目は、本番運用で達成すべきサービス水準目標（SLO）ではありません。Architectureの候補を比べられる状態にするための、基準です。

### 要求の不足に関する点検

[REQUIREMENT_GAP_REVIEW.md](../plan/reviews/REQUIREMENT_GAP_REVIEW.md)は、要求全体を横断して不足を洗い出した、レビューの記録です。

点検は第三巡まで進みました。組織間連携（Federation）の名前空間、成果物（Artifact）の解析と展開、制御系（Control Plane）の権限分離、大規模な資源回収（reclaim）、電力と発熱に関する境界を確認しています。

ここに書かれた提案そのものは、正本ではありません。必要と判断した内容を製品要求または脅威モデルへ反映して、初めて正式な要求になります。

## 要求のレビューで確認したいこと

要求をレビューする際は、専門用語の細部を確認する前に、次の点を確かめてください。

### 守りたい価値とつながっているか

要求が厳しいほど安全になるとは限りません。

たとえば、すべてのWorkerに企業管理端末と同等のIdentityを求めると、アドホック参加という価値を大きく損ないます。逆に、参加しやすさだけを優先すると、機密データを安全に扱えません。

要求は、[製品価値](../product/value.md)と[製品設計原則](../product/principles.md)の両方に照らして説明できなければなりません。

### 実装方式を先に決めていないか

「mTLSを使う」「NATSを使う」「WASMを使う」といった記述は、それだけではProduct Requirementではありません。

本当に必要なのが「相手を認証し、改変を検出できること」なら、まずその性質をRequirementとして書きます。方式は、Architectureの比較で決めます。

### 保証を言いすぎていないか

次のような例があります。

- Remote Attestationに成功しても、Applicationの意味の上で結果が正しいとは限りません。
- 匿名のWorkerを3台使って多数決をしても、3台すべてが同じ攻撃者に支配されているかもしれません。
- Resultが正しくても、Workerが申告したGPU時間まで正しいとは限りません。
- 署名済みのArtifactであっても、脆弱なparserにとって安全な入力とは限りません。

確認した事実と、そこから保証できる範囲を混同していないか確かめます。

### 失敗したときの振る舞いが分かるか

EKIでは、Workerの離脱やTaskの失敗を、完全にはなくせません。

そのため「失敗しないこと」だけでなく、失敗時にどう扱うかも要求から読み取れる必要があります。たとえば次のような境界です。

- 再実行できるのか
- 安全な側に止まるのか
- 実行されたかどうか分からない状態として、上位へ返すのか
- 大量に離脱したとき、retryを抑えるのか

### 信頼基盤が隠れていないか

「検証済み」「Attestation済み」という言葉だけで終わらせず、誰が、どのPolicyで、何を確認したのかを説明できることが大切です。

信頼基盤をなくすのではなく、**どの信頼基盤に保証が依存するのかを明確にすること**を重視します。

## 分からない用語がある場合

[用語集](../docs/glossary.md)に、EKIで頻繁に使う用語をまとめています。

用語集は理解を助けるための文書であり、Product RequirementやThreat Modelの意味を上書きするものではありません。用語集と正本が食い違っている場合は、正本を基準にします。
