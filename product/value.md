# EKIの製品価値

## 役割

本書は、EKI Fabricが長期にわたり守る製品価値の正本です。通信方式、具体的な製品の選定、実装の構造までは定めません。

## 中心価値

EKI Fabricの中心価値は、**本来なら失われてしまう、一時的で分散した計算の余力を、安全に使える共通の資源に変え、人・組織・社会の認知能力へ還元すること**です。

クラウドの利用量を減らせることは大切な効果ですが、それ自体を最終目的にはしません。中断や失敗を許容できる計算には、中断や失敗の可能性がある資源を割り当てます。高い可用性や耐久性、専用の設備を、すべての計算に一律に求めることはしません。こうして、同じ資本でより多くの認知活動を可能にします。

この価値は、遊休資源が安いことだけには頼りません。計算資源が潤沢になっても、機械が大量に出す依頼や生成物を無条件に信用しないこと、人と端末を優先すること、確認できたことだけを確認済みとして記録することは、引き続き必要です。EKIの価値の中心は、余力の量そのものより、**信頼性が異なる多様な資源について統治上の条件を守って計算を配置し、実行を検証できる形で扱うこと**にあります。今後2〜5年の生成AIとAI Agentの普及を見すえた検討は、[AI時代の価値と位置づけ](../research/ai-era-value-positioning.md)にあります。

## 守る価値

### Human first

業務端末も個人端末も、第一に人が利用するための資産です。計算資源の提供は、人の操作、端末の寿命、電力、発熱、ネットワークの品質を損なわない範囲にとどめます。提供者は、適切な範囲で、いつでも計算資源の提供を減らしたり停止したりできなければなりません。

### Distrust without exclusion

参加する主体をあらかじめ信頼しなければ協力できない基盤にはしません。処理の依頼元（Client）も実行端末（Worker）も、悪意を持つ可能性があることを前提にします。そのうえで、善意のアドホックな参加者が、過度な事前審査なしに価値を提供できる余地を残します。

### Heterogeneity as normal

社員のPC、GPUワークステーション、専用端末、ブラウザ、クラウド、他組織の計算資源、将来登場する機器も、例外として扱いません。資源の種類が異なり、一時的にしか利用できないことを、通常の状態とみなします。

### Managed and opportunistic resources on one fabric

EKIは、使われていない資源だけを扱う特殊な基盤ではありません。専用サーバ、GPUクラスタ、クラウド、既存のオーケストレータが管理するクラスタなどの**管理された資源**と、業務端末、ブラウザ、他組織の余剰などの**一時的・機会的な資源**を、共通の処理依頼（Task）の契約、配置判断、検証、監査によって扱える分散基盤をめざします。

利用者は、まず管理クラスタの運用基盤としてEKIを使い始め、あとから遊休資源を加えられます。逆に、遊休資源を活用しにくい環境でも、管理された資源の統治だけで価値が成り立つようにします。

ただし、管理された資源にも、信頼の免除はありません。「管理されている」ことは、保証の水準を上げる根拠の一つにはなります。それでも、結果（Result）の検証を省いてよい理由にはなりません。また、KubernetesやSlurmのような既存のオーケストレータを置き換えるのではなく、資源の供給元として接続し、その上でTask契約、配置、検証、監査を共通にします。一つのオーケストレータにしか対応しなければ、その製品に固有の拡張機能との違いがなくなります。そのため、複数の系統に対応できることを重視します。接続方式の検討は、[既存オーケストレータとの接続、およびSEI・TEIとの層構造](../research/orchestrator-integration-and-layering.md)にあります。

### Compute where it is economically sensible

計算能力だけでなく、データの局所性、転送量、利用者への影響、電力、信頼性の要求、セキュリティ、外部の利用料金まで含めて、全体として意味のある場所で処理します。計算を分散させること自体は目的にしません。

### Cognitive abundance

使われていない計算資源は、単なる費用削減の手段ではありません。費用対効果の理由で普段は省かれる、観察、比較、分類、検証、探索、再索引、候補の生成といった認知活動に、余力を回せるようになると考えます。計算の余力が増えるほど、組織がより多くの認知活動を行える構造をめざします。

ここでいう認知処理は、大型のLLMだけを指しません。小型の分類器、embedding、異常検知、疎な連想・再帰型のネットワーク、ローカルの軽量LLM、より大きな推論モデルなど、計算の特性が異なる処理を、CPU、GPU、NPUなどの資源へ適切に配置できることを含みます。

ただし、認知処理の意味や正しさを管理する責任はEKIにはありません。どの認知を行うべきか、結果をObservation、Hypothesis、Decisionなどのどの意味で扱うかは、利用側のProductとworkload契約の責務です。

### Interoperability before ecosystem lock-in

SEI Cognition、TEI、SUI Sensemakingは重要な最初の利用者です。しかし、EKIをそれらの内部実装にはしません。まだ知られていないOSS、他社製品、Webアプリケーション、異なる言語や実行環境からも、同じ基盤を使えることを重視します。

### Verifiable contribution

計算資源の提供は、必要に応じて、検証できる提供実績（Contribution）として記録できるようにします。ただし、EKI自身は通貨、市場価格、現金化、交換レートを提供しません。Contributionをどのような社会的・経済的価値に結びつけるかは、各主体や外部の制度に任せます。

### Public-interest extensibility

企業、クラウド事業者、個人などが、余剰の計算資源を公益性の高い活動に提供できる構造を妨げません。提供者と受益者が、互いを全面的に信頼していなくても協力できることを価値とします。

## 隣接Productとの境界

SUI Sensemaking、SEI Cognition、TEIから、認知、検証、生成、シミュレーションなどの処理依頼を受け取る場合でも、EKIが所有するのは、**計算を安全かつ合理的に実行できる資源へ配置し、その実行を検証できる形で扱う境界**です。

```text
SUI / SEI / TEI
  = application / cognition / formal meaning

EKI
  = compute placement / execution fabric
```

そのため、EKIの中核には、SUIの仮説（Hypothesis）、SEIの判断（Decision）、TEIの業務上の意味の正本などを複製しません。EKIがこれらを必要とする場合も、application semanticsとして理解するのではなく、資源要件、データの局所性、信頼と分離の要件、期限、中断の可否、結果の検証方式といったworkload契約に置き換えて受け取ります。

また、EKIが実行端末を選んだこと、計算が成功したこと、複数の端末が同じ結果を返したことだけでは、利用する側の判断が意味の上でも正しかったことにはなりません。

この分離によって、認知系のOSSが進化し、処理の種類が変わっても、EKIを汎用の分散計算基盤として独立して利用できます。

### TEIはEKI上で稼働する

TEIは、EKIを参照したり操作したりする管理者側の製品ではありません。**EKIを実行基盤の一つとして使い、その上で稼働する利用側**と位置づけます。TEIが業務の意味を定義し、EKIは資源の種類にかかわらず、その実行と配置を統治します。依存の向きは、TEIからEKIへの一方向です。

- TEIは、資源の種類（どのクラスタか、端末か）やEKIの内部構成を知らずに、workload契約として実行を依頼します。
- EKIは、TEIの業務の意味を学習も保持もしません。EKIで計算が成功しても、TEI上の業務の事実が確定するわけではありません。
- 業務アプリケーション本体の常時稼働のように、開始と終了のある実行試行として扱えない仕事は、EKIが主に扱う領域の外です。既存のオーケストレータに任せます。
- EKI Kernel、Local Governor、署名権限、およびEKIが停止しても使える最小限の運用手段は、TEIに依存させません。EKIの管理画面をTEIで作る場合も、「EKIを直す画面が、EKIの停止で動かなくなる」という循環を作りません。

TEI側で、EKIを実行のTargetやProviderとしてどう定義するかは、TEIリポジトリの正本で決めます。

### 統治の方針は、利用者の経路から入れない

SEIのような製品が組織の統治に利用される場合でも、依頼元（Client）が添えた情報だけを理由に、EKIが予算、配置条件、権限を拡張することはしません。統治の方針をEKIで有効にする行為は、組織の管理者の権限（Administrative Plane）の経路で扱い、利用者としての権限とは分けます。SEIは利用者として依頼を出し、EKIの記録を統治の証拠として参照できます。ただし、その記録は、SEIの判断が正しかったことを意味しません。

### 端末の局所の判断は、隣接Productを待たない

業務端末では、利用者の本来の作業と端末の安全を守る判断を、中央のSchedulerより先に、端末側のLocal Governorが下します（Principles §4）。この判断は、中央との通信が途切れていても成り立たなければなりません。

同じ作者の関連製品群（以下、製品ファミリー）では、各製品が他の製品の稼働や承認を待たずに、自分の範囲で完結させる局所のループを「反射弓」と呼び、設計の原則として検討しています。EKIのLocal Governorは、この原則をもっともはっきり示す例です。

SEI Cognitionの側には、製品をまたいだ認知を記録し、時間をかけて再構成する「統合の頂点」として、SEIを位置づける提案があります。この提案でも、SEIは、他の製品へ命令する頂点にも、止まると他の製品まで止まる頂点にもなりません。EKIとの関係は次のとおりです。

- SEIは、EKIの反射弓には入りません。Local Governorの判断に、SEIの稼働、承認、助言のどれも必要ありません。
- SEIからEKIへ渡るのは、計算を実行してほしいという依頼だけです。EKIは、それをworkload契約に置き換えた条件として受け取り、配置と実行を、自分のAuthorityで決めます。
- EKI Coreは、SEIのObservation、Decision、Unknownなどの意味を、学習も保持もしません。
- EKIは、SEIへ何も送らなくても、単独で成り立ちます。

「反射弓」と「統合の頂点」は、設計を説明するための比喩です。ここからRequirementやfieldを導き出すことはしません。SEI側の提案とEKIとの概念の対応は、[SEI Cognitionとの対応ノート](../research/sei-cognition-mapping.md)にまとめています。

## EKIが価値としないもの

- すべての計算を分散すること
- すべての資源を、最大の使用率まで使い切ること
- Workerの数や総FLOPSそのものを、成功の指標にすること
- 高可用性のクラスタや既存のオーケストレータを置き換えること自体を、目的にすること。管理されたクラスタは、資源の供給元として接続します。
- 匿名の参加者を、善意だと仮定すること
- 独自の経済圏や投機の市場を作ること
- 利用者を、特定のクラウド、Runtime、言語、GPUベンダーに固定すること
- 認知、判断、sensemaking、業務モデルの意味を、EKI Coreの正本として所有すること
