# Operator CA の運用手順

Operator と Administrator は、Control Plane とは**別の入口**（別ポート・別 CA）から入ります（[ADR-0038](../../plan/adr/0038-operator-and-administrator-authentication.md)）。この文書は、その CA を**発行・更新・失効**する手順をまとめたものです。

**この文書は手順であって、決定ではありません。** 決めたこと（なぜ別の入口なのか、なぜ秘密鍵を EKI が持たないのか）は ADR-0038 にあります。

## 1. 前提: EKI が持たないもの

EKI は次のものを**持ちません**。配備が用意します。

- **CA の秘密鍵**。
- **Operator／Administrator の秘密鍵**。
- **証明書の配布経路**（ファイル、OS のストア、HSM など）。

EKI が読むのは**公開鍵証明書だけ**です（`operator_ca_file`、`operator_cert_file`、`operator_key_file`）。**秘密鍵が EKI の設定に現れることはありません**。現れていたら、その配備は設計と違います。

## 2. 発行

1. **申請者を確認する。** 誰が Operator か Administrator かは、**技術ではなく運用の判断**です。EKI は役割を証明書から読みますが、**その人を選ぶのは配備**です。
2. **役割 URI を1つだけ入れる。** 証明書には
   - 主体を表す URI（`eki://<domain>/operator/<name>` または `.../administrator/<name>`）を**1つ**、
   - 役割を表す URI（`eki://<domain>/role/<role>`）を**1つ**。

   両方の役割を入れた証明書や、主体と役割が食い違う証明書は、EKI が**読み込み時に拒否**します（`internal/core/operatorcert`）。
3. **有効期間を短くする。** Operator の証明書は**人の操作のため**に使われます。長く持つ必要はありません。**更新の手間より、漏えいしたときの被害の小ささ**を優先します。
4. **発行の記録を残す。** 誰に、いつ、どの役割で出したか。**EKI はこの記録を持たない**ので、配備の台帳に残します。

## 3. 更新

1. **期限の前に更新する。** CA の期限が切れると、**Operator の入口が丸ごと止まります**（EKI は起動時に CA の有効性を確かめ、期限切れなら**起動を拒否**します）。
2. **CA を替えるときは、両方を信頼する期間を作る。** 新しい CA に切り替えた瞬間に古い証明書が通らなくなると、**更新の途中で Operator が閉め出されます**。移行のあいだは、新旧どちらの CA も検証できる構成にします。
3. **切り替えたら、設定の `trust_domain` と CA のファイルを同時に替える。** 片方だけ替えると、**証明書は正しいのに主体の解釈が変わる**状態が生まれます。

## 4. 失効

1. **まず入口を閉じる。** EKI は証明書の失効一覧（CRL／OCSP）を**見ません**。失効は**配備側で経路を断つ**ことで効かせます（CA を替える、その証明書を配れなくする、ネットワークで遮断する）。
2. **失効したら、その Operator が承認した版を確認する。** 承認は台帳に残っています（`GET /v1/operator/trust-bundles/approvals`）。**どの版が、誰の承認で受理されたか**を追えることが、この経路を分けた理由です。
3. **必要なら Trust Bundle を戻す。** 失効した主体の承認で受理した版が問題なら、**新しい版で置き換えます**（版は履歴として残り、Administrator の署名が要ります）。

## 5. 秘密鍵の保管

- **Operator／Administrator の秘密鍵は、その人の端末か HSM に置きます。** Control Plane のサーバに置くと、**入口を分けた意味が半分になります**。
- **Administrator の署名鍵は、EKI の外にあります**（ADR-0038 §6）。Control Plane が持つのは**公開鍵だけ**で、**署名つき版を作ることはできません**。持たせたくなったら、それは設計の変更です。

## 6. 点検の観点（運用のレビューで見るもの）

- 証明書の**残り期間**（CA と各 Operator）。
- **役割の持ち主**が実際の担当と合っているか（異動・退職）。
- 承認の台帳に、**説明できない版**が無いか。
- `audit_unrecorded` の数（[ADR-0040](../../plan/adr/0040-audit-records-and-retention.md)）。**0 でない期間は、記録が欠けています**。

## 7. 未決

- 失効を**EKI の中で**扱うか（CRL を読むか）。いまは配備の責任です。
- CA の**移行期間**を何日にするかの目安。証明書の寿命と運用の頻度で変わります。

## 8. 「どの鍵で受理したか」を読む

版が受理されたとき、記録には**2つの鍵の情報**が入ります。**役割が違う**ので、読むときに区別してください。

| 項目 | 何を表すか | 誰が決めるか |
| --- | --- | --- |
| `key_id` | **署名側が名乗った名前** | **Administrator のツール**（EKI は対応を検証しません） |
| `verified_key` | **実際に検証した公開鍵の指紋**（SHA-256） | **EKI**（鍵から計算するので偽れません） |

- **`key_id` だけで「誰の鍵か」を判断しないでください。** 同じ鍵に複数の名前を付けることも、**別の鍵が同じ名前を名乗る**こともできます。
- **`verified_key` を設定の鍵と突き合わせてください。** 設定している鍵の指紋は、**公開鍵の SHA-256** です。**一致しなければ、その版は想定していない鍵で受理されています**。
- **移行期間（ADR-0038 §7）では、2つが食い違って見えることがあります。** 古い鍵と新しい鍵を並べて受け付けているので、**`verified_key` が新しい鍵を指していれば移行は進んでいます**。旧鍵を外す判断は、**受理済みの版の `verified_key` がすべて新鍵になったこと**で行えます。

**記録の場所**: 版の記録は**状態ストア**に残ります（ログではありません）。ログにも同じ内容が出ますが、**保持が短い**ので、監査にはストア側を使ってください（ADR-0040）。

## 9. issuer fingerprint の移行（2026-11-04）

`IssuerFingerprint` の計算を直したため（#466）、**この修正より前に発行した版は issuer の fingerprint が古い値**です。修正後のプロセスは正しい値で照合するので、**そのままでは一致しません**。

**やること**:

1. **版を発行し直す**（新しい値で issuer を書く）。
2. **先に新しい版を受理**してから、旧い版を外します。順序を逆にすると、**照合に失敗する時間**ができます。
3. 署名鍵も変わっている場合は、**ADR-0038 §7 の鍵集合**で**旧鍵と新鍵を並べて受け**、その間に版を作り直します。

**失敗したときの見え方**: issuer の照合に失敗すると**接続が拒否されます**（fail closed）。**「版が無い」と同じ扱いにはなりません**（[ADR-0036](../../plan/adr/0036-trust-bundle-distribution-and-rotation.md) の追記）。

**確かめ方**: 版の履歴（`GET /v1/operator/trust-bundles/versions`）に `verified_key` が出るので、**古い版が残っていないか**をここで確認できます。
