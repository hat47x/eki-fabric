# EKI Fabric 用語集

この用語集は、EKI Fabricの文書を読む際に意味を取り違えやすい言葉を、EKIでの使い方に限定して説明するものです。

一般的な定義を網羅することは目的にしていません。同じ用語が別分野で異なる意味を持つ場合は、EKIのRequirementやThreat Modelでどの意味を採っているかを優先します。

## Accepted Result / 受理済みの結果

Workerが返した結果を、そのまま正しいものとして扱うのではなく、Taskに必要な検証を通過した後の結果を指します。

EKIでは、Workerが返した直後の情報と、利用側が信頼してよい状態になった結果を区別します。

関連: `Result Claim`, `Worker Assurance`

## Ad-hoc participant / アドホック参加者

長期契約や強い事前審査を必須とせず、一時的に計算資源を提供する参加者です。個人PCやブラウザからの一時参加などを含みます。

アドホックであることは、善意でも悪意でもあることを意味しません。EKIでは、参加しやすさと、Task結果や機密データに必要な保証を分けて扱います。

## Artifact / 成果物

Taskの入力、Executor、モデル、生成物など、識別して受け渡すデータのまとまりです。

保存場所のURLそのものをArtifactの正体とせず、内容の完全性を検証できる識別を持たせることを要求しています。

## Assurance / 保証

「このWorkerは信頼できる」と一括りにせず、Identity、実行環境、機密性、結果完全性、独立性など、何をどこまで確認できるかを表します。

EKIでは単一のTrust Levelより、複数軸の保証として扱う方針です。

## Attestation / Remote Attestation

端末や実行環境が、期待された状態にあることを外部から確認するための仕組みです。

重要なのは、Attestationが成立したからといって、Taskの意味上の答えまで自動的に正しいとは限らないことです。EKIでは「実行環境についてのEvidence」と「Resultの意味上の正しさ」を分けます。

## Beneficiary / 利用主体

Compute Grantなどを通じて、他者が提供した計算資源を利用する主体です。

ProviderとBeneficiaryは同一組織の場合も、別組織の場合もあります。

## Client / クライアント

EKIへTaskを依頼する側のソフトウェアまたは主体です。

SEI Cognition、TEI、SUI、未知のOSS、Webアプリ、他社製品などがClientになり得ます。

`Client`という名称は善意を意味しません。認証済みClientも改変・侵害され得るものとして扱います。

## Compute Grant

Providerが、自身の計算資源について、対象、期間、上限、Data Class、優先度、停止条件などを定めたうえで、他主体が利用できるようにする利用枠です。

現金や通貨そのものではありません。

## Contribution / 資源提供実績

WorkerやProviderが、計算、待機能力、帯域などの資源を提供した事実を表します。

EKIでは、将来の価値交換に利用できるよう記録する余地を持たせますが、Contributionそのものを通貨とは定義しません。

## Contribution Record / 資源提供実績の記録

資源提供実績について、提供主体、Resource Class、量、対象Task、測定方法、検証状態などを記録したものです。

Workerの自己申告だけで価値あるContributionが成立することは前提にしません。

## Control Plane / 制御プレーン

Taskの受理、Policy判断、配置、Lease、検証など、Fabric全体を統制する側の機能群を指す概念です。

現時点では具体的なプロセス構成や製品を指しません。

## Data Class / データ分類

TaskやArtifactが扱うデータの機密性区分です。

公開データ、社内限定、機密など、どのWorkerへ配置できるかを判断する材料になります。具体的な分類体系は今後の設計事項です。

## Executor / 実行体

Taskの具体的な処理を実行する実装単位です。

たとえば画像変換、Embedding生成、文書解析などがExecutorとして提供される可能性があります。ClientがTaskを投入できることと、新しいExecutorを任意に配布できることは別の権限として扱います。

## Fabric / ファブリック

EKIの名前に使っている語で、複数の異質な計算資源を、Policyや保証条件を保ちながら接続する基盤全体を表します。

固定した一つのクラスタだけを意味しません。

## Federation / 連合

異なる管理主体が、それぞれのIdentityやPolicyの管理権を保ったまま、限定された範囲で協力することです。

Federationしたこと自体を、相手組織への包括的な信頼とはみなしません。

## Human-first / 人間優先

業務端末や個人端末では、端末利用者の本来の作業を分散計算より優先する原則です。

CPUやGPUが空いているように見えても、ネットワーク、温度、電力、利用者の復帰などを考慮し、必要なら資源提供を止めます。

## Identity

Client、Worker、Providerなどを暗号学的・運用的に識別するための情報です。

Identityが確認できることと、その主体の結果が正しいこと、任意の権限を持つことは別です。

## Lease / リース

一定時間だけTaskの実行権やResourceへの権限を渡す考え方です。

Workerが消えたり通信断になったりした場合、永続的にTaskを保持したままにせず、期限切れ後に別Workerへ回せるようにするために利用できます。具体方式は設計段階で決定します。

## Opportunistic Worker / 機会的ワーカー

常時稼働を期待せず、安全に使える余力があるときだけ参加するWorkerです。

業務端末、個人PC、ブラウザなどが代表例です。離脱を異常事象ではなく通常の状態変化として扱います。

## Policy / ポリシー

誰が何をできるか、どのTaskをどのWorkerへ置けるか、どの程度の資源を使えるか、といった制約を表します。

Clientの自己申告だけで安全性を弱められないことを要求しています。

## Provider / 提供主体

CPU、GPU、メモリ、帯域などの計算資源をEKIへ提供する主体です。

企業、個人、クラウド事業者、大学などがProviderになり得ます。

## Reflex arc / 反射弓

同じ作者の関連製品群（製品ファミリー）の設計検討で使う比喩です。各製品が、他製品の稼働や承認を待たずに、自分の範囲で完結させる局所の判断ループを指します。

EKIでは、業務端末のLocal Governorが、利用者の復帰、温度、電源、opt-outなどを理由に、中央Schedulerを待たずに資源提供を縮小・停止できることが代表例です。SEI Cognitionなどの他製品は、このループに入りません。

あくまで比喩であり、ここから新しいRequirementやfieldを導きません。厳密な条件はRQ-005〜RQ-007とRQ-053を参照してください。

関連: `Human-first`, `Resource Governor`

## Resource Class

異なるハードウェアを価値や能力の面で扱いやすくするための資源分類です。

「GPU 1時間」のような単純な時間だけでは性能差を表せないため、ContributionやGrantでは能力区分と量を分けて扱う方向で検討しています。

## Resource Governor / 資源ガバナ

Worker側で、実際にどれだけ資源を提供してよいかを最終的に制限する役割を表す概念です。

中央側が高い上限を許可していても、利用者の操作、温度、電源、ネットワーク、ローカル設定などを理由に、Worker側がより厳しく制限できることを要求しています。

## Result Claim / 結果の申告

Workerが返した未検証の結果です。

「このWorkerはこの結果を返した」という事実と、「その結果が正しい」という判断を分離するための概念です。

## Sybil attack / Sybil攻撃

一つの攻撃主体が多数のIdentityを作り、あたかも多数の独立した参加者が存在するように見せる攻撃です。

たとえば3台中2台の一致を正しいとする方式でも、その3台すべてを一人の攻撃者が作れるなら強い保証にはなりません。

## Task / タスク

ClientがEKIへ依頼する計算の単位です。

必要なCPU/GPU、期限、再実行可能性、機密性、結果検証条件などを表現できる必要があります。具体的なwire formatはまだ設計していません。

## Trust Domain / 信頼ドメイン

あるIdentity体系を管理する境界です。組織、管理環境などが一つのTrust Domainになる可能性があります。

異なるTrust Domain間で協力しても、相手のすべてのIdentityや権限を無条件に信頼するわけではありません。

## Validator

Workerが返した結果がTask固有の条件を満たすか確認する仕組みです。

すべての処理に共通する万能Validatorを想定していません。数値計算、変換、AI処理などで確認方法は異なります。

## Verifiable Computation / 検証可能計算

実行したWorker自体を信用しなくても、計算結果が期待するProgramとInputの関係から得られたことを、暗号学的なProofなどで確認する考え方です。

強力な方法ですが、すべてのTask、とくに大規模GPU処理で現実的なコストになるとは仮定していません。

## Worker / ワーカー

計算資源を提供し、Taskを実行する側です。

業務PC、GPUワークステーション、サーバ、ブラウザ、外部参加者の端末、クラウド資源などがWorkerになり得ます。

Worker Agentが正規版であること、長期間正しく動いていたこと、企業所有であることだけを理由に、結果や自己申告を無条件には信用しません。

## WorkOrder / 作業指示書

外部Clientからの要求をそのままWorkerへ流さず、認可、Policy、資源上限などを確定した後にWorkerへ渡す内部実行命令として検討している概念です。

現時点では上流要件から導かれた設計候補であり、wire schemaや正式名称を採用済みとはしていません。

## ADRで使う訳語

`plan/adr/`のADRでは、読みやすさのため、次の概念名を日本語にして書き、各ADRの初出に英語を括弧で添えています。ここに挙げる訳語は表記をそろえるためのものであり、意味の正本は各Requirementと設計文書です。

| 英語 | ADRでの訳語 | 補足 |
|---|---|---|
| Attempt | 試行 | 同じTaskに対する一回ごとの実行 |
| Authority | 権限主体 | 認可判断を発行する役割。善意や信頼性を意味しない |
| Decision（署名付き） | 認可判断 | Authorityが署名して発行する判断。Leaseや作業指示書などを含む |
| Principal | 主体 | 認証された呼び出し元の識別 |
| Admission | 受理審査 | Taskを受け付ける段階の検査 |
| Local Governor | 端末側ガバナ | 端末上で資源提供を縮小・停止する局所の判断 |
| Key Registry | 鍵レジストリ | 管理者が管理する署名鍵の登録簿 |
| Trust Store | 信頼ストア | 検証側が持つ公開の信頼情報 |
| State Store | 状態ストア | Taskなどの状態を永続化する部品 |
| Resource Provider | 資源プロバイダ | 管理クラスタなどから実行枠を供給する接続先 |
| Claim | 申告 | 検証されるまで事実として扱わない主張 |
