# TEI利用からの圧力の評価（PAS-CAND-17〜23とSpike）

## 役割

TEIがEKIを実行基盤として使う場面から出てきた候補Scenario 7件と、[TEIの仕事の投影Spike](../spikes/tei-workload-projection/README.md)の観測を、既存のRequirement、Assurance Model、Architecture Baselineで扱えるかという観点で評価した記録です。問い直しの背景は[TEIから使う分散基盤としてのEKI](../research/tei-usage-requirements-review.md)にあります。

[PAS-CAND-07〜16の評価](PAS_CAND_07_16_EVALUATION_2026-10-06.md)と同じ方針をとります。Requirementを増やすこと自体は目的にしません。既存の要求で扱える候補は、そのまま扱えると結論します。

前回の評価と違い、本評価では**正本（`requirements/`）の文言を変えていません**。Requirementの草案と、既存Requirementへの追記案は、すべてこの文書に置き、レビューを待ちます。理由は、草案の一部（「つなぐ」形態、資源プール）が、MVPの範囲と優先順位に影響し得るためです。

## 結論

| 区分 | 候補・観測 | 結論 |
|---|---|---|
| 既存要求で扱える | 20、21 | 追加のRequirementは不要。Architecture側の観点として残す |

## 個別の評価

### PAS-CAND-17 — 人が待っている、設計候補の一斉評価

- 既存の根拠: RQ-008、RQ-011、RQ-014、RQ-017、RQ-019、RQ-021。
- 不足: 既存の要件は、Taskを一件ずつ受理し、配置し、検証する形だけを想定している。Spikeでは、TEIの決定的な操作（5〜11ミリ秒）より、EKIへ一件投げる往復（受理の永続化だけで中央値10.2ミリ秒）の方が長かった。配置と検証が加われば差はさらに開く。RQ-014（分散した方が不利なら分散しない）は正しく働くが、その結果、続けて来る小さな依頼で遊休資源を使う道がなくなる。
- 不足: `priority`は順番の希望であり、応答時間の見込みや、人が待っている仕事と背景の仕事を分ける単位にならない。
- 措置: RQ-055（二つの利用形態）とRQ-056（管理者が定義する等級）の草案を下に置く。

### PAS-CAND-18 — 運営者の異なる二つのプールでの、再現ビルドの照合

- 既存の根拠: RQ-021（検証の方法を選べる）、RQ-022（独立性）、RQ-026（実行体の来歴）、RQ-029（任意の取得をしない）、RQ-044（検証の権限）、Assurance ModelのRA-2とAxis E（resource provider、operatorの次元）。
- 評価: 要件の方向は揃っている。Spikeで新しく分かったのは、二経路での一致が、EKIの検証より先に、**実行体の設定（`-trimpath`、toolchainの版）で決まる**こと。RQ-026は「許可されたExecutorと、実際に実行されるArtifactが同一であること」を求めるが、結果を左右する実行の設定が、Executorの同一性に含まれるかは書かれていない。
- 措置: RQ-026への追記案を下に置く。
- Architecture側の観点: TaskRequestに保証の要求（RA、経路の数、独立性の次元、同等の判定方法）を書く場所を設ける。Resultの来歴にRuntime Classを入れる。Runtime Classの開示は、Workerの識別情報の開示ではないことを、RQ-018・RQ-040との関係で設計に明記する。

### PAS-CAND-19 — 期限までに必ず終えたい、リリース前の一括検証

- 既存の根拠: RQ-010、RQ-012、RQ-016、RQ-017、RQ-024、RQ-034（Compute Grant）、RQ-052。
- 不足: 期限に向けて保証された容量へ引き上げる規則と、その予算の権限が、要件にない。Compute Grantは「提供者が利用枠を与える」モデルで、利用者の側から見た「間に合わせるために、どこまで使ってよいか」の枠ではない。
- 不足: 費用の記録の単位が決まっていない。ADR-0010により、EKI Coreの契約には価格の語彙を入れられない。物理量で記録し、換算をCoreの外に置くことを、要件として明示しておく必要がある。
- 措置: RQ-057（期限に向けた引き上げと、物理量での消費の記録）の草案を下に置く。
- クラウドの関数実行の自動再試行は、RQ-054の草案（下位の見えない再実行）で扱える。RQ-054の草案の「資源提供基盤」に、クラウドの関数実行やキューを含めることを、レビューで確認する。

### PAS-CAND-20 — 系統の異なる評価者による、画面の評価

- 既存の根拠: RQ-009、RQ-021、RQ-022、RQ-026、RQ-039、RQ-045、PAS-CAND-04、PAS-CAND-08の評価（Axis Eへのmodel lineageの追加）。
- 評価: 既存の要求で扱える。Spikeで、受理の上限が全Taskで共通の一組しかないため、大きな仕事だけが拒否された。これはRequirementの不足ではなく、受理の方針の設計（ADR-0006のM0の簡略化）の問題。
- Architecture側の観点: 受理の上限を、等級またはExecutorごとに分ける（RQ-056の草案と合わせて扱う）。

### PAS-CAND-21 — 資源プールの予実を良く見せる

- 既存の根拠: RQ-019、RQ-023、RQ-041、RQ-047、Assurance ModelのAxis F（運用の実績）とAxis G（測定の保証）。
- 評価: 既存の要求で扱える。予実をControl Planeの観測から作り、WorkerやAdapterの申告から作らないことは、RQ-019とAxis Gの`control-observed`の区別から導ける。
- 備考: Axis FはWorker単位で書かれている。資源プールの単位で実績を持つかは、下記のRQ-058の草案（資源プール）と合わせて決める。

### PAS-CAND-22 — 予実と状況の横断的な閲覧と、開示の段階

- 既存の根拠: RQ-018、RQ-028、RQ-039、RQ-040、RQ-041、RQ-051、[既存オーケストレータとの接続](../research/orchestrator-integration-and-layering.md) §7.4（循環の回避）。
- 不足: 管理者が束ねる「資源プール」という単位が、要件にも設計にもない。Worker ClassとDeployment Profileはあるが、日々入れ替わる業務端末を、運用と予実の単位としてまとめるものがない。予実を持つ単位、管理者の権限の範囲、開示の段階の単位として、プールが要る。
- 措置: RQ-058（管理者が定義する資源プール）の草案を下に置く。
- Architecture側の観点: 権限の判断に使う状態と、管理画面のための観測情報の保存先を分ける。現在の`eki-control`には、メトリクスの出力もヘルスチェックの入口もない。予実の管理より先に、観測情報の出口が要る（M4のOTLP計画を前倒しするかの判断）。

### PAS-CAND-23 — 期限を過ぎた、実行されなかった依頼

- 既存の根拠: RQ-011（期限があるかを表せる）、RQ-012、RQ-046。
- 不足: RQ-011は、Taskが期限を持てることを求めるが、期限を過ぎたTaskがどうなるかを求めていない。Spikeでは、期限を過ぎても`queued`のままだった。Clientは、安全に再投入してよいかを判断できない。
- 措置: RQ-011への追記案を下に置く。

## Requirementの草案と追記案

いずれもレビュー前のため、正本（[Product Requirements](../requirements/PRODUCT_REQUIREMENTS.md)）には入れていません。

### RQ-055（草案）— 一件ずつの依頼と、枠の中での連続した依頼

EKIは、少なくとも次の二つの利用形態を区別して表現できなければならない。

- 一件ずつの依頼（Task）。依頼ごとに受理、配置、検証を行う。
- 期限と予算のある枠（Session）を先に開き、その中で、同じ実行体、同じData Class、同じ予算の範囲の小さな依頼を続けて流す形態。

枠を開いたことは、特定のWorkerを使い続ける権利や、資源の予約を意味してはならない。業務端末のLocal Governorは、枠の途中でも資源の提供を止められる（RQ-006）。枠の中の依頼の合計と、そこから派生した依頼は、枠の予算を超えてはならない（RQ-017）。枠の中で検証を省いた結果は、検証済みの結果と区別して返さなければならない（RQ-019）。

理由: 一件では分散する利点がない小さな仕事も、続けて来る全体としては遊休資源を使う価値がある。一件ずつの受理と検証の費用が仕事より大きいと、RQ-014により分散されず、その機会を失う。
非目標: 常時動き続けるサービスの運用。枠には必ず期限がある。

### RQ-056（草案）— 管理者が定義する等級を、利用者の選択の単位にする

利用者が依頼の信頼性、保証、速さの見込み、資源の規模を選ぶ単位として、管理者が定義する等級（Service Class）を使えなければならない。

等級は、資源の上限、保証の水準、独立性の要求、期限の見込み、利用できる資源プールの範囲をまとめる。利用者は、自分に許された等級を選び、その範囲内で条件を狭めることができる。等級より広い条件は書けない。利用者が資源プールやWorkerを直接指定することは認めない（RQ-016）。

受理の上限と未完了の依頼の上限は、等級ごとに分けられなければならない。人が待っている依頼と背景の依頼が、同じ上限を取り合ってはならない。

理由: 利用者側の実装を「投げる」「つなぐ」だけで済ませるには、必須の資源量を毎回決めさせない既定値が要る。また、大きな仕事のために全員の上限を上げることを避けるため。
非目標: 等級を、予算の権限や機密性の保証を利用者が自分で広げる手段にすること。

### RQ-057（草案）— 期限に向けた引き上げと、物理量での消費の記録

期限のある依頼について、遊休資源だけでは期限に間に合わない見込みが高まった場合に、管理者が付与した予算の範囲で、保証された容量を持つ資源プールへ移す規則を表現できなければならない。予算が尽きた場合や、Data Classの条件で移せない場合は、間に合わない見込みを、期限の前に依頼者へ知らせなければならない。

EKIは、期限に必ず間に合うことを保証しない。引き上げの可否は、依頼者の申告ではなく、管理者が付与した予算の権限で決まる。

資源の消費は、依頼ごとに、物理量（CPU時間、メモリ量と時間、関数の呼び出し回数、転送量など）とその観測者（Axis G）で記録できなければならない。金額への換算は、EKI Coreの外の責務とする（RQ-038、ADR-0010）。

理由: 遊休資源と、クラウドを含む管理された資源を一つの基盤で扱う主な利点は、遊休資源で足りない場合に、統治された形で管理資源へ移せることにある。費用を物理量で記録しておかないと、誰の依頼が費用を使ったかを辿れない（RQ-039）。
非目標: 価格の形成、請求、クラウドの費用の最適化そのもの。

### RQ-058（草案）— 管理者が定義する資源プール

管理者は、性質の近いWorkerや資源提供者を、資源プールとして束ねられなければならない。資源プールは、Worker Class、管理主体、Data Classの上限、Assuranceの上限、資源の上限、実行時間の上限を持てる。Workerがどのプールに属するかは、管理者の設定と検証済みの根拠で決まり、Workerの自己申告では決まらない（RQ-047）。

資源プールごとの運用の実績（期限内の完了割合、所要時間の分布、中断の回数、検証の不一致の回数など）は、Control Planeが自分で観測した出来事から作らなければならない。この実績は配置の最適化に使えるが、保証の根拠にしてはならない（RQ-023）。

実績の開示は、利用者、プールの管理者、Fabric全体の管理者で段階を分けなければならない。利用者の権限から、プールの数、種類、所在を列挙できてはならない（RQ-018）。

理由: 業務端末は日々入れ替わるため、Worker単位の実績は薄く、すぐ古くなる。運用の単位、予実の単位、管理者の権限の範囲として、Workerより大きい単位が要る。
非目標: プールを利用者が指定する単位にすること（RQ-056の等級を通して選ぶ）。

### RQ-026への追記案

> 結果を左右する実行の設定（ビルドのフラグ、toolchainの版、依存の固定など）は、Executorの同一性の一部として、管理者が登録する側で固定できなければならない。Clientのparameterによって、結果の再現性に関わる設定を変えられる構造にしてはならない。

理由: Spikeで、`-trimpath`の有無だけで、二経路の成果物のdigestが一致・不一致に分かれた。Clientがこれを切り替えられると、複数経路での照合を、Clientが意図的に失敗させたり、照合の意味を変えたりできる。

### RQ-011への追記案

> 期限を持つTaskについて、期限までに配置または完了しなかった場合の扱いと、そのときに返す状態を、契約として明示しなければならない。期限までに実行されなかったことが確かな場合と、実行されたかどうか分からない場合を、区別して返せなければならない。期限を過ぎたTaskが、未完了の依頼の上限を占め続けてはならない。

## External ContractとArchitectureに残す項目

Spikeで観測した次の点は、Requirementではなく、契約と設計の項目として扱います。

| 項目 | 観測 | 置き場所の候補 |
|---|---|---|
| Artifactの取り込みと結果の取得 | 9種中8種がワークスペースの入力を要し、すべて422。結果の取得は501 | M1の計画どおり。TEIの利用はこれが揃うまで始まらない |
| 実行体のdigestをClient側から固定する | `executor.digest`はschemaで400、拡張は422 | ExecutorRequirementに、安全側への制限としてdigestの指定を加える案。登録済みのdigestと一致しなければ拒否する |
| 副作用の有無、決定性を、Executorの属性として持つ | Clientが`effect_mode: "none"`と書けば、配備の操作も受理された | Executorの登録情報（MVP計画の「admin-registered command executor」）に、効果の種別と決定性を含める |
| Resultの来歴としてのRuntime Class | TEIの証拠は実行環境の区分を要する | TaskResultの来歴の項目 |
| 等級ごとの受理の上限 | 画面の評価だけが共通の上限で拒否された | ADR-0006の後継。RQ-056の草案と合わせて扱う |
| キャッシュの局所性 | ビルドキャッシュの有無で約15倍の時間差 | Placementの費用の入力（Control/Data Plane §42）に、ビルドキャッシュと依存のキャッシュを含める |
| toolchainと依存の事前配置 | TEIの`go.mod`の指定で、別版のtoolchainが選ばれた | Runtime Classの定義。Worker内のネットワーク取得はRQ-029で認めない |
| 観測情報の出口 | `eki-control`にメトリクスもヘルスチェックもない | M4のOTLP計画。予実の管理の前提 |

## 分散認知としての利用で、何を測るか

[研究メモ](../research/tei-usage-requirements-review.md) §4.7で、ジョブの指標の代わりに、最初の結果までの時間、期限内の完了割合、検証済みの割合、達成した独立性、中断と再配置の回数、本来の作業への影響、委譲の連鎖の消費を候補に挙げました。これらはRequirementではなく、[Quality Attributes](../requirements/QUALITY_ATTRIBUTES.md)と、成功指標を定める[ADR-0008](adr/0008-product-value-evidence-metrics.md)の候補として扱うのが適切です。採用するかは、Quality Attributesの次の見直しで決めます。

利用側が返す「採用された」などの評価を、EKIの最適化に使うかは、Open Questionとして残します。

## 残る課題

1. RQ-055〜RQ-058の草案と、RQ-026・RQ-011への追記案のレビュー。
2. RQ-055（枠）を、MVPの後のどの段階で扱うか。M0〜M1の優先順位（[Upstream Plan](UPSTREAM_PLAN.md)の2026-09-27 mainline priority guard）は変えない前提で、M2以降の候補とするか。
3. 研究メモ§7のOpen Question。
4. TEI側で、EKIを実行先としてどう定義するか（プラグインの起動経路か、配備Executorか）は、tei-platformリポジトリで決める。本評価は、EKI側で成り立つべき条件だけを扱う。
