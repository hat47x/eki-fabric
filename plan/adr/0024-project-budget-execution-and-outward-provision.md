# ADR-0024 SEIの判断の執行：案件の予算の執行と、組織の余力の外部への提供

- 状態: **採用**
- 日付: 2026-10-22
- 関連: Issue [#142](https://github.com/hat47x/eki-fabric/issues/142)、[#143](https://github.com/hat47x/eki-fabric/issues/143)、[ADR-0013](0013-product-core-and-faces.md)、[ADR-0014](0014-authorities-for-delegation-budget-capacity.md)、[ADR-0019](0019-sandbox-face-isolation-levels-and-frontends.md)、[ADR-0021](0021-observation-plane-and-disclosure-tiers.md)、[ADR-0022](0022-mandate-operation-classes-and-thresholds.md)、[ADR-0023](0023-autonomy-scope-and-request-interfaces.md)、RQ-018、RQ-031、RQ-033、RQ-034、RQ-035、RQ-036、RQ-052、RQ-057、RQ-061、SEC-030

## 1. 背景

ADR-0013で、EKIはSEIの判断を執行し、予実と提供の記録を証跡として返す役割を担うことにしました。代表的な対応は二つです。

- SEIが自動で立ち上げた案件に、予算の枠を割り当てて計算を執行する（#142）。
- 組織の余力を、EKIのネットワークを介して、研究機関や取引先へ安全に提供する（#143）。

ADR-0014で予算（BUD-1）と容量（CAP-1）の権限を、ADR-0022で委任状で委任できる操作の区分を、ADR-0023で承認と通知の形を定めました。このADRは、それらの上で二つの対応を組み立てます。

## 2. 決定

### 案件の予算の執行

1. 案件は、EKIの中では、予算の枠（BUD-1の入れ子の一段）と、それを使う依頼（TaskやTask Group）として表す。案件の名前や目的は、EKIでは意味を持たない識別子として扱い、意味との対応はSEIの側で持つ（Principle 7）。
2. 案件の予算の枠は、委任状を持つSEIが、親の枠の中で作る。これはADR-0022の「範囲内の拡大」にあたり、閾値（一つの配分先へ親の枠の30%など）を超える場合は人間の承認を経る。枠の期間は、委任状の期限を超えない。
3. 案件で依頼を出す主体には、DLG-1が利用の許可を与える。SEIがClientとして依頼を出す場合も、委任状を使う識別とは分けたClientの識別を使う（RQ-061）。
4. 依頼の予算と、費用を生む容量（CAP-1）の予約は、案件の枠から行う。案件の枠を超えた消費は起きない。
5. 案件の予実（枠に対する消費、期限に間に合う見込み、終わった依頼と終わらなかった依頼の数）は、Observation Planeから、照会で返す（ADR-0021）。SEIには、委任先の管理者と同じ段階の開示とし、Workerの識別や内部の構成は返さない（RQ-018）。
6. 期限に間に合わない見込みと、枠の消費が管理者の定めた割合を超えたことは、通知で知らせる（ADR-0023）。
7. 枠の期間が終われば、使わなかった分は親の枠へ戻る。期間を委任状の期限より延ばすには、新しい委任状か、人間の操作が要る。

### 組織の余力の外部への提供

8. 外部への提供は、人間の管理者が定める「提供の方針」の範囲で行う。提供の方針は、資源の区分ごとの上限、提供してよい相手の一覧、Data Classの上限、隔離の水準の下限、提供してよい時間帯を持つ。
9. 提供は、Compute Grantとして行う（RQ-034）。Grantを発行する権限は、Administrative PlaneのCompute Grant Administrationが持つ。既存のGrantの実装のとおり、Grantを発行できるのはGrantが名指しした提供者だけで、狭めるときは失効させて発行し直す。
10. 提供の操作を、ADR-0022の区分に当てはめる。
    - 提供の方針の上限の中で、一覧にある相手へのGrantを発行し直して量を増やす: 範囲内の拡大（委任状を持つSEIに委任できる）
    - 提供を縮小する、止める: 安全側の操作（SEIにも、EKIの自律の判断にも許す。ADR-0023）
    - 新しい相手を一覧に加える、新しい相手への提供を始める: 人間の承認
    - 提供の方針の上限、Data Classの上限、隔離の水準の下限を変える: 委任できない
11. 提供先の仕事は、組織の端末やサーバで、外部の主体のコードとして動く。そのため、外部への提供に使う委任先には、隔離の水準の下限を設け、既定の雛形ではISO-2以上とする（ADR-0019）。提供先の仕事は、組織の内部のネットワークに参加せず、組織のデータやほかの仕事への権限を持たない（RQ-033、SEC-030）。
12. 内部の需要が増えたとき、EKIは提供の方針に従って、提供を自律的に縮小できる。多数のGrantを一度に縮小するときは、mass reclaimの回復の方針（RQ-052）を通し、提供先の再配置や再試行が集中しないようにする。縮小は、提供先へ通知する。業務端末の持ち主の拒否権は、提供より優先する。
13. 提供した事実は、Contribution Recordとして記録する（RQ-036）。記録を金銭や評価にどう対応づけるかは、組織の外の方針に任せる（RQ-037、RQ-038）。

## 3. 移行

- M0とMVPの優先順位は変えない。案件の予算の執行と外部への提供は、ADR-0013の段階のS7（SEIとの連動）で実装する。外部への提供は、Compute Grantの実装（`internal/core/grant`）をAdapterへつなぐところから始める。
- Authority BoundariesのBUD-1と、Deployment ProfilesのDP-5に、この決定への案内を追記する。版は0.2のままとし、追記の日付を記す。

## 4. 影響

### 良い点

- 案件と外部への提供が、新しい権限を足さずに、BUD-1、DLG-1、CAP-1、Compute Grant、委任状の区分の組み合わせで表せる。
- SEIは、縮小や停止を速く執行でき、拡大は上限と承認の中で行う。外部への提供の開始のように組織の外へ影響する判断は、人間が承認する。

### 悪い点と制約

- 提供の方針と案件の枠の設定が、人間の管理者の新しい仕事になる。雛形を用意する必要がある。
- ISO-2以上の隔離を用意できない委任先は、外部への提供に使えない。業務端末の多いWindowsの環境では、提供に使える端末が限られる。

## 5. 未決事項

- 案件の枠の消費の通知を出す割合の既定値。
- 提供の方針の雛形（資源の区分ごとの上限、時間帯）。
- 提供先との契約や条件（利用規約、データの扱い）を、EKIの記録とどう結び付けるか。EKIは契約の内容を判断しない。
