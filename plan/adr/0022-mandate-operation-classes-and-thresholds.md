# ADR-0022 委任状で委任できる操作を、危険の大きさで四つに分け、承認の閾値の雛形を定める

- 状態: **採用**
- 日付: 2026-10-21
- 関連: Issue [#141](https://github.com/hat47x/eki-fabric/issues/141)、[#142](https://github.com/hat47x/eki-fabric/issues/142)、[#143](https://github.com/hat47x/eki-fabric/issues/143)、[#145](https://github.com/hat47x/eki-fabric/issues/145)、[ADR-0013](0013-product-core-and-faces.md)、[ADR-0014](0014-authorities-for-delegation-budget-capacity.md)、[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)、RQ-016、RQ-060、RQ-061、SEC-027、PAS-CAND-25、PAS-CAND-26

## 1. 背景

ADR-0014とRQ-061で、人間の管理者が管理者権限の一部を、範囲と期限を限った委任状としてSEIなどへ委ねられることを決めました。委任状が持つもの（委任先の主体、委任できる操作、越えさせない線、承認の閾値、期限）と、持たせない権限（自己更新など）は決まっています。

残っていたのは、「どの操作を委任できるか」と「どこから人間の承認を求めるか」です。これが決まらないと、SEIが案件を立ち上げて予算を執行すること（#142）や、外部への提供の方針を出すこと（#143）を設計できません。

PAS-CAND-25では、SEIが外部の文書に仕込まれた指示に影響され、部門の予算の8割を一つの案件へ配分する場面を想定しました。委任状を持つ主体の判断は、範囲の中であっても誤り得ます。

## 2. 決定

1. 管理の操作を、委任したときの危険の大きさで、次の四つに分ける。

   | 区分 | 性質 | 委任状での扱い |
   | --- | --- | --- |
   | 安全側の操作 | 権限や資源を狭める、止める。誤っても、資源が使われないだけで、権限は広がらない | 広く委任できる |
   | 範囲内の拡大 | 人間が定めた枠の中で、配分を変える、許可を与える | 上限つきで委任できる。上限を超えるものは人間の承認を経る |
   | 人間の承認が要る操作 | 組織の外に影響する、元に戻しにくい | 委任状を持つ主体は提案だけを出し、人間が承認して有効になる |
   | 委任できない操作 | 信頼の根拠、安全の下限、委任の仕組みそのものに関わる | 委任状に含められない |

2. 操作ごとの区分を、次のように定める。

   | 操作 | 区分 |
   | --- | --- |
   | 利用の許可を取り消す、狭める | 安全側 |
   | 委任先を一時的に候補から外す | 安全側 |
   | 外部への提供を縮小する、止める | 安全側 |
   | 常駐を失効させる | 安全側 |
   | 予算の枠を減らす | 安全側 |
   | 予算の枠を、親の枠の中で配分し直す（部門、案件） | 範囲内の拡大 |
   | 案件の予算の枠を作る（期間は委任状の期限以内） | 範囲内の拡大 |
   | 登録済みの委任先と等級について、利用の許可を与える | 範囲内の拡大。等級ごとに、委任できる上限を委任状で定める |
   | 等級（Service Class）の優先度の重みを変える | 範囲内の拡大 |
   | 外部への提供の量を、人間が定めた上限の中で増やす | 範囲内の拡大 |
   | 新しい外部の相手への提供を始める | 人間の承認 |
   | 閾値を超える予算の配分 | 人間の承認 |
   | 予算の総額を変える | 委任できない |
   | 委任の等級を定義する、上げる、委任先を候補へ戻す | 委任できない |
   | 隔離の水準の登録、Executorのadmission | 委任できない |
   | Data Classの下限、Trust Root、Federationの関係を変える | 委任できない |
   | 費用を生む容量の確保の閾値を変える | 委任できない |
   | 委任状を発行する、更新する | 委任できない |

3. 閾値の雛形を、次のように定める。雛形は既定値であり、人間の管理者が委任状ごとに狭めたり広げたりできる。ただし、「委任できない」区分の操作は、閾値の設定で委任できるようにはならない。
   - 一つの配分先（部門、案件）へ、親の枠の30%を超えて配分する場合は、人間の承認を求める。
   - 一日の配分し直しの合計が、親の枠の20%を超える場合は、人間の承認を求める。
   - 委任状の期限は、最長30日とする。委任状のもとで出す方針の期限は、委任状の期限を超えない。
   - 委任状を持つ主体が一時間に出せる「範囲内の拡大」の操作の数に、上限を置く。誤りや乗っ取りの影響が広がる速さを抑えるためである。
4. 委任状のもとで出された方針は、どれも、どの委任状のもとで出されたかを記録し、人間の管理者が個別に取り消せる（RQ-039、SEC-027）。安全側の操作も記録する。
5. 委任状を持つ主体の判断の理由（案件の重要性など）を、EKIは評価しない。EKIが守るのは、区分、上限、閾値、期限だけである（RQ-061）。

## 3. 移行

- M0とMVPの優先順位は変えない。委任状は、ADR-0013の段階のS7（SEIとの連動）で実装する。
- Authority Boundariesの委任状の節に、操作の区分を加える。版は0.2のままとし、追記の日付を記す。

## 4. 影響

### 良い点

- 安全側の操作を広く委ねられるので、SEIが「縮小する、止める」判断を速く執行できる。誤っても権限は広がらない。
- 範囲内の拡大には上限と速さの上限があるため、PAS-CAND-25のような偏った配分の影響を閉じ込められる。
- 案件の予算の執行（#142）と外部への提供（#143）を、この区分の上で設計できる。

### 悪い点と制約

- 雛形の数値（30%、20%、30日）は、運用の実績がない段階の値である。実際の組織での運用を見て見直す必要がある。
- 人間の承認が要る操作が多いと、SEIとの連動の速さの利点が減る。

## 5. 未決事項

- 一時間あたりの操作の数の上限の既定値。
- 人間の承認を、何人の、どの役割の人が行うか（Authority Boundaries §16のmulti-party approvalと合わせる）。
- 雛形の数値を、組織の規模に応じて変えるか。
