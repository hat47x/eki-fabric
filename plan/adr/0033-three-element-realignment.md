# ADR-0033 主体・資源・証拠の三要素で上流を再編成し、未決を「決める場所」に割り当てる

- 状態: **提案中**
- 日付: 2026-11-01
- 関連: Issue [#381](https://github.com/hat47x/eki-fabric/issues/381)、[#365](https://github.com/hat47x/eki-fabric/issues/365)、[#354](https://github.com/hat47x/eki-fabric/issues/354)、[#321](https://github.com/hat47x/eki-fabric/issues/321)、[#320](https://github.com/hat47x/eki-fabric/issues/320)、[#316](https://github.com/hat47x/eki-fabric/issues/316)、[#315](https://github.com/hat47x/eki-fabric/issues/315)、[#243](https://github.com/hat47x/eki-fabric/issues/243)、[#198](https://github.com/hat47x/eki-fabric/issues/198)、[ADR-0013](0013-product-core-and-faces.md)、[ADR-0014](0014-authorities-for-delegation-budget-capacity.md)、[ADR-0017](0017-start-and-stop-authority.md)、[ADR-0030](0030-assignment-delivery-pull-and-lease-currentness.md)、[ADR-0031](0031-local-execution-slots-and-resource-reservation.md)、[ADR-0032](0032-task-phase-transition-subjects.md)

## 1. 背景: なぜいま再編成するか

EKI Fabricの上流は、要求（RQ）、脅威、ADR、設計（`architecture/`）が、それぞれ妥当な単位で積み上がっています。しかし**積み上げの軸が統一されていません**。そのため、次のような症状が出ています。

1. **同じ問いが複数の場所で別々に立つ。** 「完了とは何か」は、状態モデル（phase）、結果の受理（AcceptedResult）、公開状態（terminal_code）、そして#365（完了を書ける境界）に分かれて現れます。それぞれは正しいのに、どれが上位の判断かが読み取れません。
2. **決める順序が決まっていないため、下流のIssueが上流の未決で止まる。** #381（`active`→`verifying`の配線）は #267 の残りですが、本質は「検証中という状態を保存するか」という上流の判断に依存します。#365（完了の境界）は「証拠が無い完了を許すか」という判断に依存します。#354（同時実行の予約）は「資源の会計単位を何にするか」に依存します。
3. **「ブロックされた」の意味が曖昧になる。** 実装が止まっているのか、上流の判断が無いのか、単に作業量が多いのかが、Issueの本文からは区別できません。区別できないと、優先順位も付けられません。

このADRは、上流を**三つの要素と、その間の三つの関係**で読み直し、すべての要求・設計・Issueをその関係のどこかに割り当てます。割り当てが決まれば、「何を先に決めるか」は関係の順序から導けます。

## 2. 三要素と三関係

### 2.1 三要素

| 要素 | 問い | 正本 |
| --- | --- | --- |
| **主体（Actor）** | 誰が、何を根拠に、どこまで許されているか | `requirements/`（RQ-006、RQ-042）、`architecture/AUTHORITY_BOUNDARIES.md`、ADR-0014、ADR-0017 |
| **資源（Resource）** | 何を、どれだけ、いつまで使えるか | RQ-057、RQ-058、ADR-0014、ADR-0031、`spec/external`のLease/WorkOrder |
| **証拠（Evidence）** | 何が起きたことを、何で確かめ、何を主張できるか | RQ-026、`architecture/TASK_STATE_MODEL.md`、ADR-0028、ADR-0030 |

三要素は「モノの分類」ではありません。**同じ対象が、どの関係から見るかで別の要素になる**ことが要点です。たとえばAcceptedResultは、主体（誰の結果か）から見れば権限の帰結、資源（どのLeaseの実行か）から見れば消費の記録、証拠（何を主張できるか）から見れば検証の成果です。

### 2.2 三関係

| 関係 | 意味 | 主な担い手 |
| --- | --- | --- |
| **R1 主体 → 資源**（委任） | 主体が、資源の使用を、条件つきで許す | Placement Approval、Lease、WorkOrder、Local Governor |
| **R2 資源 → 証拠**（実行と観測） | 許された資源の上で実行が起き、証拠が生まれる | Attempt、ResultClaim、AcceptedResult、Artifact |
| **R3 証拠 → 主体**（説明と回復） | 証拠にもとづいて、主体へ説明し、権限を更新する | 公開状態、terminal_code、相関ID、reclaim、監査 |

EKIの価値（委任の核）は、**R1・R2・R3が同じ権限の連鎖の上に乗っていること**にあります。どれか一つが欠けると、委任は「許した」「実行した」「確かめた」のどれかが言えなくなります。

### 2.3 関係の順序

決める順序は **主体 → 資源 → 証拠** です。

- 主体が決まらないと、資源の意味（誰のための上限か）が決まりません。
- 資源が決まらないと、証拠の意味（何の実行の証拠か）が決まりません。
- 逆順に決めると、下流の判断が上流に書き換えられ、ADRの整合が壊れます（これが§1の症状2の原因でした）。

## 3. 決定: 上流を三関係で読み直し、未決を「決める場所」に割り当てる

### 3.1 すべてのIssueを三関係のいずれかに割り当てる

Issueの本文の先頭に、**どの要素の、どの関係の話か**を一行で書きます。書けないIssueは、上流のどこかが欠けている証拠であり、Issueを増やすのではなく上流を直します。

割り当ての例（現在のopen Issue）:

| Issue | 要素・関係 | 何を決めるか |
| --- | --- | --- |
| #321 Trust Bundleの配布・更新・失効 | 主体（R1の前提） | 主体の同一性の根拠を、誰がいつ配り、いつ無効にするか |
| #316 依頼できる範囲を拒否前に知る | 主体→資源（R1） | 委任の前に見せる「許される範囲」の表現 |
| #354 同時実行と予約の合計 | 資源（R1/R2の境界） | 資源の会計単位（slot・予約）と、実行中の合算 |
| #320 成果物の本体の保管・取得 | 証拠（R2） | ダイジェストに対応する本体を、どこに置き、誰が読めるか |
| #365 完了を書ける境界 | 証拠→主体（R3） | 証拠が無い完了を、境界で拒否できるか |
| #381 `active`→`verifying`・`active`→`ready` | 資源→証拠（R2） | 証拠を評価中の状態を、保存するか導出にするか |
| #315 受理応答・状態・結果の照合 | 証拠→主体（R3） | 依頼元が自分の依頼と結果を結び付けられる識別子 |
| #243 / #198 配送とwire契約 | R1/R2の運搬 | 何を、どの向きに、どの契約で運ぶか |

### 3.2 ブロックされた課題は「上流の決定」に置き換える

「実装が止まっている」Issueは、次の3種類に分けます。種類が決まれば、次にやることも決まります。

1. **上流の未決で止まっている**（決定が無い）: 決定をADRに書き、Issueは決定への参照に置き換える。例: #381（`verifying`を保存するか）、#365（完了の証拠性）。
2. **上流は決まっているが配線が無い**（決定はある）: 実装Issueとして、変更点・試験・影響を書く。例: #354のAgent側の予約計上。
3. **作業量が多いだけ**（決定も配線も方針もある）: 分割して順に進める。例: #320のArtifact Store。

この分類を、Issueの本文かコメントに必ず残します。分類が無いIssueは、レビューの対象にしません。

### 3.3 各要素の「境界」を先に決める

三関係のそれぞれに、**越えてはならない境界**を一つ置きます。境界が決まれば、下流の実装は境界の内側で自由に決められます。

| 関係 | 境界 | 既存の実装との対応 |
| --- | --- | --- |
| R1 主体→資源 | 資源を使う権限は、署名された判断（Placement Approval・Lease・WorkOrder）にのみ由来する。Workerの自己申告・Control Planeの善意に依存しない | `placementauth`、`leaseverify`、`workorderverify`、`workorderaccept` |
| R2 資源→証拠 | 証拠は、許された資源の上の実行に結び付く。結び付かない証拠は受理しない（Lease・fence・nonceの照合） | `resultclaim`、`resultaccept`、`resultverify`、`CommitAcceptedResult` |
| R3 証拠→主体 | 主体へ主張する状態は、証拠から導けるものだけにする。証拠が無い完了・取消・失敗を、公開状態にしない | `admission.project`、`terminal_code`、`acceptedresult` |

### 3.4 この再編成で解けるもの（ブロックの解消）

- **#381（遷移の配線）**: R2の境界「証拠は実行に結び付く」から、`verifying`は「証拠を評価している状態」であり、実行中（`active`）とは別の状態として保存する必然が出ます。ADR-0032 §2.4の既定（保存する）が、上位から導かれます。ブロックの正体は「保存するかの未決」であり、それは§3.3のR2境界で解けます。
- **#365（完了の境界）**: R3の境界「証拠が無い完了を公開状態にしない」から、汎用CASで`terminal/completed`を書けること自体が境界違反になります。したがって「受理の入口だけが完了を書ける」は、実装の都合ではなく境界の帰結です。残る作業は、Client APIの試験fixtureを受理のcommitへ寄せることだけになります（§3.2の種類2）。
- **#354（同時実行）**: R1/R2の境界から、資源の会計単位は「実行中のPlanの上限の合計」であり、slotは資源の一部（同時実行数の上限）として扱えます。Agent側の予約計上は種類2（配線）です。
- **#321（Trust Bundle）**: 主体の同一性の根拠はR1の前提であり、R1の境界（署名された判断にのみ由来）を成立させるための配布・更新・失効です。ADR-0025の鍵更新とADR-0027のenrollmentの間に位置します。
- **#320（成果物）**: 証拠の本体が無いと、R3の「証拠から導ける」が成立しません。ダイジェストだけの結果は、本体の所在と取得の権限（R3）を伴って初めて証拠になります。

### 3.5 文書の配置

- この三要素・三関係の定義は、このADRを正本とします。
- 要求は引き続き`requirements/`、設計は`architecture/`、判断は`plan/adr/`が正本です。このADRは**それらの読み方と順序**を定めるもので、内容を置き換えません。
- `architecture/`の各文書の冒頭に、どの要素・関係を扱うかを一行で書きます（例: `TASK_STATE_MODEL.md`はR2とR3）。

## 4. 選ばなかったもの

1. **Issueを要素ごとに並べ替えるだけ**: 並べ替えは分類であって、決める順序を定めません。順序（主体→資源→証拠）を決めて初めて、下流の未決が上流で解けます。
2. **すべてを一つの大きな設計文書に統合する**: 正本の分離（要求・設計・判断）を壊し、更新のたびに全体を書き換えることになります。読み方と順序だけを上位に置きます。
3. **要素を「データ種別」として扱う**: 同じ対象が関係によって別の要素になる（§2.1）ため、データ種別の分類では関係の欠落を見つけられません。

## 5. 未決

- 三関係の境界を、テスト（conformance）でどう固定するか。境界ごとに一つ、越えたら落ちる試験を置く方針は決めたが、R1の境界試験は既存の`conformance/protocol`と重複する可能性がある。
- #316（依頼できる範囲を拒否前に知る）をR1の一部とするか、R3（説明）とするか。契約の形（拒否前の照会か、受理時の応答か）で変わる。
- 要素の英語名（Actor / Resource / Evidence）を、既存文書の用語（Principal、Capacity、Assurance）とどう揃えるか。
- `architecture/`の各文書へ「要素・関係」の一行を足す作業の単位（一括か、文書ごとか）。
