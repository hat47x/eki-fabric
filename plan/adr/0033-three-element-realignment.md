# ADR-0033 三要素分析法（データ・機能・業務）で上流を再編成し、ブロックを「欠けている視点」として解く

- 状態: **提案中**
- 日付: 2026-11-01
- 関連: Issue [#381](https://github.com/hat47x/eki-fabric/issues/381)、[#365](https://github.com/hat47x/eki-fabric/issues/365)、[#354](https://github.com/hat47x/eki-fabric/issues/354)、[#321](https://github.com/hat47x/eki-fabric/issues/321)、[#320](https://github.com/hat47x/eki-fabric/issues/320)、[#316](https://github.com/hat47x/eki-fabric/issues/316)、[#315](https://github.com/hat47x/eki-fabric/issues/315)、[#243](https://github.com/hat47x/eki-fabric/issues/243)、[#198](https://github.com/hat47x/eki-fabric/issues/198)、[ADR-0013](0013-product-core-and-faces.md)、[ADR-0014](0014-authorities-for-delegation-budget-capacity.md)、[ADR-0031](0031-local-execution-slots-and-resource-reservation.md)、[ADR-0032](0032-task-phase-transition-subjects.md)

> **このADRは、同じ番号で先に出した案（主体・資源・証拠の三要素）を撤回し、置き換える。** 三要素分析法は渡辺幸三氏の手法であり、三つの要素はデータ・機能・業務である。先の案は名称だけを借りた独自の枠組みで、出典の方法と一致していなかった。

## 1. 背景: なぜ再編成するか

EKI Fabricの上流は、要求・脅威・ADR・設計がそれぞれ妥当な単位で積み上がっています。しかし**積み上げの軸が統一されていません**。そのため次の症状が出ています。

1. **同じ問いが複数の場所で別々に立つ。** 「完了とは何か」は状態モデル（データ）、結果の受理（機能）、公開状態（業務への説明）に分かれて現れ、どれが上位の判断か読み取れません。
2. **決める順序が無いため、下流のIssueが上流の未決で止まる。** #381・#365・#354 は、いずれも「一つの視点でしか語られていない」ことが原因です。
3. **「ブロックされた」の意味が曖昧。** 実装が止まっているのか、上流の判断が無いのか、単に作業量が多いのかを区別できません。

## 2. 方法: 三要素分析法（データ・機能・業務）

このADRは、渡辺幸三氏の三要素分析法を、EKIの委任の核に適用します。方法の内容は、隣接リポジトリ `tei-platform` の `reference/business-system-design/` と `requirements/BUSINESS_SYSTEM_DESIGN_REQUIREMENTS.md`（RQ-025、RQ-026）で、**Data / Function-Interaction / Business の cross-view** として運用されている形に合わせます。一次資料の本文は転載せず、用語と運用だけを参照します。

### 2.1 三要素

| 要素 | 何を表すか | EKIでの例 | 正本 |
| --- | --- | --- | --- |
| **データ** | 実体と、実体の間の関連 | Task、Attempt、Lease、WorkOrder、ResultClaim、AcceptedResult、Artifact、Trust Bundle、Policy | `architecture/TASK_STATE_MODEL.md`、`spec/external`、ADR-0012 |
| **機能** | 処理と、処理の連鎖（何が何を呼ぶか） | 受理、配置、実行、結果の受理、回復、失効の伝播 | `internal/core`、`internal/control`、ADR-0015、ADR-0032 |
| **業務** | 業務手順、アクター、判断（誰が、どの目的で、何を決めるか） | 依頼元の依頼と承認、端末利用者のopt-out、運用者の停止・回復の判断、管理者のpolicy | `requirements/`、ADR-0013、ADR-0017 |

**要素は「モノの分類」ではありません。** 同じ対象が、どの視点から見るかで別の要素になります。たとえばAcceptedResultは、データとしては実体、機能としては結果受理の出力、業務としては依頼元への説明の根拠です。三視点を分離することと、同じ意味を三箇所へ複製することを混同しません（`tei-platform/reference/business-system-design/README.md`の「三視点を分離することと、同じ意味を三箇所へコピーすることを混同しません」に対応）。

### 2.2 三つの対応関係（cross-view）

| 関係 | 問い | EKIでの道具 |
| --- | --- | --- |
| 業務 → 機能 | この業務手順は、どの機能で支えられるか | 業務手順と機能の対応表、`Acceptance Scenario` |
| 機能 → データ | この機能は、どのデータを読み書きするか | CRUDの対応（Lease・WorkOrderの発行が何を書くか） |
| データ → 業務 | このデータは、誰のどの判断の根拠か | 権限の境界（ADR-0014）、公開状態（#249、#315） |

### 2.3 決める順序

**業務 → 機能 → データ** の順に決め、最後に三視点を突き合わせます。

- 業務（誰が何を決めるか）が決まらないと、機能の正しさ（何をしてよいか）が決まりません。
- 機能が決まらないと、データの意味（何を残すべきか）が決まりません。
- 逆順に決めると、下流の判断が上流を書き換え、ADRの整合が壊れます（症状2の原因）。

## 3. 決定

### 3.1 Issueと文書に「どの視点か」を書く

Issueの本文の先頭に、**データ・機能・業務のどれか（複数可）**を一行で書きます。書けないIssueは、上流のどこかが欠けている証拠です。

### 3.2 ブロックを「欠けている視点」として名指しする

ブロックされた課題は、次の3種類に分けます。

1. **欠けている視点がある**（一つの視点でしか語られていない）: 三視点の対応を書いて、欠けを埋める。埋まると決めるべきことが確定する。
2. **視点は揃っているが配線が無い**: 実装Issueとして、変更点・試験・影響を書く。
3. **作業量が多いだけ**: 分割して順に進める。

分類をIssueに残さないものは、レビューの対象にしません。

### 3.3 現在のブロックへの適用

| Issue | 揃っている視点 | 欠けている視点 | 欠けを埋めると決まること |
| --- | --- | --- | --- |
| [#381](https://github.com/hat47x/eki-fabric/issues/381) `active`→`verifying` | 機能（結果受理の処理） | データ（検証中の状態が無い） | 検証中を表すデータ（`verifying`）を保存する。機能はそれを読んで完了を確定する |
| [#365](https://github.com/hat47x/eki-fabric/issues/365) 完了の境界 | データ（completed ⇒ AcceptedResult） | 機能（汎用CASが完了を書ける） | 完了を書ける機能を受理の入口に限る。データの不変条件が機能の制限として現れる |
| [#354](https://github.com/hat47x/eki-fabric/issues/354) 同時実行 | 機能（開始の関門） | データ（予約が実体として無い）・業務（端末利用者の同意との対応） | 予約をデータとして持つ。業務の同意（Local Governor）が予約の上限になる |
| [#321](https://github.com/hat47x/eki-fabric/issues/321) Trust Bundle | データ（Trust Bundle）・機能（enrollment・更新） | 業務（誰が更新を承認するか） | 更新の承認者と手順を先に決める。データの配布はその帰結になる |
| [#320](https://github.com/hat47x/eki-fabric/issues/320) 成果物の本体 | データ（ダイジェスト）・機能（ingest/get） | 業務（依頼元が本体を読む権利） | 閲覧の権利を決める。保管と取得はその帰結になる |

この表のとおり、ブロックの正体は「実装の難しさ」ではなく**視点の欠落**です。欠けを埋めると、決めるべきことが一つに絞られます。

### 3.4 文書の配置

- 三要素・三対応・順序の定義は、このADRを正本とします。
- 要求は`requirements/`、設計は`architecture/`、判断は`plan/adr/`が正本であることは変えません。このADRは**それらの読み方と順序**を定めます。
- `architecture/`の各文書の冒頭に、どの視点を扱うかを一行で書きます（例: `TASK_STATE_MODEL.md`はデータ、ADR-0032は機能）。

## 4. 選ばなかったもの

1. **独自の三要素を発明すること**（先に出した「主体・資源・証拠」の案）: 出典の方法と名称が一致せず、既存の運用（`tei-platform`のcross-view）とも接続できません。撤回します。
2. **データ種別として分類すること**: 同じ対象が視点によって別の要素になるため、種別分類では視点の欠落を見つけられません。
3. **一つの大きな設計文書へ統合すること**: 正本の分離を壊します。読み方と順序だけを上位に置きます。

## 5. 未決

- 三要素分析法の**一次資料**（著書・公開資料）での用語と手順の確認。`tei-platform`では一次資料の特定を別Issueで扱っており、EKI側でも同じ確認が要る。本文の転載はしない。
- 「業務アクター」と「認証された主体」を混同しないこと（`tei-platform` RQ-025が明示）。EKIの`Principal`との対応をどこで定義するか。
- CRUDの対応表を、どの単位で作るか（機能ごとか、業務手順ごとか）。
- 視点の対応を、conformanceの試験でどう固定するか（境界ごとに一つ、越えたら落ちる試験を置く方針）。
