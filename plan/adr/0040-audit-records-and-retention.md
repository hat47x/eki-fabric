# ADR-0040 監査の記録と保持

- 状態: 提案中（**仮承認**。利用者の包括承認 2026-11-03 による）
- 日付: 2026-11-03
- 関連: ADR-0038（Operator の認証）、ADR-0039（測定）、#584

## 1. 問題

EKI は3種類の「あとから調べたいこと」を作っています。

- **成果物の取得**（`ArtifactAccess`）: 誰が、いつ、どの成果物を取ったか。拒否も含む。
- **Operator の操作**（`Access`）: 誰が、いつ、何を承認・却下したか。
- **測定の数**（ADR-0039）: 断った回数と回収した回数。

EKI は**どれも保存しない**と決めています（ADR-0039 §2.3、各監査はコールバックで、既定はログ）。保存先と保持期間は配備が決めることになっていますが、**決め方の指針が無い**ままだと、配備ごとに桁違いの保持期間が生まれます。

## 2. 決定

**3種類を、別々の保持期間で扱います。** 同じ「監査」でも、問いが違うためです。

| 記録 | 期間の目安 | なぜその長さか |
| --- | --- | --- |
| 成果物の取得 | **90日** | 「この結果を誰が見たか」は、成果物の保持（24時間）より**ずっと長く問われる**。漏えいの疑いを調べるには、本体が消えたあとも記録が要る |
| Operator の操作 | **1年** | 信頼の根を変えた操作は、**変更の理由を説明する責任**が長く残る。年次の監査に合わせる |
| 測定の数 | **30日** | 傾向を見るための数で、個別の説明には使わない。長く持つほど**個人の行動の推測**に近づく |

決めた理由:

- **測定期間を短くしたのは、プライバシーのためだけではありません。** 数を長く持つと、**「断られた回数」が特定の主体の行動の記録**に近づきます。EKI は人を数えないと決めた（ADR-0039 §2.2）ので、**持ち続けない**ほうが決定と整合します。
- **取得の記録を90日にしたのは、成果物の保持（24時間）と揃えないため。** 揃えると、本体が消えた時点で「誰が見たか」も消え、**漏えいの調査ができません**。

**保存先は配備が決めます**が、満たすべき条件を決めます。

1. **追記のみ**（書き換え・削除ができない）。監査を書き換えられるなら、記録は記録ではありません。
2. **EKI のプロセスから削除できない**（保持期間の経過は保存先が判断する）。
3. **時刻は UTC** で、**EKI の時計**を使う（保存先の時計と混ぜない）。

## 3. 何を保証しないか

- **記録が無いことは、出来事が無かったことを意味しません。** プロセスが落ちた瞬間の取得は記録の前に消えることがあります（ADR-0039 §3 と同じ限界）。
- **保存先の完全性は保証しません。** 追記のみという条件を**満たしているかは配備の責任**で、EKI は確かめません。
- **記録の内容は、本文を含みません。** ダイジェストと Principal だけで、**何が書かれていたか**は残りません。

## 4. 未決

- 保持期間を**配備ごとに変えられる**ようにするか（いまは目安としての既定値）。
- 保存先が落ちているとき、EKI は**取得を止めるか**（fail closed）**続けるか**。止めると可用性が下がり、続けると記録が欠ける。
- 監査の**閲覧権限**（Administrator だけか、Operator も含むか）。

**仮承認:** 本節までの決定は、利用者の包括承認（2026-11-03「人的判断はすべて仮承認でパス」）による仮承認です。あとから覆す場合は、この ADR と #584 を参照してください。

## 5. 監査の保存先が落ちているとき、何を止めるか（2026-11-03、#610）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

**決定: 記録の種類で分ける。Operator と Administrator の操作は止める。成果物の取得は続ける。**

| 記録 | 保存先が落ちているとき | 理由 |
| --- | --- | --- |
| **Operator／Administrator の操作** | **止める**（操作を拒否する） | 信頼の根を変える操作は**めったに起きず、人が介在する**。記録できないなら**その場で止めるほうが安い**。あとから「誰が版を受理したか分からない」状態は、監査の前提を壊す |
| **成果物の取得** | **続ける**（失敗を記録に残す） | 取得は**読み取り**で、**所有者だけ**という安全は記録に依存せず効いている。記録が欠けるのは**観測性の低下**であって、権限の破れではない。ここで止めると**監査基盤の障害が利用者の障害になる** |

**fail closed を適用する範囲を、これで明確にしました。** fail closed は**安全側の判断**に使う原則で、**観測性の低下にまで広げると、守る対象を守らないまま可用性だけを落とします**。

**記録が欠けたことをどう扱うか**:

- **数える**: 保存先の失敗を**測定の数**（ADR-0039）に1種増やし、`audit_unrecorded` として数えます。**黙って続けない**ためです。
- **応答は変えない**: 取得の応答に「記録できなかった」を含めません。**依頼元にできることが無い**情報で、応答を複雑にするだけです。
- **ログには残す**: 失敗はプロセスのログに残します（測定は数、ログは詳細）。

**何を保証しないか**: 保存先が落ちているあいだの取得は、**あとから「誰が見たか」を説明できません**。その期間があることを、運用者は `audit_unrecorded` の数で知ります。

**未決**: `audit_unrecorded` を**誰が見るか**（Operator の画面か、監視か）。測定の数を配備が拾う形（ADR-0039 §2.3）なので、**拾わない配備では気づけません**。

## 6. `audit_unrecorded` を誰がどう見るか（2026-11-03、#632）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

**決定: 監視のアラートにする。値が増えたら鳴らす。日次レビューにはしない。**

理由:

- **EKI は数を5分ごとに出す**（#392）。新しい仕組みは要らず、**ログの1行を監視の条件に書けば足ります**。
- **欠けた記録は取り戻せません。** 記録できないまま取得は続くので（§5）、**翌日に気づいても、その日の「誰が見たか」は永久にありません**。遅れて知ることに価値がありません。
- **しきい値は「増えたら」で十分です。** 正常な配備では**0 のまま**なので、**1でも増えたのは異常**です。件数の大小で判断する余地がありません。

運用の形:

- **1回の増加**は、保存先の一時的な失敗かもしれません。**次の5分の書き出しでも増えていれば**、持続的な障害として扱います。
- **増え続ける**なら、保存先の障害か、**設定が既定のログのまま**（`docs/operations/audit-sink.md`）です。
- **アラートの宛先は Operator ではなく、配備の監視**にします。Operator は「信頼の根を変える人」で、**保存先の運用は別の役割**です。

**何を保証しないか**: 監視が**無い配備**では、この数は**ログに流れて消えます**。EKI は数を出すだけで、**見る仕組みは配備の責任**です。

**未決**: アラートの文面と、**誰が一次対応するか**（保存先の持ち主か、運用か）。

## 7. 監査の保存先を、配備がどう挿すか（2026-11-03、#639）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

**決定: 設定に `audit_sink_url` を1つ置き、記録を JSON で POST する。失敗は「書けなかった」として扱う。**

形:

- **1件1リクエスト**（`POST <audit_sink_url>`、`Content-Type: application/json`）。本文は `ArtifactAccess` または `Access` の JSON。
- **2xx 以外は失敗**。タイムアウトは**5秒**。
- **並びは保証しません。** 保存先が順序を要するなら、**記録に時刻が入っている**ので保存先で並べられます。
- **再送はしません。** 失敗は**その場で数える**（取得は `audit_unrecorded`、Operator 操作は 503）。**あとから再送すると、失敗した記録と成功した記録の区別が失われます**。

理由:

- **EKI は保存しない**（§2.3）ので、**HTTP の1本の口**で足ります。DB の方言やベンダの SDK を持ち込むと、**EKI が保存の実装を持つ**ことになります。
- **失敗を返せることが要件**です（§5）。`POST` は**必ず成否を返す**ので、この要件に合います。
- **再送しない**のは、**「書けなかった」を記録すること自体が目的**だからです。黙って再送して成功すると、**遅れて書かれた記録**が**その時刻の記録**のように見えます。

**何を保証しないか**:

- **保存先が追記のみであることは確かめません**（§2 の条件は配備の責任）。
- **記録の到達**は保証しません。失敗は数に出るだけです。
- **HTTPS を強制しません**。ループバックの収集器に送る配備を許すためです。**平文で送るなら、その区間は読まれ得ます**。

**未決**: 記録の**本文に何を入れるか**（いまの構造体をそのまま JSON にするか、`schema` を付けるか）。

**記録の本文（2026-11-03、#641 の続き）**: POST する本文は**外側に `schema`、内側に `record`** を持つ封筒にします。

```json
{"schema": "eki.audit.artifact-access/v1", "record": {"At": "...", "Principal": "...", "Artifact": "...", "Outcome": "served"}}
```

- **`schema` を付ける理由**は、保存先が**2種類の記録**（取得と Operator 操作）を**推測せずに読む**ためです。形が似ているので、**名前が無いと取り違え**が起きます。
- **`v1` は交渉の版ではありません。** **知らない版は拒否**する前提の名前です（読めない記録を**別の意味で読まない**）。

**未決**: `record` の中の**キー名の流儀**（いまは Go の構造体の JSON タグそのまま。`At` が大文字なのは**構造体のフィールド名**が出ているためで、契約として望ましくない可能性があります）。
