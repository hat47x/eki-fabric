# ADR-0006 M0のClient API認証とTask Admissionの境界

- Status: **Accepted for M0 / DP-0, DP-1**
- Date: 2026-10-06

## 1. 背景

P0 External契約（`spec/external/openapi.json`）は、すべての操作で認証を必須（`x-eki-authentication-required: true`）にしていますが、認証方式そのものは固定していません。OIDCやmTLSなどの具体的な方式は、別のセキュリティの作業単位で決める前提です。

一方、M0縦断スライスでは、悪意あるClientからTaskを受理するところから確認する必要があります。認証なしで動かす暫定版は作りません。「あとで認証を足す」前提で作ると、匿名で動く経路がテストと設計の既定になり、後から塞ぎにくくなるためです。

このADRは、M0で何を実装し、何を実装しないかだけを決めます。

## 2. 決定

### 2.1 認証

M0では**固定のBearerトークン**を使います。

- トークンは設定ファイルに平文で置かず、SHA-256の16進表現だけを置く。設定ファイルが漏れても、使えるトークンは漏れない。
- トークンは`Authorization: Bearer`ヘッダだけから読む。クエリ文字列やボディからは読まない（URLはログやプロキシに残る）。
- 照合は、全エントリを最後まで比較する定数時間の比較で行う。どのエントリが一致したか、いくつあるかを時間から推測させない。
- 受理するトークンは20文字以上、512文字以下。生成は`eki-control gen-token`が行い、256bitの乱数をbase64urlにする。
- トークンにはPrincipalとRoleを紐づける。Roleは`client`と`admin`で、Client APIは`client`だけを受け付ける。`admin`のトークンでTaskを提出することはできない（RQ-015、RQ-016）。管理用のAPIはM0にはなく、Roleの分離だけを先に固定する。
- `Handler`は認証器なしでは作れない。匿名で配信する経路をコードに残さない。

M0の固定トークンには、失効、期限、ローテーション、利用者ごとの監査がありません。これらは本番向けの方式で扱います。M0の固定トークンを、本番認証の代わりにしません。

### 2.2 通信路

- TLSを設定できる（TLS 1.2以上）。
- TLSなしの平文HTTPは、ループバックアドレスでだけ起動する。それ以外のアドレスでは、`allow_insecure_listen`を明示しない限り起動を拒否する。信頼できるプロキシが手前でTLSを終端する構成のための、意図的で目に見えるopt-outである。
- サーバには、ヘッダ、読み取り、書き込み、アイドルの各タイムアウトと、ヘッダの大きさの上限を設定する。

### 2.3 Task Admission

`internal/core/admission`がADM-2を担当し、HTTPを知りません。次の順序で、最初に失敗した段階で拒否します。

1. Idempotency-Keyの形式
2. JSONの構造検査（UTF-8、重複キー、深さ、配列長、オブジェクト幅、文字列長、末尾データ）
3. P0スキーマの検証（未知のフィールドを拒否し、必須フィールドと範囲を確認）
4. ポリシー（承認済みExecutor、Taskごとの資源上限、リトライ上限、期限、GPU・Artifact・拡張の拒否）
5. 原子的な受理（冪等性、principalごとの未完了Task数上限、Task作成）

M0で意図して拒否するものは次のとおりです。いずれも「後で使えるようにする」のではなく、対応する権限と部品がまだないために、安全側で拒否します。

- Artifactを入力にするTask（Artifact Storeがなく、入力を認可できない）
- GPU資源
- 拡張（`extensions`）
- Executorのバージョン制約の解決（Executor Admission、EXE-1が未実装。要求された制約はTask IRに記録するだけ）

### 2.4 冪等性

- Keyは**principalごと**。別のprincipalが同じKey文字列を使っても衝突しない。
- 同じKeyで、正規化した後のリクエストも同じなら、同じTaskを返す（HTTPは同じ`202`）。同じKeyで別のリクエストなら`409`。
- 比較に使うフィンガープリントは、キー順、空白、省略された既定値に依存しない。一方、数値は送られたリテラルのまま扱う（`1`と`1.0`は別のリクエスト）。誤るとしても「別のリクエストを同じものとみなす」のではなく、「同じリクエストを別のものとして競合にする」側を選んだ、ということである。
- 受理と冪等性の記録と未完了Task数の確認は、一つのトランザクションで行う。同時に来た同じKeyの提出が二つのTaskを作ることも、同時の提出が上限を超えることもない。
- 再提出（replay）は、上限に達していても拒否しない。
- Cancelの`Idempotency-Key`は契約上は必須だが、保存はしない。Cancelは繰り返しても結果が変わらないからである。

### 2.5 可視性

- Taskを観測・Cancelできるのは、提出したprincipalだけ。
- 存在しないTask、他のprincipalのTask、形式が不正なTask IDは、**同じ`404`**を返す。Task IDの探索を許さない（RQ-018）。
- 公開状態は内部状態の縮約で、Worker、Attempt、Lease、ポリシーリビジョン、principal、ダイジェストを含まない。

### 2.6 Cancel

- まだAttemptを持たないTask（admitted、ready）は、副作用を持ち得ないため、Cancel要求と同時に`cancelled`で終了する。
- 実行中のTaskは、Cancellation Intentを記録するだけにする。実際の停止は、実行を所有する部品（今後のスケジューラ、Lease Authority）が行う。
- 終了済みTaskのCancelは`409`。すでにCancel済みのTaskへの再Cancelは成功する。

## 3. 影響

### 良い点

- 匿名の経路がない。
- 設定ファイルの漏えいがトークンの漏えいにならない。
- 再起動をまたいでも、Task、冪等性、未完了Task数の上限が保たれる。
- OpenAPIの応答スキーマとの一致を、テストで機械的に確認できる。

### 制約

- 固定トークンは失効できない（設定を変えて再起動する）。
- 一つのプロセスの未完了Task数上限だけで、リクエスト頻度の制限は持たない。
- P0 OpenAPIが宣言していない`401`、`405`、`501`を、認証と未実装のために返す。P0へ反映する場合は別途契約を更新する。
- Admission後にポリシーが厳しくなった場合、同じKeyの再提出がポリシーの検査で`422`になる。元のTaskが返るのは、ポリシーを通る間だけである。この順序は、新規の不正な作業を先に拒否することを優先した結果である。

## 4. 実装記録（2026-10-06）

- `internal/core/admission`、`internal/control/clientapi`、`internal/control/service`、`cmd/eki-control`に実装した。
- State Store SPIに`AdmissionStore`を追加し、メモリとSQLiteの両方が共通の契約を通る（SQLiteはマイグレーション2、全トランザクションを`BEGIN IMMEDIATE`にした）。
- 検証はGo 1.27.0（WSL2、Linux）。実プロセスでの簡易確認（提出、未認証、SIGTERMでの正常終了、状態ファイルのモード0600、トークンがログに出ないこと）も確認した。
