# ADR-0039 受益者の分布と、停止・取消・上限が効いたことを何で測るか

- 状態: 提案中（**仮承認**。利用者の包括承認 2026-11-03 による）
- 日付: 2026-11-03
- 関連: ADR-0035（測定の境界）、TAI RQ-YI-014 / RQ-YI-015、#392、#393

## 1. 問題

「この仕組みは誰の役に立っているのか」「止める仕組みは本当に効いているのか」を、あとから**数字で**確かめたいという要求があります（TAI の RQ-YI-014 と RQ-YI-015）。

素直に考えると、次の2つを集めたくなります。

1. **受益者の分布**: どんな属性の人が、どれだけ計算資源を受け取ったか。
2. **停止・取消・上限の効果**: 何回止められ、何回断られ、何回上限に当たったか。

前者は**人に関する属性**を集めることになり、後者は EKI がすでに記録している**出来事の回数**です。同じ「測る」でも、危険度がまったく違います。

## 2. 決定

**EKI は、自分がすでに記録している出来事の回数だけを数えます。人は数えません。**

### 2.1 数えるもの（RQ-YI-015）

次の4つを、**出来事が起きた場所で**数えます。

| 数えるもの | どこで | 意味 |
| --- | --- | --- |
| `admission.rejected` | 受付 | 依頼が受け付けられなかった回数（理由: 権限・重複・上限） |
| `lease.reclaimed` | Control Plane | 貸与が取り戻された回数（期限切れ・失効） |
| `claim.refused` | Control Plane | 結果の報告が受け入れられなかった回数 |
| `limit.refused` | Worker | 出力の上限で送信を断った回数 |

**数えるのは回数と理由の別だけ**で、誰がどういう事情だったかは数えません。

### 2.2 数えないもの（RQ-YI-014）

**受益者の属性（年齢、地域、所属、収入、健康状態など）は集めません。**

理由は3つあります。

1. **EKI は受益者を認証しない。** 受益者という主体は要求には出てきますが、Control Plane が会うのは Client と Worker だけです。「受益者」の属性を集めるには、**別の身元**を新しく作って結びつけることになります。
2. **集めた瞬間に、守るべき対象が増える。** 属性は漏れると取り返しがつかず、EKI の他の部分（本文を読まない、ダイジェストだけを扱う）と矛盾します。
3. **分布は EKI の外で測れる。** 誰がどれだけ得たかは、配備している組織が自分たちの記録から測れます。EKI が中央で集めなくても、同じ問いに答えられます。

**代わりに数えるもの**: 「いくつの Task が完了し、いくつの成果物が取得されたか」という**件数**。これは人の属性ではなく、EKI 自身の仕事の量です。

### 2.3 集計の置き場所

- 数は**既存の監査の記録**（成果物の取得 `ArtifactAccess`、Operator の操作 `Access`）と同じ形で出します。**保存先は配備が決める**（ログ、SIEM、DB）。
- EKI は**集計値を保存しない**。読む側が数える。
- **割合を出すための分母も、EKI は持たない**（総人口などは EKI の外の情報）。

## 3. 何を保証しないか

- **数え漏れは起こります。** プロセスが落ちた瞬間の出来事は、記録の前に消えることがあります。厳密な会計ではありません。
- **「抑止できた」ことは測れません。** 上限があることで最初から依頼されなかった、という出来事は記録に残りません。測れるのは「断った回数」だけです。
- **属性を集めないので、分布の偏りは EKI だけでは分かりません。** 配備している組織の記録と突き合わせる必要があります。
- **数は攻撃で膨らませられます。** 依頼を大量に送れば `admission.rejected` は増えます。増加は「抑止が効いていない」ではなく「依頼が多い」ことを意味するだけです。

## 4. 未決

- 数の**保持期間**（監査と同じか、別か）。
- 複数の Control Plane があるときの**合算**（同じ Task を二重に数えない工夫）。
- 断った理由の**語彙**をどこで固定するか（いまは自由文字列）。

**仮承認:** 本節までの決定は、利用者の包括承認（2026-11-03「人的判断はすべて仮承認でパス」）による仮承認です。あとから覆す場合は、この ADR と #392 / #393 を参照してください。

## 5. 実装状況（2026-11-03）

決定を実装へ移したときに分かったことを残します。**決定そのものは変わりません。**

| 数えるもの | 状態 | 発生点 |
| --- | --- | --- |
| `admission.rejected` | 実装済み | `clientapi.Handler.fail` の 4xx |
| `limit.refused` | 一部 | `governor.OutputBudget` の拒否フック（**呼び出し元がまだ無い**） |
| `claim.refused` | 実装済み | `claimplane.Submit` が自分で断った分 |
| `lease.reclaimed` | 未 | **期限切れの貸与を回収する走査が無い**（`ActiveAt` の呼び出しは0件） |

分かったこと:

- **数える仕組みより先に、「数える出来事」が起きていない**箇所が2つありました。`limit.refused` は `OutputBudget` を組み立てる呼び出しが無く、`lease.reclaimed` は回収する走査がありません。数を出す前に、出来事を起こす経路が必要です。
- そのため #548 は「3つは配線済み、1つは前提待ち」で終わり、残りを #555 に分けました。**数を合わせるために空の計器を置かない**方針は維持しています（0 は「起きなかった」ではなく「数えていない」かもしれないため）。
