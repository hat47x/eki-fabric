# ADR-0009 管理された資源は既存オーケストレータを置き換えず、資源プロバイダとして接続する

- 状態: **提案中**
- 日付: 2026-10-06
- 改定: 決定4は[ADR-0013](0013-product-core-and-faces.md)で、止められても正しさが失われない常駐の認知処理を対象に含めるよう改めた
- 関連: Issue #67, RQ-001, RQ-003, RQ-004, RQ-019, RQ-030, [orchestrator-integration-and-layering](../../research/integration/orchestrator-integration-and-layering.md)

## 1. 背景

[value.md](../../product/value.md)の「Managed and opportunistic resources on one fabric」は、2種類の資源を同じタスク（Task）契約、同じ配置判断、同じ検証、同じ監査で扱うことを掲げています。一つは専用サーバや、KubernetesやSlurmなどが管理するクラスタです。もう一つは業務端末やブラウザのように一時的に使える資源です。

単純に作る方法は二つ考えられますが、どちらもこの価値と矛盾します。

- **EKIがクラスタを直接管理する方法**では、Nodeの管理、常駐サービス、ネットワーク構成までEKIが持つことになる。これは既存オーケストレータを置き換えることになり、企業が使い慣れた運用経路（原則 §12）とぶつかる。
- **管理された資源を信頼済みとして特別扱いする方法**では、たとえば「Kubernetes上のワーカー（Worker）は検証しない」と決めることになる。そうすると、改変されたPodや設定ミスが検証を通り抜けてしまう（原則 §1、§9）。

## 2. 決定

1. 既存オーケストレータは、**資源プロバイダ（Resource Provider）**としてEKIへ接続する。EKIはプロバイダ（Provider）へ、制約、期間、量を指定して実行枠を依頼する。プロバイダはその枠をワーカーとして提供する。Podの配置やNodeの管理は、引き続きオーケストレータが受け持つ。
2. 管理された資源から来たワーカーも、ほかのワーカーと同じく、リース（Lease）、作業指示書（WorkOrder）、結果（Result）の検証を経る。「管理されている」ことは、保証水準（Assurance Level）や配置の優先度を上げる根拠の一つにすぎない。この根拠は管理者が設定するポリシーでだけ表現し、ワーカー自身の申告では表現できない（RQ-047）。
3. プロバイダの接続では、特定製品のAPIをCoreへ入れない。拡張SPI（[EXTENSION_SPI.md](../../architecture/EXTENSION_SPI.md)）のアダプタとして実装する。MVP後の最初の検証では、Kubernetes系とバッチスケジューラ系のように性質の異なる2系統を接続できることを確かめる。1系統だけでは、その製品の拡張機能と区別がつかないので、完了としない。
4. 業務アプリケーション本体のように終わりのない常駐サービスはEKIの対象外とし、プロバイダへの依頼にも含めない。

## 3. 影響

### 良い点

- 遊休資源を活用しにくい組織でも、管理クラスタを統治するだけで導入価値が成り立つ。
- 管理された資源と遊休資源とで、結果の検証や監査の基準が分かれない。

### 悪い点と制約

- Podの起動やキューの待ちといったオーケストレータ側の待ち時間が配置判断に入ってくるので、Suitabilityゲート（ADR-0029）の規則が複雑になる。
- プロバイダアダプタが持つ資格情報は、EKIの中でも特に強い権限の一つになり得る。そのため、制御プレーン（Control Plane）の権限分離（RQ-051）の対象に含める必要がある。
