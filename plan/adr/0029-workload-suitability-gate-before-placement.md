# ADR-0029 「EKIへ載せない」判断をスケジューラより前のSuitabilityゲートで行う

- 状態: **提案中**
- 日付: 2026-10-06
- 関連: RQ-011, RQ-014, RQ-046, RQ-024, Issue #58
- 番号: 当初ADR-0007として採番したが、同じ番号が外部副作用の再実行規則（暫定）にも付いていたため、2026-10-28に0029へ振り直した（Issue #246）

## 1. 背景

EKIの価値は、多くのワーカー（Worker）へタスク（Task）を送れることではありません。遊休資源を使う意味があるワークロードだけを、安全にファブリック（Fabric）へ入れることにあります（[value.md](../../product/value.md)の「Compute where it is economically sensible」、[principles.md](../../product/principles.md) §5、§6）。

単純に作るなら、受理したタスクをすべてスケジューラへ渡し、スケジューラに最適なワーカーを選ばせる設計になります。この設計には次の問題があります。

- スケジューラは必ずどこかのワーカーを選ぶので、「どこにも置かない方が良い」という答えを返しにくい構造になる。
- たとえば、2GBの入力を読んで10秒だけ計算するタスクでは、どのワーカーを選んでも転送時間が計算時間を上回る。スケジューラが最速のワーカーを選んでも、ローカルで実行するより遅くなる。
- 外部APIへ書き込むタスクでは、ワーカーが離脱してリトライされると二重に書き込まれる（RQ-046）。これは性能の問題ではない。そもそもファブリックへ載せてはいけない性質である。
- #19のlearned schedulingのようにスケジューラの性能を上げても、載せるべきでないタスクが混ざったままでは、導入価値を説明する根拠にならない。

## 2. 決定

1. 受理審査（Admission、ADR-0006、ADM-2）の後、スケジューラの前に**ワークロードSuitabilityゲート**を置く。スケジューラが決めるのは「どこへ置くか」だけであり、「EKIへ載せるか」はゲートが決める。
2. ゲートは次の3つのいずれかを返す。スケジューラへ進めるのは`FABRIC_JUSTIFIED`だけである。
   - `FABRIC_JUSTIFIED`: ファブリックで実行する根拠がある。タスクをスケジューラへ渡す。
   - `FABRIC_NOT_JUSTIFIED`: ファブリックで実行する根拠がない。理由コードを添えて返す。EKI Coreはローカル実行を始めない。どこで実行するか（ローカルのプロセス、既存のサーバー、クラウドなど）は、クライアント（Client）または上位のオーケストレータが決める。
   - `NEEDS_MEASUREMENT`: 入力量や実行時間の目安など、判定に必要な事実が足りない。足りない事実を推測で埋めて`FABRIC_JUSTIFIED`にはしない。見込まれる利点が、設定した最小の差以下のときもこれを返す。

   現在のProfileでは安全に扱えないタスクは、ゲートの値では表さない。リトライの扱いが決まっていない外部への書き込みや、データ分類（Data Class）上ワーカーへ渡せない入力がこれにあたる。これらは受理審査と、セキュリティ・データ・資源の実行可能性（feasibility）の判定で候補から外し、ゲートへは渡さない。
3. 最初の実装（EKI-SUIT-0）は、あらかじめ決めた規則だけで判定し、MLや学習済みモデルを使わない。判定に使った事実と規則のバージョンを記録し、あとから判定理由を説明できるようにする。
4. ゲートの入力には、クライアントが申告したワークロードの事実も含まれる。ただし、申告（Claim）として扱う（原則 §3）。クライアントが申告を偽っても、セキュリティプロパティは崩れない。受理審査、リース（Lease）、端末側ガバナ（Local Governor）が別にそれを守っているからである。ゲートが守るのは効率と導入判断の正しさであり、ゲートはセキュリティ境界ではない。
5. `FABRIC_NOT_JUSTIFIED`を返すのは失敗ではなく、製品が正しく動いた結果である。この判定も計測し、表示する。

## 3. 影響

### 良い点

- 「分散しない」という答えを、スケジューラのついでではなく、明示した判断として返せる。
- 導入を検討する人へ、どのワークロードがEKIに向くかを、規則と記録をもとに説明できる。
- スケジューラを評価する際（#19）、ファブリックに向くタスクだけを対象にできる。

### 悪い点と制約

- ゲートの規則が粗いと、本来EKIで有利になるタスクまで`NEEDS_MEASUREMENT`に回してしまう。初期はこの保守的な振る舞いを許容する。
- クライアントが申告を偽れば効率は下がり得る。資源上限（RQ-009、RQ-017）と資源提供実績（Contribution）の記録でこれを抑えるが、ゲート単体では防がない。

## 4. 未決事項

- 転送コストと計算で得られる利点を比べる閾値を、どの受け入れシナリオ（Acceptance Scenario）から決めるか。
- `NEEDS_MEASUREMENT`になったタスクを管理された資源で試しに実行し、足りない事実を集める経路を持つか。

## 5. 改訂の記録

## 5. データの所在は「助言」としてだけ使う（2026-11-05、#717）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

PAS-CAND-01（説明の並列探索）の受け入れ条件に、**「同じ入力を12回転送するより、入力を持つ Worker や近くの Worker に、まとめて配置する判断ができる」**があります。いまの配置は**資源の要求だけ**を見ており、**データの所在を入力に持っていません**。

**決定: データの所在は、配置の「助言」としてだけ使う。判断の根拠にはしない。使えるのは公開・低機密の入力に限る。**

理由:

- **「持っている」は自己申告で、確かめられません。** Worker が「この Artifact を持っている」と言っても、**EKI は確かめる手段を持ちません**（**持っているかを問い合わせるには、その中身か一覧を信じるしかない**）。**確かめられない申告を配置の条件にすると、申告する側が得をします**（**わざと「持っている」と言って、機密の入力を自分に寄せる**）。
- **助言なら、外れても壊れません。** 申告が嘘でも、**Artifact はダイジェストで取得して検証**されるので、**余計に転送しただけ**で済みます（ADR-0034）。**配置の正しさは資源の判断が担保**し、**所在は速さの話**にします。
- **機密の入力では使いません。** 「近いから」という理由で**機密を特定の Worker に寄せると、その Worker を狙う攻撃者に有利**です。**データの分類（`data_class`）が public・low のものだけ**を対象にします。

**決めた形（実装するとき）**:

1. Worker の登録に **`held_artifacts`（ダイジェストの一覧）**を足す。**任意**で、無い場合は「何も持っていない」と同じ扱い。
2. 配置は**資源の適合で候補を絞ったあと**、**同点の範囲で** `held_artifacts` に**入力のダイジェストが含まれる Worker を優先**する。**資源の判断を飛び越えない**（**資源が足りない Worker は、持っていても選ばない**）。
3. **`data_class` が internal 以上の入力では、この優先を使わない**（**申告に機密の行き先を決めさせない**）。
4. **「持っている」を理由に、取得の検証を省かない**（**ダイジェストの検証は常に**）。

**何を保証しないか**:

- **「近い」ことは保証しません。** EKI は**ネットワークの距離を知りません**（**知っているのは「持っていると申告した」だけ**）。
- **転送量は減るとは限りません。** 申告が正しければ減りますが、**EKI は測っていません**（**転送量を判定しない**、ADR-0037 §11.6 と同じ立場）。

**未決（残す）**: `held_artifacts` を**Worker の登録に持たせるか、Artifact の取り出しの履歴から推定するか**（**申告させるほうが単純だが、推定のほうが嘘に強い**）。実装するときに決めます。
### 5.1 `held_artifacts` は登録で申告させる（2026-11-05、§5 の未決）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5 の未決「登録で申告させるか、取得履歴から推定するか」を決めます。

**決定: 登録で申告させる。推定しない。**

理由:

- **推定には、Worker ごとの取得履歴を保存する必要があります。** それは**新しい保存**（保持期間・監査の対象・削除の手当て）を増やします。**「助言」のために増やす保存としては重すぎます**。
- **推定は「EKI が見た取得」しか知りません。** 端末の外で手に入れた Artifact、**別の経路で配られた入力**は推定に入りません。**推定のほうが正確だという前提が成り立ちません**。
- **嘘への強さは、使い方で担保します。** §5 のとおり、**申告は同点の並べ替えにだけ使い、機密では使わない**ので、**嘘の損得は「余計に転送した」だけ**です。

**決めた形**:

1. Worker の登録に `held_artifacts`（ダイジェストの一覧）を**任意**で持つ。無い場合は「何も持っていない」。
2. **上限**を設ける（`MaxHeldArtifacts`）。**長すぎる一覧は 1 台が全員の入力の助言を占める**ことになるため。
3. **空の項目や上限超過は、申告ごと捨てる**。**黙って短くしない**（**「一部だけ効く」は、嘘より分かりにくい**）。
4. **失効・取消と独立**に扱う（**鍵や権限ではなく、助言**なので、**古い一覧でも害は転送量だけ**）。
### 5.2 配線が止まる理由: 配置の判断から入力 Artifact のダイジェストが見えない（2026-11-06、#717）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.1 までで、**申告を書く経路**（`/test-profile/v1/held-artifacts`）と**読む経路**（`Worker.HeldArtifacts`）、**同点の並べ替え**（`LocalityHint.PreferOrders`）が揃いました。**残りは配置の判断への配線**ですが、**その手前で止まります**。

**止まる理由**: `pickWorker` は `taskstate.TaskRecord` を受け取りますが、**そこには入力 Artifact のダイジェストがありません**。Task は**入力**を `ArtifactReference{Name, ArtifactID}` で参照し（`internal/core/admission`）、**記録に残るのは `TaskIRDigest` だけ**です。**`ArtifactID` はダイジェストではない**ので、**申告（ダイジェストの一覧）と突き合わせられません**。

**選択肢と、いま選ばない理由**:

| 案 | 内容 | いま選ばない理由 |
| --- | --- | --- |
| **記録に入力のダイジェストを足す** | Task の記録（または Attempt の記録）に、入力 Artifact のダイジェストを保存する | **保存の形が変わる**（マイグレーション）。**何を「入力」と呼ぶか**（入力の入力、生成物）を決める必要がある |
| **配置時に Artifact の記録を引く** | `ArtifactID` → ダイジェストを、配置のたびに引く | **配置の経路に新しい読み取りが増える**。**引けない場合（削除済み・未登録）の扱い**を決める必要がある |
| **Task IR のダイジェストを使う** | `TaskIRDigest` を「入力の同一性」として扱う | **意味が違う**。**同じ IR でも入力が違えば別物**で、**「持っている」の対象にならない**（**誤った同点処理**になる） |

**決定: 配線は、入力のダイジェストを配置の判断から参照できるようにしてから行う。** **「IR のダイジェストで代用する」はしません**（**動いているように見えて、意味の違う比較**になる）。**どの案を採るかは、保存の形を変えるかどうかの判断**なので、**別の Issue で決めます**。

**この節の意味**: **「あと少しで配線できる」と思っていたものが、実は入力の参照から必要だった**という記録です。**助言の仕組みだけを作って配線しない**ままにせず、**何が足りないかを名指し**しておきます。
### 5.3 入力のダイジェストは、受理のときに記録へ写す（2026-11-06、#736）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.2 で残した「配置の判断から入力のダイジェストを参照できるようにする」を決めます。

**決定: 受理のときに、入力 Artifact のダイジェストを Task の記録へ写す。配置のときに Artifact を引き直さない。**

理由:

- **入力は受理の時点で決まり、その後変わりません。** Task IR が不変なのと同じ理由で、**入力のダイジェストも不変**です。**不変なものを毎回引き直すのは、変わらないことを確かめ直しているだけ**です。
- **配置は tick ごとに走ります。** **配置のたびに Artifact の記録を引くと、その分だけ遅くなり、引けない場合の分岐が増えます**（**削除済み・未登録・読めない**）。**「助言が無い」だけの話に、経路の失敗を混ぜない**ほうが安全です。
- **写しが古くなる危険は小さい。** 入力のダイジェストは**受理時に確定**し、**Artifact が後から消えても、その Task の入力は変わらない**（**取得は失敗するかもしれないが、配置の判断は同じ**）。
- **上限がある。** 入力は **最大 64 件**（`maxInputs`）なので、**記録に足しても大きくなりすぎません**。

**決めた形**:

1. **受理**（`internal/core/admission` の検証が通ったあと）で、**入力の `ArtifactID` をダイジェストに解決**し、**Task の記録に `InputDigests` として保存**する。
2. **解決できない入力がある Task は受理しない**（**入力が読めない Task を、後で配置のときに困る形で通さない**）。**fail closed**。
3. **配置**（`pickWorker`）は、**記録の `InputDigests` を `LocalityHint` に渡す**。**Artifact を引き直さない**。
4. **`InputDigests` が空の Task**（入力なし）は、**助言を使わない**（**同点の並べ替えもしない**）。

**何を保証しないか**:

- **「その Artifact を持っている」ことの正しさ**（**申告のまま**、§5）。
- **入力の内容の同一性**（**ダイジェストが一致することだけ**。**中身の意味は EKI が見ない**）。

**未決（残す）**: **`ArtifactID` からダイジェストへの解決を、受理の経路で同期的に行うか**（**受理の遅延**になる）**、非同期に埋めるか**（**配置の判断が「まだ埋まっていない」状態を持つ**）。**まず同期で実装し、遅さが問題になったら測ってから**決めます。
### 5.4 補正: `ArtifactID` は「ダイジェストとは限らない」（2026-11-06、#736）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.2 で「`ArtifactID` はダイジェストではない」と書きましたが、**半分だけ正しい**ことが分かりました。

- **受理の検証**は、`artifact_id` を**不透明な識別子**として扱います（`^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`）。**ダイジェストであることを要求していません**。
- **一方、Client API の成果物の一覧**（`internal/control/clientapi/artifacts_view.go`）は、**`ArtifactID` にダイジェストの 16 進を入れています**（`out.ArtifactID = digest.Hex()`）。

つまり **`ArtifactID` は「ダイジェストのこともある識別子」**です。**実装上の意味**:

1. **受理で解決するとき、`ArtifactID` を 16 進としてパースしてはいけません。** **登録（Artifact の記録）を引いてダイジェストを得る**必要があります。
2. **「一覧がダイジェストを返しているから、入力もダイジェストだ」と推論しない**こと。**一覧の都合と、受理の契約は別**です。
3. **解決できない入力を拒否する**（§5.3 の 2）は**そのまま**です。**`ArtifactID` がダイジェストでない配備でも、登録を引けば解決できます**。

**この補正の意味**: **「読めば分かる」で実装を始めると、テスト用の値（`art_1`）では動き、production の値では動かない**、という形の誤りになります。**契約（受理の検証）と、たまたま同じ値になる経路（一覧）を分けて読む**必要があります。
### 5.5 入力そのものが受け付けられていない（2026-11-06、#736）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.3・§5.4 の実装（入力のダイジェストの記録と配線）に着手して、**前提が崩れている**ことが分かりました。

**いまの配備は、Artifact の入力を受け付けません。** 受理の方針（`internal/core/admission/policy.go`）が、**入力が 1 件でもあると `422 ARTIFACT_NOT_AVAILABLE`** を返します（「この配備では、入力の Artifact は利用できない」）。**テスト用の要求はすべて `"inputs": []`** です。

つまり:

- **入力のダイジェストを記録しても、その入力を持つ Task は受理されません。** **書く機会が無い**。
- **`LocalityHint` は、入力のダイジェストが空なので、常に「助言なし」**になります。**配線しても何も起きません**。
- **§5.3 の「解決できない入力がある Task は受理しない」は、いまの配備では「入力がある Task は受理しない」と同じ**です。**方針が先に止めています**。

**決定: §5.3 の配線は、Artifact の入力を受理できるようにする決定のあとにする。** **先に「入力を受け付ける」を決めずに、入力の記録だけを作らない**（**使われない欄と、到達しない分岐**が増える）。

**何が要るか（次の決定）**:

1. **入力の Artifact を受理してよい条件**（**登録済みであること**、**取得できること**、**data_class の扱い**）。
2. **入力の取得の失敗を、受理の失敗として扱うか**（**fail closed** か、**配置のときに扱う**か）。
3. **`ARTIFACT_NOT_AVAILABLE` を外す時期**と、**外したときに何が保証できなくなるか**。

**この節の意味**: **「助言の仕組み」を作り込むほど、土台（入力が通らない）との差が広がります**。**動かない機能の周辺を磨くより、土台が無いことを先に記録する**ほうが、次の判断を間違えません。
### 5.6 入力の受理は「解決できる配備」だけに開く（2026-11-06、#741）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.5 の「入力そのものが受け付けられていない」に対して決めます。

**決定: 入力を解決できる配備（`Config.Inputs` に `ArtifactResolver` がある配備）だけが、入力を受理する。解決できない配備では、従来どおり `422 ARTIFACT_NOT_AVAILABLE` で断る。**

理由:

- **断る理由は「Artifact の名前を信じない」こと**でした（`policy.go` のコメント）。**その理由は、解決できる配備では消えます**（**名前ではなくダイジェストで扱える**）。**理由が消えた配備だけ開く**のが筋です。
- **配備ごとの能力を、設定で表せます。** **Artifact の登録を持たない配備は、入力を受け取っても配置の助言に使えない**ので、**受け取る意味がありません**（**受け取って捨てるより、断るほうが正直**）。
- **「解決できない入力は受理しない」はそのまま**（**fail closed**、§5.3）。**入力を 1 件でも解決できなければ、Task を受理しません**（`INPUT_ARTIFACT_UNRESOLVABLE`）。
- **入力なしの Task は影響を受けません**（**解決の設定と無関係に通る**）。

**決めた形**:

1. `admission.Config.Inputs`（`ArtifactResolver`）が**非 nil のときだけ**、`policy.check` が入力を許す（**設定が能力の宣言**）。
2. 受理の直前に **`InputDigests` で解決**し、**失敗は `INPUT_ARTIFACT_UNRESOLVABLE`（422）**。
3. **解決したダイジェストを `Accepted.InputDigests`** で返す（**記録に載せるのは次の段**）。
4. **記録への保存と配置への配線は、まだしない**（**#736 の続き**）。

**何を保証しないか**:

- **入力の内容の正しさ**（**ダイジェストが一致することだけ**）。
- **Artifact の取得**（**配置・実行の段の話**。§5.5 の 2 は未決のまま）。
### 5.7 入力の取得の失敗は、実行の段で扱う（2026-11-06、#741）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.5 の未決「入力の取得の失敗を、受理の失敗として扱うか、実行の段で扱うか」を決めます。

**決定: 取得の失敗は実行の段で扱う。受理では、ダイジェストに解決できることだけを確かめる。**

理由:

- **受理が決めるのは「走らせてよいか」で、実行が決めるのは「いま走らせられるか」**です。**取得できるかは後者**で、**Artifact の期限切れや保存先の障害で、受理のあとにも変わります**。**受理のときに確かめても、実行のときの状態は保証できません**（**確かめた気になるだけ**）。
- **受理を保存先の可用性に依存させると、保存先が重いときに受理まで止まります**。**Task を受け付けて並べることは、Artifact の取得と独立に進められます**。
- **失敗は、Attempt の失敗として記録できます**。**`retryable` の Task なら再試行**し、**そうでなければ失敗**します（**既存の信頼性の扱いをそのまま使う**）。
- **取得できない入力を、黙って空として扱いません**。**実行を始めない**（**入力を読まずに走る Task は、結果の意味が変わる**）。

**決めた形**:

1. **受理**: `ArtifactID` → ダイジェストの解決だけを行う（**解決できなければ受理しない**、§5.3）。
2. **配置**: **入力のダイジェストを、Worker へ渡す割当に含める**（**Worker が自分で取得する**）。
3. **実行**: **取得に失敗したら、Attempt を失敗にする**（**第三者に取得させる・代理で取りに行く経路は作らない**）。
4. **どの失敗かを記録に残す**（**取得できなかったことを、結果が空だったことと区別する**）。

**何を保証しないか**:

- **取得できること**（**保存先の可用性に依存**）。
- **取得したバイトが入力のダイジェストと一致することの検証**は、**取得する側（Worker）の責任**とします（**EKI は転送を仲介しない**）。

**未決（残す）**: **Worker が取得できないときに、Control Plane が代理で取得するか**（**ネットワークの分離された配備では要るかもしれない**）。**まず Worker 取得だけを実装し、必要が出たら足します**。
### 5.8 入力のダイジェストは、別の表に順序つきで置く（2026-11-06、#741）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.3 の「Task の記録に `InputDigests` を持たせる」を実装しようとして、**置き場所を変えるべき**ことが分かりました。

**分かったこと**:

- `tasks` の行を読む経路が**8か所**あり、**すべてが同じ列の並び**を書いています。**列を足すと、8か所すべてを直す**ことになります。
- **古い schema のまま動かす試験**（`openWithMigrations(path, migrations[:N])` で当時の DB を作り、更新を確かめるものが8件）は、**その schema に無い列を書かない**前提で動いています。**列を足すと、更新前の DB に Task を書く時点で落ちます**（実際に落ちました）。
- **`TaskRecord` にスライスを足すと、`==` で比較している箇所が壊れます**（記録の比較は値比較に直す必要がある）。

**決定: 入力のダイジェストは、`task_inputs` のような別の表に、(task_id, 順序, ダイジェスト) の行として置く。**

理由:

- **順序のある一覧は、行の集まりが自然**です。**1列に詰めると、区切り文字と順序の両方を自分で守る**ことになります（**列の CHECK も書きにくい**）。
- **`tasks` の行を読む8か所に触れません。** 入力のダイジェストが要るのは**配置の判断**だけで、**Task の状態遷移は要りません**。**要る場所だけが読む**形にすれば、**既存の経路はそのまま**です。
- **古い DB は、表が空なだけ**です。**列の有無で分岐する必要がありません**（**更新前の DB に Task を書く試験も、そのまま通ります**）。
- **`TaskRecord` にスライスを足しません。** **比較の意味を変えずに済みます**（**記録は値で比べられるまま**）。

**決めた形**:

1. **受理**で解決したダイジェストを、**Task と同じトランザクションで `task_inputs` に書く**（**入力の無い Task は行を作らない**）。
2. **配置**は `LoadTaskInputs(ctx, taskID)` で読む（**Task の記録とは別の呼び出し**）。
3. **`TaskRecord` は変えない。**
4. **古い schema の試験は、`task_inputs` が無くても動く**（**表を作る migration は新しい番号**）。

**この節の意味**: **「記録に欄を足す」は、いちばん素直に見えて、いちばん広く触る**やり方でした。**読む場所が8か所あることと、古い schema で動く試験があること**を、**着手してから知りました**。**触る範囲を小さくする置き場所**に変えます。
### 5.9 入力の分類は、配備の方針が言う（2026-11-06、#741）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

配置の助言（§5）を使えるのは**公開の入力**だけですが、**その分類を誰が言うか**が未決でした。候補は三つありました。

| 案 | 内容 | 難点 |
| --- | --- | --- |
| **Task ごとに宣言** | 依頼の本文に `data_class` を書く | **依頼元が「公開」と書けば、機密でも助言の対象になる**（**分類を主張する側が得をする**） |
| **入力ごとに宣言** | 入力の参照ごとに `data_class` | 同上。**さらに、分類の無い入力をどう扱うかを決める必要がある** |
| **Artifact の記録の分類** | 成果物の `data_class`（ADR-0034 §9）を使う | **あれは Worker の申告**で、**入力の分類ではない**（**別の Task の出力を、入力として使うとは限らない**） |

**決定: 配備の方針（`Policy`）が「入力は公開か」を言う。それ以外では助言を使わない。**

理由:

- **分類を主張する側に、分類を決めさせない。** **依頼元が「公開」と書けば機密でも助言の対象になる**なら、**「公開」と書く動機**が生まれます（**§5 の「自己申告を条件にしない」と同じ理由**）。
- **配備は、自分が扱うデータを知っています。** **「この配備の入力は公開のデータだけ」**という宣言は、**配備の性質**であって、**依頼ごとの主張**ではありません。
- **既定は「使わない」。** 方針が何も言わなければ、**助言は効きません**（**安全側の既定**）。
- **粒度を粗くしておく。** **入力ごとに分けると、分類の無い入力をどうするかを決める必要**が生まれます。**配備単位なら、その判断が要りません**。

**決めた形**:

1. `Policy` に **`PublicInputs bool`**（仮の名前）を足す。**true のときだけ**、配置の助言が使える。
2. `PlacementHintSource` の実装は、**`task_inputs` のダイジェスト**と、**方針の `PublicInputs`** を返す。**分類は Task ごとには読まない**。
3. **方針が古い場合**は、**その時点の方針**で判断します（**Task の受理時の方針を覚えない**。**助言は速さの話**なので、**方針の変更に追従してよい**）。

**何を保証しないか**:

- **配備の宣言が正しいこと。** **「公開だけ」と宣言した配備が、実際には機密を扱う**ことは、**EKI には分かりません**（**配備の責任**）。
- **入力の内容の分類**（**EKI は中身を見ません**）。
### 5.10 入力の取得は、Worker Plane の取得の口から行う（2026-11-06、#741）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

§5.7 で「**取得は Worker が行う**」と決め、§5.3 で**割当にダイジェストを載せる**ところまで実装しました。**取得の口が無い**ので、次にその形を決めます。

**決定: Worker は、Worker Plane の取得の口から、ダイジェストで入力を受け取る。**

**形**:

1. **経路**: Worker Plane に `GET /test-profile/v1/artifacts/{digest}` を足す（**test-profile の下**に置く。**本番の Worker Protocol は #198 の決定後**）。
2. **認証**: **既存の mTLS**（クライアント証明書）。**新しい資格情報を足さない**。
3. **認可**: **そのダイジェストが、その Worker に現在割り当てられている Attempt の入力に含まれること**。**「持っているから取れる」ではない**（**割当に載っていること**が根拠）。**割当が失効したら取れない**。
4. **アドレス**: **ダイジェストだけ**。**パスや ID で任意の場所を指せない**（**SSRF の余地を作らない**）。
5. **応答**: **内容そのもの**（`application/octet-stream`）。**サイズ上限**を設け、**超過は失敗**（**読めないまま大きな入力を抱えない**）。

**理由**:

- **取得は Worker→Control Plane の向き**で、**既に mTLS で認証されている経路**に載せるのが**いちばん資格情報を増やさない**。
- **認可の根拠を割当にする**ことで、**「認証された Worker は何でも取れる」を避けます**。**割当は Control Plane が決めた事実**で、**Worker の申告ではありません**。
- **ダイジェストだけをアドレスにすると、取得の意味が「内容を確かめる」ことになる**（**受け取った側でダイジェストを検証できる**）。**パスで指定させると、その検証ができない**。

**何を保証しないか**:

- **取得できること**（**保存先の可用性**、§5.7）。
- **転送量**（**EKI は測らない**、ADR-0037 §11.6）。
- **data_class による取得の制限**。**分類は配置の判断に使い**（§5.9）、**取得は「割当にあるか」で決めます**。**分類で取得を止めると、割当と取得の判断が二重になり**、**片方だけ緩い配備**が生まれます。

**未決（残す）**: **本番の Worker Protocol にこの口をどう載せるか**（#198 の決定と合わせる）。
