# ADR-0029 「EKIへ載せない」判断をスケジューラより前のSuitabilityゲートで行う

- 状態: **提案中**
- 日付: 2026-10-06
- 関連: RQ-011, RQ-014, RQ-046, RQ-024, Issue #58
- 番号: 当初ADR-0007として採番したが、同じ番号が外部副作用の再実行規則（暫定）にも付いていたため、2026-10-28に0029へ振り直した（Issue #246）

## 1. 背景

EKIの価値は、多くのワーカー（Worker）へタスク（Task）を送れることではありません。遊休資源を使う意味があるワークロードだけを、安全にファブリック（Fabric）へ入れることにあります（[value.md](../../product/value.md)の「Compute where it is economically sensible」、[principles.md](../../product/principles.md) §5、§6）。

単純に作るなら、受理したタスクをすべてスケジューラへ渡し、スケジューラに最適なワーカーを選ばせる設計になります。この設計には次の問題があります。

- スケジューラは必ずどこかのワーカーを選ぶので、「どこにも置かない方が良い」という答えを返しにくい構造になる。
- たとえば、2GBの入力を読んで10秒だけ計算するタスクでは、どのワーカーを選んでも転送時間が計算時間を上回る。スケジューラが最速のワーカーを選んでも、ローカルで実行するより遅くなる。
- 外部APIへ書き込むタスクでは、ワーカーが離脱してリトライされると二重に書き込まれる（RQ-046）。これは性能の問題ではない。そもそもファブリックへ載せてはいけない性質である。
- #19のlearned schedulingのようにスケジューラの性能を上げても、載せるべきでないタスクが混ざったままでは、導入価値を説明する根拠にならない。

## 2. 決定

1. 受理審査（Admission、ADR-0006、ADM-2）の後、スケジューラの前に**ワークロードSuitabilityゲート**を置く。スケジューラが決めるのは「どこへ置くか」だけであり、「EKIへ載せるか」はゲートが決める。
2. ゲートは次の3つのいずれかを返す。スケジューラへ進めるのは`FABRIC_JUSTIFIED`だけである。
   - `FABRIC_JUSTIFIED`: ファブリックで実行する根拠がある。タスクをスケジューラへ渡す。
   - `FABRIC_NOT_JUSTIFIED`: ファブリックで実行する根拠がない。理由コードを添えて返す。EKI Coreはローカル実行を始めない。どこで実行するか（ローカルのプロセス、既存のサーバー、クラウドなど）は、クライアント（Client）または上位のオーケストレータが決める。
   - `NEEDS_MEASUREMENT`: 入力量や実行時間の目安など、判定に必要な事実が足りない。足りない事実を推測で埋めて`FABRIC_JUSTIFIED`にはしない。見込まれる利点が、設定した最小の差以下のときもこれを返す。

   現在のProfileでは安全に扱えないタスクは、ゲートの値では表さない。リトライの扱いが決まっていない外部への書き込みや、データ分類（Data Class）上ワーカーへ渡せない入力がこれにあたる。これらは受理審査と、セキュリティ・データ・資源の実行可能性（feasibility）の判定で候補から外し、ゲートへは渡さない。
3. 最初の実装（EKI-SUIT-0）は、あらかじめ決めた規則だけで判定し、MLや学習済みモデルを使わない。判定に使った事実と規則のバージョンを記録し、あとから判定理由を説明できるようにする。
4. ゲートの入力には、クライアントが申告したワークロードの事実も含まれる。ただし、申告（Claim）として扱う（原則 §3）。クライアントが申告を偽っても、セキュリティプロパティは崩れない。受理審査、リース（Lease）、端末側ガバナ（Local Governor）が別にそれを守っているからである。ゲートが守るのは効率と導入判断の正しさであり、ゲートはセキュリティ境界ではない。
5. `FABRIC_NOT_JUSTIFIED`を返すのは失敗ではなく、製品が正しく動いた結果である。この判定も計測し、表示する。

## 3. 影響

### 良い点

- 「分散しない」という答えを、スケジューラのついでではなく、明示した判断として返せる。
- 導入を検討する人へ、どのワークロードがEKIに向くかを、規則と記録をもとに説明できる。
- スケジューラを評価する際（#19）、ファブリックに向くタスクだけを対象にできる。

### 悪い点と制約

- ゲートの規則が粗いと、本来EKIで有利になるタスクまで`NEEDS_MEASUREMENT`に回してしまう。初期はこの保守的な振る舞いを許容する。
- クライアントが申告を偽れば効率は下がり得る。資源上限（RQ-009、RQ-017）と資源提供実績（Contribution）の記録でこれを抑えるが、ゲート単体では防がない。

## 4. 未決事項

- 転送コストと計算で得られる利点を比べる閾値を、どの受け入れシナリオ（Acceptance Scenario）から決めるか。
- `NEEDS_MEASUREMENT`になったタスクを管理された資源で試しに実行し、足りない事実を集める経路を持つか。

## 5. データの所在は「助言」としてだけ使う（2026-11-05、#717）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

PAS-CAND-01（説明の並列探索）の受け入れ条件に、**「同じ入力を12回転送するより、入力を持つ Worker や近くの Worker に、まとめて配置する判断ができる」**があります。いまの配置は**資源の要求だけ**を見ており、**データの所在を入力に持っていません**。

**決定: データの所在は、配置の「助言」としてだけ使う。判断の根拠にはしない。使えるのは公開・低機密の入力に限る。**

理由:

- **「持っている」は自己申告で、確かめられません。** Worker が「この Artifact を持っている」と言っても、**EKI は確かめる手段を持ちません**（**持っているかを問い合わせるには、その中身か一覧を信じるしかない**）。**確かめられない申告を配置の条件にすると、申告する側が得をします**（**わざと「持っている」と言って、機密の入力を自分に寄せる**）。
- **助言なら、外れても壊れません。** 申告が嘘でも、**Artifact はダイジェストで取得して検証**されるので、**余計に転送しただけ**で済みます（ADR-0034）。**配置の正しさは資源の判断が担保**し、**所在は速さの話**にします。
- **機密の入力では使いません。** 「近いから」という理由で**機密を特定の Worker に寄せると、その Worker を狙う攻撃者に有利**です。**データの分類（`data_class`）が public・low のものだけ**を対象にします。

**決めた形（実装するとき）**:

1. Worker の登録に **`held_artifacts`（ダイジェストの一覧）**を足す。**任意**で、無い場合は「何も持っていない」と同じ扱い。
2. 配置は**資源の適合で候補を絞ったあと**、**同点の範囲で** `held_artifacts` に**入力のダイジェストが含まれる Worker を優先**する。**資源の判断を飛び越えない**（**資源が足りない Worker は、持っていても選ばない**）。
3. **`data_class` が internal 以上の入力では、この優先を使わない**（**申告に機密の行き先を決めさせない**）。
4. **「持っている」を理由に、取得の検証を省かない**（**ダイジェストの検証は常に**）。

**何を保証しないか**:

- **「近い」ことは保証しません。** EKI は**ネットワークの距離を知りません**（**知っているのは「持っていると申告した」だけ**）。
- **転送量は減るとは限りません。** 申告が正しければ減りますが、**EKI は測っていません**（**転送量を判定しない**、ADR-0037 §11.6 と同じ立場）。

**未決（残す）**: `held_artifacts` を**Worker の登録に持たせるか、Artifact の取り出しの履歴から推定するか**（**申告させるほうが単純だが、推定のほうが嘘に強い**）。実装するときに決めます。
