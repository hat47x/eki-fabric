# ADR-0014 委任先の登録、予算、容量の権限と、管理者権限の委任状を加える

- 状態: **採用**
- 日付: 2026-10-20
- 関連: Issue [#147](https://github.com/hat47x/eki-fabric/issues/147)、[#148](https://github.com/hat47x/eki-fabric/issues/148)、[ADR-0013](0013-product-core-and-faces.md)、[委任の核の概念モデル](../../research/topics/delegation-core-model.md)、[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)、RQ-016、RQ-017、RQ-023、RQ-047、RQ-048、RQ-051

## 1. 背景

ADR-0013で、EKIのコアを信頼の水準に応じた委任の核と定め、自律の最適化、クラウドの自動拡張、SEIの組織レベルの意思決定との連動へスコープを広げました。[委任の核の概念モデル](../../research/topics/delegation-core-model.md)で、Architecture Baseline 0.1の権限と突き合わせた結果、次の判断を受け持つ権限がないことが分かりました。

- 委任先ごとの信頼の水準と、誰がどの委任先を使えるかを、誰が登録するか。
- 予算の総額と配分を、誰が持つか。
- クラウドの拡張のように費用を生む容量の確保を、誰が承認するか。
- SEIへ管理者権限の一部を委ねるとき、何をどの範囲で委ねるか。

候補Scenario PAS-CAND-24〜30の評価（#148）でも、足りないのは新しい要件ではなく、これらの権限の設計だと確かめました。

## 2. 決定

1. DLG-1（委任先と信頼の水準の登録）を加える。 委任先、信頼の水準とその根拠、利用の許可を登録し、失効させる管理の権限とする。RVR-1とRAC-1は、確定に要る検証の強さを、DLG-1の登録から読む。委任先の申告からは読まない。抜き取りの検証で不一致が出た委任先は、管理者が定めた方針に従って自動で一時的に候補から外す。候補から外すことは安全側の操作なので自動で行えるが、候補へ戻すことと信頼の水準を上げることは管理者の操作とする。
2. BUD-1（予算）を加える。 予算の総額と、入れ子の予算の枠（組織、部門、案件、利用者、依頼の群）への配分を持つ。総額は人間の管理者だけが定める。配分は、人間の管理者か、委任状を持つ主体が行う。ADM-2（依頼の受理）とCAP-1（容量の確保）は、BUD-1の枠から予約する。予算は物理量で表し、金額への換算は持たない（ADR-0010）。
3. CAP-1（容量）を加える。 費用を生む容量（クラウドの拡張、有償の外部の資源）の確保と解放を、SCH-1の提案を受けて承認する。確保の費用は、提案の時点で、容量を必要とする依頼者の予算の枠と、組織の容量の予算の枠の両方から予約する。資源の提供元の側の上限と合わせ、二重に止まる。管理者が定めた閾値を超える確保は、人間の承認を経るまで行わない。CAP-1はADM-2とBUD-1から分ける。予算を配分する権限と、費用を使う権限が同じだと、一つの侵害で配分と支出の両方を操作できるからである。
4. ADM-1に、管理者権限の委任状を加える。 人間の管理者は、管理者権限の一部を、委任状として範囲と期限を限って委任できる。委任状は、委任先の主体、委任できる操作、越えさせない線、人間の承認を求める閾値、期限を持ち、人間の管理者が署名する。期限を持たない委任状は発行しない。委任状を持つ主体は、委任状を自分で更新できない。委任状を持つ主体のClientとしての識別と、委任状を使う識別は分ける。
5. 権限の有限性を基本原則に加える。 実行の権限（Lease）も、管理の権限（委任状）も、期限、範囲、予算を持つ。常駐の処理とSEIへの委任状も、この原則の例外にしない。
6. 既存の権限を改める。
   - ADM-2: 委任先の指名を、DLG-1の利用の許可と照らして「許された範囲を狭める」条件として受理する。具体的なWorkerの選択を持たせない境界は変えない。Session、Sandbox、常駐の依頼を受理する。予算はBUD-1の枠から予約する。
   - LSE-1: Leaseの対象を、Task Attemptに加えて、Sessionと常駐の期間へ広げる。常駐は期間ごとにLeaseを更新し、更新のたびにBUD-1の予約、DLG-1の失効、Policyの現在性を確かめ、fencingの番号を進める。
   - RVR-1、RAC-1: 確定に要る検証の強さを、DLG-1に登録した信頼の水準から決める。
7. Authority BoundariesをBaseline 0.2へ上げる。 上の決定を[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)の正本へ反映する。

## 3. 移行

- M0とMVPの実装は、Baseline 0.1の権限の上で進めてよい。新しい権限は、ADR-0013の段階（S1以降）で実装する。M0とMVPの優先順位は変えない。
- いまの`eki-control`の受理の方針（全Taskで共通の一組の上限と、利用者ごとの未完了の上限）は、BUD-1とDLG-1の最も単純な場合とみなせる。予算の枠が一つで、委任先が一つ、等級が一つの状態である。新しい権限を実装するときは、この状態から設定を移せるようにする。
- 小さな構成（DP-1）では、新しい権限を一つのプロセスに同居させてよい。その場合も、Authority Boundaries §2のとおり、権限の識別、鍵、書き込める状態、監査の記録を分ける。

## 4. 影響

### 良い点

- ADR-0013の自律の最適化、クラウドの拡張、SEIとの連動を、既存の「提案と承認を分ける」構造の中に収められる。
- 費用を生む権限が、受理からも予算の配分からも分かれ、費用を負わせる攻撃（PAS-CAND-27）を二重に止められる。
- SEIへの委任が、期限と範囲のある委任状として記録され、SEIの停止や誤りの影響を時間の上でも閉じ込められる（PAS-CAND-25、26）。

### 悪い点と制約

- 権限の数が増え、小さな構成でも鍵と状態の分離を保つ実装の手間が増える。
- 予算の枠の入れ子を深くすると、予約と精算の整合が難しくなる。最初は浅い入れ子から始める。

## 5. 未決事項

- 信頼の水準の引き上げを、一人の管理者の操作で成立させるか、複数人の承認を求めるか（Authority Boundaries §16のmulti-party approvalと合わせて決める）。
- 委任状で委任できる操作の一覧と、人間の承認を求める閾値の既定値（#141）。
- 予算の枠の入れ子の深さ（#142）。
- 信頼の水準の表し方（Assuranceの軸の組み合わせか、名前を付けた段階か。#138）。
