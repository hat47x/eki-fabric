# ADR-0037 Workerの出力の本体を、Workerのディスクに保持する

- 状態: 提案中（**仮承認**。利用者の包括承認 2026-11-03 による）
- 日付: 2026-11-03
- 関連: #320（完了）、#491、#492、#493、#494、#198、ADR-0034

## 1. 問題

native runner は標準出力をメモリのバッファへ溜め、SHA-256 と byte 数だけを `Result` へ入れて返します。プロセスが終われば本体は消えます。そのため、委任が完了しても依頼元が受け取れるのは「何かのダイジェスト」だけで、出力そのものは取り出せません。

本体を残すには、**どこに・いつまで**置くかを決める必要があります。Control Plane へ送る経路（#492）と、依頼元へ返す経路（#494）は別の判断なので、ここでは最初の区間だけを決めます。

## 2. 決定

**Worker は出力の本体を、自分のディスクの spool ディレクトリに保持します**（`internal/agent/spool`）。

- 置き場所: Agent の状態ディレクトリの下（`state/spool`）。モード `0700`。出力は Worker の持ち物であり、同じホストの他の利用者に読ませる理由がありません。
- 1つの出力につき1ファイル。ファイル名は `<sha256>.<expires_at_unix_nano>.body`。**期限をファイル名に入れる**のは、`Sweep` がファイルの更新時刻に依存しないためです。判定する時計は `Put` が使った時計であり、ディスクの時計ではありません。
- 書き込みは一時ファイルへ書いてから `rename`。途中で落ちても、半端な本体を成果物として残しません。
- 上限は WorkOrder の `resources.output_bytes_max`。**超えたら `ErrTooLarge` で失敗**し、本体は残しません。打ち切った本体は別のダイジェストになるので、「入りませんでした」以外の答えは嘘になります。
- 読み出し時は、**期限**と**ダイジェストの再計算**の両方を確かめます。ディスク上のファイルが入れ替えられていれば `ErrDigestMismatch` で拒否します（fail closed）。
- 保持期間の既定は 24 時間（`New` の引数）。Control Plane が受け取ったら（#492）、または期限が来たら `Sweep` が消します。

## 3. なぜ Control Plane へ直接送らないのか

最初から Control Plane へ送る形にすると、送信の失敗・再送・分割の設計が同時に必要になります。**最初の区間をローカルに閉じる**と、runner は「書けたか、上限を超えたか」だけを見ればよく、送信の設計（#492）は独立に進められます。

## 4. 何を保証しないか

- **耐久性は保証しません。** Worker のホストが落ちれば本体は失われます。その場合、依頼元はダイジェストだけを受け取り、本体は取得できません（#493 で記録の表現を決めます）。
- **機密性は、ホストのファイル権限までです。** ディスク全体の暗号化や、ホストの管理者から守ることは、この決定の範囲外です。
- **中身の安全性は保証しません。** 本体は信頼できない入力であり、EKI は解釈しません（`spec/external/README.md` の該当節）。

## 5. 2つの上限の関係（2026-11-03、仮承認）

出力の量には2つの上限が関係します。どちらも同じ数字ではありません。

- **WorkOrder の `resources.output_bytes_max` は、1つのTaskの出力の上限**です。依頼元が「この依頼の出力はこれだけ」と宣言した値で、Taskごとに違います。spool はこの値で `Put` を止めます。
- **Local Governor の上限は、ホストが同時に抱えてよい量の上限**です。Worker の持ち主（業務端末の利用者など）が決める値で、Taskごとではなくホスト全体にかかります。

**決定:**

- spool が検査するのは **WorkOrder の値**です。Taskの都合で決まる値であり、「この依頼の出力が入るか」を判断できるのはこちらだけです。
- Local Governor の上限は、**同時に走るTaskと保持する本体の合計**に対して効きます。spool の保持量が上限に近づいたら、新しいTaskを始めない（`held` にする）のが Governor の仕事です。
- **WorkOrder の値が Local Governor の上限より大きい場合**、そのTaskはそのホストでは走れません。走らせて途中で失敗させるより、始める前に断るほうが、Worker の資源を無駄にしません。断り方は Governor の既存の判断（受けない理由）に含めます。

**この決定の限界:** 「合計」を数えるには、いま保持している本体の量を知る必要があります。spool はディレクトリの合計を出す手段（`Usage`）を持っていないので、実装は次のIssueで行います。

## 6. 未決

- 保管期間を配備ごとに変えられるようにするか（いまは 24 時間固定）。
- 転送後に消すか、期限まで残すか（#492 と合わせて決める）。
- spool の合計量を Governor へ渡す方法（`Usage` の追加）。

## 7. 転送は既存の本文の経路を使う（2026-11-03、仮承認、#492）

出力の本体を Control Plane へ運ぶ経路は、**新しい経路を作らず、すでにある本文の受信路を使います**（ADR-0034 §2.2 の claim 報告に続けて本文を送る経路）。

- 受信側の `Put(body, claimedDigest, maxBytes)` は、**申告されたダイジェストを受け取り**、byte 数を上限で切ります。つまり「申告と本体を突き合わせる」形は、この関数の引数としてすでに用意されています。
- **再計算は受信側で行います。** Worker の申告は事実ではないので、受け取った本体から SHA-256 を計算し、`ResultClaim` の値と一致しなければ受理しません（fail closed）。不一致のときは、保管もしません。
- 途中で切れた転送（本文が途中で終わる、上限を超える）は、**成果物として残しません**。半端な本体は、正しいダイジェストを持たないので、後から「取得できる成果物」と区別できなくなります。
- 圧縮や分割で運ぶ場合も、**展開後の byte 列**で計算します（`spec/external/README.md` の束縛の規則）。

**この決定の限界:** 経路そのもの（HTTP の形、再送、分割アップロード）は ADR-0034 の決定に従います。この節は「どの値で何を確かめるか」だけを決めています。

**受信側は、すでにこの規則で動いています**（2026-11-03 に確認）。`internal/control/claimbody` の `Receive` は claim を読み、worker の一致を確かめ、`Put` に申告ダイジェストと上限（**claim の値**であり、リクエストの値ではない）を渡し、測った値が一致したときだけ保持します。試験も揃っています。

- `TestAReceivedBodyIsMeasuredAgainstTheClaimItBindsTo` — 申告と一致すれば保持され、測ったダイジェストが返る。
- `TestADisagreeingBodyIsNotKept` — 一致しなければ `ErrDigestMismatch` で、保持されない。
- `TestTheMaximumComesFromTheClaimNotTheRequest` — 上限は claim から取る（送信側の言い値では広がらない）。

したがって #492 の残りは**送る側**だけです。Worker が spool に置いた本体を、claim の報告に続けてこの経路へ送る配線が要ります。

**未決:** 転送が成功した後、spool の本体をすぐ消すか、保持期間まで残すか。すぐ消すと、Control Plane 側で保管に失敗したときに再送できません。

## 8. 送る側の現状（2026-11-03、仮承認、#508）

**Agent は、すでに claim の後に本体を送っています**（`internal/agent/service/execution.go` の `sendingBodies.Send`）。

- claim を送り、成功したら `bodyHold` から本体を取り出して `SendBody` に渡す。送信は 30 秒で打ち切り、成否を `eventBodySent` / `eventBodySendFailed` として記録する。
- 本体は**メモリ上**（`bodyHold`）にある。プロセスが落ちると失われる。

したがって spool が足すのは**耐久性**です。claim を送った直後にプロセスが落ちても、spool に本体が残っていれば、再起動後に同じダイジェストで送り直せます。**送信の経路そのものは作らず、この既存の経路に spool を差し込む**のが #508 の作業です。

**順序（決めたこと）:**

1. runner が出力を返したら、`bodyHold` に入れる前に spool へ書く（`spool.Put`）。ダイジェストは spool が計算した値を使う。runner の値と食い違えば、**spool の値を採る**（同じ byte 列を2回測っている以上、食い違いは測定の誤りであり、後から受信側が同じ値で判定する）。
2. claim の送信後、`bodyHold` の本体を送る。送信に失敗しても、spool の本体は**消さない**。
3. 再送は、保持期間内であれば spool から読める（`spool.Open` が期限とダイジェストを確かめる）。

**この決定の限界:** 再送のきっかけ（定期の走査か、次回の claim 時か）は決めていません。決定には、Attempt がすでに閉じている場合に同じ本体を送ってよいか（受信側は `ErrUnknownAttempt` か既存の受理かを返す）を確認する必要があります。


## 9. 取消・失効のときに、保持している本体をどうするか（2026-11-03、#583）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

**決定: 本体は保持期限まで残す。ただし、取消・失効した Task の本体は、その時点から取得できない。**

3案を比べた結果です。

| 案 | 却下した理由 |
| --- | --- |
| すぐ消す | **取消の理由を後から調べる材料が消える。** 何が作られていたかを知らないまま「取り消しました」と説明することになる |
| 期限まで残し、取得も許す | **「取り消した」と「まだ取れる」が食い違う。** 依頼元から見ると取消が効いていない |
| **残すが取得は止める（採用）** | 調べる材料を残しつつ、外から見た意味を「取れない」に揃えられる |

実装上の扱い:

- 取得の判定は**Task の状態**を見る。`cancelled` など終端に達した Task の本体は、**依頼元にも返さない**。
- 依頼元には **410** と `artifact_withdrawn` を返す。他人には従来どおり **404**（存在を漏らさない）。
- 本体の削除は**保持期限の掃除（`Sweep`）に任せる**。取消の経路でファイルを消すと、**取消の処理が失敗したときに「消えたかどうか」が分からない**状態が生まれる。

**何を保証しないか**: 取消の直前に取得された本体は取り戻せません（取得は記録に残りますが、コピーは防げません）。

**未決**: 取消の理由（誰が・なぜ）を `AcceptedResult` に残すかどうか。

## 10. 台帳（lease registry）を状態ストアへ移すか（2026-11-03、#555）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

**決定: いまはファイルのまま。移すのは、状態ストアに「回収の口」を用意する決定をしたあと。**

理由:

- **状態ストアには回収の口が無い。** 貸与の列挙・期限の判定・状態遷移を**1つの取引**で行う方法が、いまのインターフェースに無い（`statestore` を確認済み）。移すには**新しい操作を設計**することになります。
- **回収の掃除を状態の更新と同じ取引空間に入れると、競合の形が変わる。** いまは**別のファイル**なので、掃除が失敗しても**状態の書き込みを巻き込みません**。同じ空間に入れると、**掃除の失敗が状態の書き込みを待たせる**（またはその逆）形になります。
- **回収は「止まっても被害が小さい」処理**です（§5）。**止まる前提で作ってよいもの**を、わざわざ**状態の正しさに近づける**理由が薄い。

**移す場合の形（将来の設計メモ）**:

1. `ListExpiredLeases(ctx, now, limit)` — 期限切れの貸与を返す（読み取りのみ）。
2. `ReclaimLease(ctx, id, expectedRevision)` — **比較交換**。既に回収済みなら何もせず、競合を返す。
3. `LeaseRecord` に **`ExpiresAt` と `ReclaimState`** を持たせる。**状態遷移の一部として回収を表現**する。

**この3つが揃うまで、ファイルの一覧を正とする。** 移行は**一覧の二重化を避ける**ため、**一度に切り替える**（ファイルを読みながらストアへ書き足す期間を長く取らない）。

**未決**: 上の3つを**いつ設計するか**。いまの優先度では、**配備のパスが1つ減る**以外の利点が小さく、**競合の設計**のほうが高くつきます。

## 11. 割当を受け入れるときの、資源と出力の判定（2026-11-03、#505）

**仮承認:** 本節は利用者の包括承認（2026-11-03）による仮承認です。

部品（`governor` の `Decision.Accept`、`spool` の集計）は揃っていますが、**割当の受け入れ**がそれを使っていません。使うために必要な**写像**を決めます。

### 11.1 資源の写像: ホストに対する百分率の**最大**を取る

`governor.Resource` は **1〜100 の百分率**です。WorkOrder の資源（`cpu_millis`・`memory_bytes`）は**絶対量**なので、**ホストの総量**で割って百分率にします。

- **百分率は切り上げ**（`ceil`）、**1〜100 に丸め**ます。`0` は「使わない」と読めてしまい、**要求があるのに無いことになる**ためです。
- **複数の資源があるときは最大を取ります。** CPU とメモリは**別々の制約**で、**和を取ると二重に数える**ことになります。**いちばん厳しい1つ**が受け入れを決めます。
- **ホストの総量は設定**で持ちます（`host_cpu_millis`・`host_memory_bytes`）。
- **設定が無いときは判定しません。** 意味のない数字（「とりあえず 10」）で判断するより、**判定していないことを知らせる**ほうが安全です。**起動時に警告**を出し、割当は従来どおり受け入れます。

### 11.2 出力の見込み: `output_bytes_max` を予約として使う

`expectedOutputBytes` には **WorkOrder の `output_bytes_max`** を渡します。

- **最悪値で判定します。** 実績の中央値を使うと、**外れたときに実行の途中で失敗**します。**始める前に断る**ほうが、Worker の時間を使いません。
- 「小さいホストでは何も始められない」という反論は、**Task 側の `output_bytes_max` を下げる**か、**ホストの予算を増やす**で解きます。**判定を甘くして解く問題ではありません**。

### 11.3 断る理由は、数字で返す

予算や資源で断るときは、**何がいくつ足りないか**を返します。「受け入れられません」だけでは、**依頼元も運用者も次の手を打てません**。

**未決**: 資源の写像を**ホストの実測**（CPU コア数・メモリ量）から既定値として埋めるか。

### 11.4 ディスクは「総容量」を分母にする（2026-11-03、#653）

`TemporaryDiskBytes` も百分率に写します。**分母は空き容量ではなく、総容量**です。

- **空き容量を分母にすると、同じ要求が通ったり断られたりします。** 他の処理が書いているだけで分母が動くので、**依頼元から見て結果が再現しません**。
- **「いま空いているか」は、開始の関門が別に判断しています**（`free()` が**実行中の使用量を引いて**残りを出しています）。**分母は固定、残りは動的**、と役割を分けます。
- 百分率の作り方は CPU・メモリと同じ（**切り上げ・1〜100**）。ホストの総容量は**設定**で持ち、**未設定なら判定しない**（§11.1 と同じ扱い）。

### 11.5 ネットワークは写像しない（2026-11-03、#653）

`NetworkBytesMax` は**転送量**で、`governor.ResourceNetwork` は**百分率**です。**転送量を百分率にするには「何分あたりか」が要ります**が、EKI は**その時間の基準を決めていません**（Lease の寿命か、Task の期限か、固定の窓か）。

**決めないまま数字を作らない**ため、**写像しません**。いまは `requireCapacity` が「ネットワークの上限が1以上あるか」だけを見ます（**容量ゼロの端末では始めない**という意味では効いています）。

**未決**: 転送量を判定に使うなら、**時間の基準**を先に決める必要があります。決まるまで、ネットワークは**「使えるか」だけ**を見ます。

### 11.6 ネットワークの転送量は、EKI では判定しない（2026-11-03、#653 の続き）

§11.5 で「時間の基準が無いので写像しない」としました。**基準を決めずに写像しない、を決定として固定します。**

**決定: M0 ではネットワークの転送量を判定しない。** `governor.ResourceNetwork` は「**使えるか**（上限が1以上か）」だけを見ます。

理由:

- **分母が端末ごとに違い、測れません。** Wi-Fi、4G、有線、共有リンクでは**容量が桁違い**で、しかも**同じ端末でも時間帯で変わります**。**測れない分母で百分率を作ると、数字だけが増えて意味が無くなります**。
- **「何分あたりか」を決めると、Task の実行時間に依存する判定になります。** 短い Task は常に通り、長い Task は常に落ちる形になり、**Task の内容ではなく長さで決まる**判定は資源の判断ではありません。
- **転送量の制限は Worker 側の実行ポリシーのほうが正確です。** 実際に流れた量を見られるのは**実行している側**で、EKI は**後から集計する立場**です（ADR-0037 §2 の役割分担）。

**代わりに何が効くか**:

- **容量ゼロの端末では始めない**（`requireCapacity`）。**ネットワークを使えない機械に、使う Task を割り当てない**という意味で効いています。
- **転送量の上限は WorkOrder に書かれ、Worker が守ります**。EKI は**それを超えたかどうかを結果で判断しません**（§9 の「EKI は本文を読まない」と同じ立場）。

**未決（残す）**: 転送量を**事後の監査**で扱うか（結果に「何バイト送ったか」を申告させ、異常を測る）。これは**判定ではなく観測**の話なので、別の Issue にします。
