# ADR-0007 — 外部副作用の再実行規則（暫定）

- Status: **Provisional（暫定）**
- Date: 2026-10-08
- 有効期間: 上位要件（業務フローとユースケース）が確定するまで。確定後に再判断する。
- Scope: External Effect の再実行判定（`internal/core/effectstate`）

## 1. 背景

Task が外部へ副作用（通知の送信、決済、発注、外部 API の更新など）を起こすとき、Worker が落ちたあとに再実行してよいかは、副作用が外部に届いたかどうかで決まります。

Task State Model には二つの記述があり、食い違って見えます。

- §31 は「dispatch 前なら retry 可能」、「dispatch 後で authoritative Receipt がなければ auto retry しない」と書いています。
- §64 の retry 安全性マトリクスは「non-idempotent effect, not dispatched → bounded retry 可能」と書いています。

実装側の初版（コミット `106cad2`）は、非冪等の効果について「意図は記録されているが dispatch が記録されていない」場合を保留（HOLD）にしていました。§64 と食い違うため、この判断を上位要件が決まるまでの暫定とし、根拠を残します。

## 2. 想定する業務フローとユースケース

上位要件は未確定のため、次の典型的な業務を想定して判断します。

| ユースケース | 効果の性質 | 重複した場合の害 | 保留した場合の害 |
| --- | --- | --- | --- |
| UC1 通知の送信（メール、チャット） | 非冪等 | 軽微（二重に届く程度） | 業務が止まり、人の判断待ちになる |
| UC2 決済、発注、契約の送信 | 非冪等 | 重大（二重の支払いや発注） | 処理が遅れ、照会と突き合わせが必要になる |
| UC3 冪等キーで重複排除できる外部 API | 冪等（Operation ID 付き） | 外部側で吸収される | 不要な待ち |
| UC4 外部副作用のない純粋計算 | なし | なし | 不要な待ち |

UC2 は重複が最も重大なため、再実行の根拠を厳しく求めます。一方で、副作用が**一度も送信されていない**ことが確実であれば、保留は業務を止めるだけで、安全性の利益はありません。

## 3. 決定（暫定）

「送信」の定義を明確にします。呼び出し側（External Effect Adapter）は、外部へ呼び出しを送る前に、dispatch の試行を耐久的に記録します。その記録がない世代は、外部へ呼び出しが送られていないことを示します（commit-before-dispatch）。

| 状態 | 行動 | 理由 |
| --- | --- | --- |
| 純粋計算 | 予算内で再実行 | 外部効果がない |
| 冪等な効果、dispatch 未記録 | 予算内で再実行（同じ Operation ID） | UC3。重複は外部で吸収 |
| 冪等な効果、dispatch 済みで結果不明 | 予算内で再実行（同じ Operation ID） | UC3。重複は外部で吸収 |
| **非冪等な効果、どの世代も dispatch 未記録、意図は記録済み** | **予算内で再実行** | 送信が確実に無いため、重複しない（UC1 の liveness を守る） |
| 非冪等な効果、過去のいずれかの世代で dispatch 済み、結果不明 | 保留。権威ある受領書の照会だけで解決する | UC2。重複を防ぐ |
| 非冪等な効果、意図が無い | 保留（EFFECT_INTENT_MISSING） | 記録の不整合。ストアの障害として扱う |
| 予算を使い切った | 保留（RETRY_BUDGET_EXHAUSTED） | 無限の再試行を防ぐ。失敗にはしない |

最後から二番目の行が、初版からの変更点です。`DispatchedGeneration == 0` を条件に加えました。以前の世代で dispatch が試みられていれば、その結果が不明なまま新しい世代で再実行すると、外部で二重に実行されるおそれがあるためです。

## 4. 前提（この判断の安全性はこれに依存する）

1. **commit-before-dispatch**: 外部への呼び出しを送る前に、dispatch の試行記録が耐久的にコミットされている。これが守られない実装では、再実行で重複が起きる。
2. 記録の耐久性: 記録は再起動をまたいで残る（State Store の durability contract で確認する）。
3. 冪等キー: 冪等な効果では、外部システムが Operation ID で重複排除する（この判定は検証しない）。

前提 1 を破る実装が入った場合、UC2 で重複が起きえます。そのため、External Effect Adapter の適合試験で、呼び出しより前に記録がコミットされることを確認する必要があります（未実装。次の作業単位に含める）。

## 5. 検討した代替案

- **A. 非冪等は、受領書で不適用が確認されるまで全て保留する（初版）**
  - 利点: 前提 1 が破れても、重複は起きない（送信が無い場合も含めて止まるため）。
  - 欠点: 送信前の障害でも人の判断が必要になる。UC1 の業務が止まる。
  - 採らなかった理由: 送信が無いことが確実な場合にまで止めると、安全性の利益がなく可用性だけを失う。前提 1 は、この実装が守るべき不変条件として明文化し、試験で確認する方が筋が良い。
- **B. 効果の種類（プロファイル）ごとに切り替える**
  - UC1 は再実行、UC2 は保留、というように効果定義で指定する。
  - 利点: 業務の害に合わせられる。
  - 欠点: プロファイルの設計が必要で、上位要件が未確定のため今は決められない。
  - 将来の候補として残す。今の判断は、全ての非冪等効果に D3 を適用する。その際、プロファイルで「送信前の再実行を許可する」フラグを足せるように、判定の入力は既に分けてある。

## 6. 結果

- 利点: 送信前の障害で業務が止まらない（UC1）。送信の記録が無い限り、UC2 でも重複は起きない（前提 1 が守られる限り）。
- 欠点: 前提 1 が破れると、UC2 で重複のリスクがある。
- 監視: 「dispatch 試行の記録がないのに外部から応答が来た」場合を、異常として記録する（未実装）。

## 7. 見直しの条件

次のいずれかが起きたら、この ADR を再判断する。

1. 上位要件（業務フローとユースケース）が確定した。特に UC2 の扱いが決まったとき。
2. 実業務で保留（HOLD）が多く発生し、業務が止まった。
3. 外部システムに受領書の照会 API があるかどうかが分かった（照会により保留を解けるかが変わる）。
4. 効果の種類ごとの切り替え（B）が必要になった。
5. 前提 1 を確認する適合試験の結果、記録の順序が守られていないことが分かった。

## 8. 未決事項

- 受領書の照会 API を持つ外部システムの扱い（照会で保留を解けるか）。
- 予算（試行回数、照会回数）の既定値。
