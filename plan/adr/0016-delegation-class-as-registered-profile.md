# ADR-0016 委任先の信頼の水準を、管理者が登録する名前付きの等級として表す

- 状態: **採用**
- 日付: 2026-10-20
- 関連: Issue [#138](https://github.com/hat47x/eki-fabric/issues/138)、[#139](https://github.com/hat47x/eki-fabric/issues/139)、ADR-0013、ADR-0014、[Worker Assurance Model](../../requirements/ASSURANCE_MODEL.md)、[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)、RQ-015、RQ-016、RQ-019、RQ-020、RQ-023、RQ-024、RQ-047、RQ-048

## 1. 背景

ADR-0013で、EKIのコアを「委任先ごとに信頼の水準を定め、条件の合う委任先へ範囲と期限を限って仕事を任せる」仕組みと定めました。ADR-0014では、その水準と利用の許可を、管理者の権限（DLG-1）が登録することを決めました。

残っている問いは、その水準を何として表すかです。

- Assurance Modelの九つの軸（Identity、Execution Environment、Confidentiality、Result Integrity、Independence、Operational History、Resource Measurement、Verification Authority、Evidence Freshness）の組み合わせとして表すか。
- 管理者が名前を付けた段階（たとえば「社内管理端末」「専用サーバ」「協力組織」）として表すか。

軸だけで表すと、設定は厳密になりますが、管理者が日常の言葉で方針を説明できません。「この仕事は専用サーバだけに任せる」という判断を、九つの軸の値の組へ毎回翻訳する必要があります。

逆に、名前付きの段階だけを一つの数字やランクとして扱うと、Assurance Modelが明確に否定した「一本のTrust Level」に戻ってしまいます。高い段階だから結果の検証を省く、という短絡も生まれます。

このADRは、両者の利点を残す表し方を決めます。

## 2. 決定

1. 信頼の水準を、管理者が登録する名前付きの等級（**Delegation Class**、委任の等級）として表す。 等級は単一のスコアではなく、名前と版を持つ方針の記録である。名前は組織が決めてよい。EKI Coreは、普遍的な信頼の順位表を同梱しない。

2. 等級は、少なくとも次の項目を明示する。 すべてを一つの値へ畳まない。
   - 等級のIDと版。版は追記のみで、過去の版を書き換えない。
   - 委任先を識別し、実行環境を確かめる条件（Assurance ModelのAxis A、B、C、Iに対応する）。
   - 認めてよいResult Assuranceの範囲（RA-0〜RA-5）と、Confidentiality Profileの範囲（CA-0〜CA-2）。
   - 結果を確定するときに要求する検証の強さ。単独のValidatorでよいか、独立した主体による複数票を要するか、再計算やproofを要するか。
   - 委任してよいData Classの上限と、仕事の型（投げる、つなぐ、隔離して試す、住まわせる）。
   - Leaseの最大寿命、更新の可否、予算と容量の上限。
   - 根拠となるEvidenceの種類、鮮度、失効の扱い。

3. 実効の条件は、Taskの要求と等級の範囲のうち、厳しい方で決める。 等級は「ここまで任せてよい」という上限であり、Taskが要求する保証を下げる権限ではない。Taskが等級の範囲を超える保証を求める場合、その等級の委任先は使えない。Data Classの下限、検証の強さ、予算の上限を、等級を理由に緩めない。

4. 等級は、委任先の自己申告から決めない。 委任先が「自分は高い等級に属する」と申告しても、等級は変わらない。等級の割り当てはDLG-1の操作であり、根拠となるEvidenceと一緒に記録する。等級を下げる操作は、抜き取りの検証で不一致が見つかった場合に自動でもよい。上げる操作は、管理者の明示的な操作とする。

5. 等級に属さない委任先は、委任できない。 未登録を「既定の高い信頼」と解釈しない。fail closedとする。一時的な参加やBrowser Workerも、対応する等級を明示的に登録した場合だけ使える。

6. 判断は、使った等級の版へbindingする。 Placement Approval、Lease、結果の確定は、どの等級の版を根拠にしたかを記録する。後から等級の定義を変えても、すでに発行した権限の根拠を遡って書き換えない。等級の変更は、新しい権限から効く。

7. 等級どうしの比較は、軸への対応づけを通して行う。 組織をまたぐ比較や説明では、等級の名前ではなく、対応する軸・Profileの組を示す。名前だけで「こちらの方が安全」と主張しない。

8. M0とMVPは、一つの暗黙の等級で動かしてよい。 現在の`eki-control`の受理方針（全Taskで共通の上限と、利用者ごとの未完了の上限）を、等級が一つだけの状態として扱う。S1以降で、複数の等級と利用の許可を設定から移せるようにする。M0とMVPの優先順位は変えない。

## 3. 影響

### 良い点

- 管理者が「社内管理端末」「専用サーバ」「協力組織」「一時参加」といった言葉で方針を説明でき、その裏側に軸・Profile・検証の強さの対応を残せる。
- 信頼の高い委任先には検証を軽くして速く任せ、低い委任先には強い検証を要求する、というADR-0013の狙いを、設定として表現できる。
- 等級の版へ判断をbindingすることで、等級の変更が既存の権限を遡って変えない。
- 「等級が高いから結果は正しい」という読み替えを、型と原則の両方で防げる。等級は「何を確認するか」を定めるが、「何が正しいか」は証明しない。

### 悪い点と制約

- 管理者が決める項目が増える。初期設定の負担を下げるため、よくある構成の雛形を用意する必要がある。
- 等級の定義を誤って高くすると、検証が軽くなった分だけ被害が広がる。定義の変更と、高い等級への割り当ては、監査と複数人承認の対象にする必要がある。
- 等級の名前が独り歩きすると、軸への対応づけが形骸化する。説明のたびに軸を示す運用が要る。
- 組織ごとに名前と分類が異なるため、そのままでは比較できない。比較の共通語は軸・Profile側に置く。

## 4. 未決事項

- 等級の定義を、外部のContract（OpenAPI / Protobuf）でどう表現するか。管理APIの範囲。
- 等級を上げる操作に、複数人の承認を求めるか。閾値をどう定めるか（Authority Boundaries §16のmulti-party approvalと合わせる）。
- 等級の変更を、実行中のTaskや常駐のLeaseへどこまで即時に反映するか。新しいLeaseからだけか、更新時にも再確認するか。
- 等級の雛形をEKIが同梱するか、組織が必ず自作するか。
- 軸の一部だけを名前付きの段階へまとめる（たとえば「隔離実行の等級」）ことを許すか。
- 等級の妥当性を、誰が、どの頻度で抜き取り検証するか（DLG-1の運用）。
