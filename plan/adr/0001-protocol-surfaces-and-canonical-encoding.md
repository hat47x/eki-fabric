# ADR-0001 通信面ごとのプロトコルと、署名対象の正規エンコーディング

- 状態: **承認済み（MVP基準0.1向け）**
- 日付: 2026-09-21
- 対象範囲: 外部クライアントプレーン、ワーカープレーン、out-of-processのアダプタPlane、署名付きの権限判断

## 背景

EKI ファブリック（Fabric）は、未知のアプリケーション、Native ワーカー（Worker）、将来のブラウザワーカー、企業のネットワーク、複数の言語で書かれたアダプタを同時に扱う必要があります。

ところが、次の要件は一つのプロトコル技術では同時に満たせません。

- External APIは、curlなどから扱いやすく、特定の言語に依存せず、企業のプロキシと共存しやすい必要がある。
- ワーカープレーン（Worker Plane）では、ワーカーから外向きに張るセッション、ストリーミング、期限、型付きのメッセージ、効率のよいバイナリエンコーディングが欲しい。
- セキュリティに関わる認可判断（Decision）では、言語、ビルド、スキーマの進化が違っても、署名対象のバイトが一つに定まらなければならない。
- 大きな成果物（Artifact）は、RPCのメッセージへbase64で埋め込まず、データプレーン（Data Plane）でストリーム転送する必要がある。

特にProtocol Buffersの公式文書は、決定的シリアライズは正規シリアライズではないと説明しています。同じ文書は、言語やビルドが違う場合や未知のフィールドがある場合に、Protobufのバイトを安定したフィンガープリントとして使うべきではないとも述べています。

そのため、通信に使うIDLと、署名に使う正規形（canonical form）を同じものにはしません。

## 決定の要約

### 外部クライアントプレーン

**HTTPS + JSON HTTP API + OpenAPI**を基準（Baseline）とします。

- Architecture上で目標とするOpenAPI Specificationのバージョンは3.2.1とする。
- P0スキーマでは、ツールとの互換性を優先する。3.2だけにある機能へ依存しない、控えめな部分集合から始める。
- JSONボディは、厳格にパースしてからスキーマで検証する。
- HTTPのエラーボディは、RFC 9457のProblem Detailsを基本の形にする。
- 成果物の大きなバイトは、JSONへbase64で埋め込まず、データプレーンのアップロード / ダウンロードへ分ける。
- 初回MVPでは、タスク（Task）の公開状態をポーリングで取得できれば足りるとする。イベントのストリーミングは後の拡張とする。

### ワーカープレーン

**Protocol Buffers IDL + HTTPS上のConnectプロトコル**を参照トランスポートとします。

- ワーカーは、自分から外向きに接続を張る（outbound-first）。
- MVPの参照実装ではConnectプロトコルを使い、HTTP/1.1やHTTP/2の環境と共存できることを優先する。
- 同じProtobufのサービス定義から、将来gRPCやgRPC-Webとも相互運用できる構造を保つ。
- 企業のプロキシが長時間のストリーミングを通さない環境もある。そうした環境向けに、単発呼び出しやポーリングを一定回数で区切るフォールバックプロファイルを、プロトコルの意味の上で認める。
- 内部のキューやブローカのプロトコルを、ワーカーへ直接公開しない。

### プロセス外のアダプタPlane

**Protocol Buffers IDL + Connectの参照プロトコル**を基本とします。

同じプロセス内で動くGoのアダプタは、同じ論理SPIをGoのインターフェースとして実装できます。ただし、GoのインターフェースをSPIの唯一の正本にはしません。

### 署名付き権限判断

**Deterministically Encoded CBOR + CDDL + COSE_Sign1**を基準とします。

- CBORは、RFC 8949のCore Deterministic Encodingの要件を基礎にする。
- スキーマの記法にはCDDLを使う。
- 署名の外枠（envelope）にはCOSE_Sign1を使う。
- 署名アルゴリズムとキーの種類は、別のADRかセキュリティプロファイルで決める。
- セキュリティに関わるペイロードでは、原則として浮動小数点を使わない。
- タイムスタンプ、リビジョン、バイト数、予算などは、単位を固定した整数で表す。
- 未知のcriticalフィールドや、対応していない認可判断のバージョンを受け取ったら、処理を進めずに拒否する（fail closed）。

### 意味にもとづくフィンガープリント

タスクの冪等性（idempotency）の判定や認可判断との結び付けでは、受け取ったJSONのバイトやProtobufをシリアライズしたバイトを、そのままフィンガープリントにしません。

External JSONを厳格にパースし、検証し、正規化します。そのうえで、用途ごとに決めた意味上の射影（semantic fingerprint projection）を決定的CBORへエンコードし、そのバイトのハッシュを取ります。

成果物の内容を表す内容ダイジェスト（Content Digest）だけは、成果物の生のバイトそのものを対象にします。

## このように分ける理由

### External HTTP / JSON

未知のクライアント（Client）に、SDKの使用を強制しないためです。

HTTP APIには、次の利点があります。

- curlや汎用のHTTPクライアントから使える。
- ブラウザ、CLI、Python、Go、Rustなどから扱いやすい。
- 企業のプロキシ、ゲートウェイ、監視の仕組みに組み込みやすい。
- OpenAPIで、人にも機械にも説明しやすい。

OpenAPIの公式Specification一覧には、2026-09-10に公開された3.2.1が載っています。3.2系ではストリーミングのメディアタイプの記述も強化されていますが、MVPのP0ではストリーミング機能そのものを必須にしません。

### ワーカー Connect / Protobuf

ワーカープレーンでは、公開RESTの資源モデルよりも、次の性質が重要です。

- 型付きのリクエストとレスポンス
- サーバ側とクライアント側のストリーミング
- 期限
- 自動生成されるクライアント
- バイナリペイロードの効率
- メッセージの進化への対応

Connectは、Protobufのスキーマからコードを生成し、Connect、gRPC、gRPC-Webのそれぞれと互換の口を持ちます。Connectプロトコル自体は、HTTP/1.1とHTTP/2の上で動きます。

EKIの企業向けの既定構成は、外向き通信だけで動き、プロキシと共存できることです。また、将来はブラウザワーカーを持ちます。Connectはこの二つと相性がよいと判断しました。

ただし、Connectのライブラリ自体をEKI中核（Core）の意味上の契約にはしません。

トランスポートを別の実装へ替えても、ワーカー契約の意味は変わりません。

### 決定的CBOR / COSE

権限判断（Authority Decision）では、署名を検証する側が、同じ意味のペイロードから同じバイトを組み立て直せる必要があります。

RFC 8949は、決定的CBORの基本要件を定めています。

COSE_Sign1は、署名者が一人の署名付きのデータオブジェクトを標準化したものです。

CBORは64-bitの整数やバイト文字列をそのまま扱えます。そのため、JCSが前提とするI-JSONの数値の制約を、セキュリティのペイロードへ持ち込まずに済みます。

## 検討した代替案

### A. すべてをREST / JSONにする

利点は次のとおりです。

- 最も分かりやすい。
- curl、ブラウザ、プロキシと相性がよい。
- OpenAPI一つで統一できる。

採用しなかった理由は次のとおりです。

- ワーカーの長時間ストリーミングや、型付きで生成されるプロトコルには、追加の設計が必要になる。
- 署名付き認可判断の正規化を、別に解決しなければならない。
- ワーカーとの細かいバイナリのやり取りの効率が下がる。

External Planeには採用しますが、すべてのPlaneへは広げません。

### B. すべてをgRPC / Protobufにする

利点は次のとおりです。

- 成熟したRPCである。
- 双方向ストリーミングがある。
- 多くの言語向けにコードを生成できる。
- バイナリエンコーディングが効率的である。

採用しなかった理由は次のとおりです。

- 公開APIを使う未知のクライアントに、gRPCのツールチェーンを求めたくない。
- ブラウザやプロキシの環境では、gRPC-Webやゲートウェイの追加検討が要る。
- Protobufのシリアライズは、暗号用の正規形ではない。

ワーカープレーンとアダプタPlaneの候補としては利用します。

### C. すべてをConnect / Protobufにする

利点は次のとおりです。

- HTTPと相性がよい。
- ブラウザと相性がよい。
- gRPCと互換性がある。
- クライアントを自動生成できる。

採用しなかった理由は次のとおりです。

- 公開資源APIが、特定のRPCの生態系へ寄りすぎる。
- OpenAPIや素のHTTPとの統合を、第一級のまま保ちたい。
- 暗号用の正規化の問題は残る。

### D. 署名付き認可判断にJSON + JCSを使う

JCS（RFC 8785）はJSONの正規表現を定めており、有力な候補でした。

採用しなかった理由は次のとおりです。

- I-JSONとIEEE 754の倍精度の制約を、セキュリティに関わる数値フィールドへ持ち込むことになる。
- バイト文字列や大きな整数を、文字列へ変換して表す必要がある。
- 内部の権限主体（Authority）ペイロードでは、通信路上で人が読めることの必要性が低い。

Externalリクエストのログや比較の用途には使えますが、基準の署名エンコーディングには採用しません。

### E. Protobufの決定的なバイトに署名する

採用しません。

Protobufの公式文書は、決定的シリアライズと正規シリアライズをはっきり区別しています。そして、言語、ビルド、スキーマの進化をまたいだ汎用のフィンガープリントとして使うことを推奨していません。

## External クライアント APIのプロファイル

### HTTP

- TLSで保護したHTTPSを使う。
- 最低限の互換性としてHTTP/1.1を認める。
- HTTP/2を使える。
- HTTP/3はMVPでは必須にしない。

### JSON

External JSONに対しては、次の処理を行います。

- 重複したプロパティを拒否する。
- ボディの最大サイズを制限する。
- 入れ子の最大の深さを制限する。
- 文字列、配列、メタデータの最大数を制限する。
- 整数の範囲を検証する。
- 未知の中核フィールドを拒否する。

JSONのnumberが任意の精度の整数を表せるとは期待しません。

セキュリティや予算の都合で64-bitの精度が必要なフィールドは、スキーマ上で範囲を明示します。必要であれば、10進の文字列のような明示的な表現を使います。

### OpenAPI

API記述の正本として目標とするのはOpenAPI 3.2.1です。

ただし、2026-09の時点で3.2.1は新しいため、P0では次の控えめな部分集合を使います。

- 通常のJSONのリクエストとレスポンス
- 標準のHTTPメソッド
- 3.2にしかないストリーミングの構文を必須にしない

ツールチェーンが3.2.1を処理できない場合に備えて、元の意味のスキーマを弱めずに、3.1互換の派生物を生成できる余地を残します。

### エラー

HTTPのエラーは、RFC 9457の`application/problem+json`を基本にします。

EKI固有の拡張として、次の項目を追加できます。

- 安定したエラーコード
- 開示しても安全な範囲での、タスクや試行（Attempt）との対応付け
- リトライできるかどうかの分類
- ポリシーによる拒否理由の分類

`detail`の文字列を、機械側の処理の判断に使わせません。

## ワーカープレーンのプロファイル

### Protobuf

Protobufは、ワーカープレーンのIDLと、通信するメッセージの形式として使います。

用途は次のとおりです。

- WorkerHello
- ResourceAdvertisement
- WorkOfferと作業指示書（WorkOrder）の運搬
- WorkOrderAck
- Heartbeat
- LeaseRenewalRequestとその結果
- ResultClaimの運搬
- StopとReclaimの通知

セキュリティに関わる権限判断の、署名対象そのものには使いません。

### Connect

参照トランスポートはConnectです。

理由は次のとおりです。

- 標準的なHTTPの基盤に載せやすい。
- HTTP/1.1とHTTP/2を扱える。
- gRPCやgRPC-Webの生態系と相互運用する道がある。
- ブラウザワーカーへ広げやすい。
- Goのnet/httpと軽く統合できる。

### セッションの方式

MVPでは次の二つの方式を認めます。

1. ストリーミングセッション
2. ポーリングまたは単発呼び出しによるフォールバック

どちらの方式でも、次の値は同じにします。

- 作業指示書 ID
- 試行 ID
- リース（Lease）リビジョン
- 重複して届いたときの扱い

通信の方式によって、状態の意味を変えません。

## 大きな成果物のプロファイル

成果物のバイトはRPCのメッセージに入れません。

制御プレーン（Control Plane）のAPIでアップロード意図（Upload Intent）やArtifactGrantを取得し、データプレーンのエンドポイントへ転送します。転送には`application/octet-stream`や、アダプタごとのマルチパート転送、再開可能な転送方式などを使います。

内容ダイジェストは、成果物の生のバイトを対象にします。

圧縮する場合は、保存した識別子が圧縮後のバイトを指すのか、展開した論理上のバイトを指すのかを、成果物のMediaやProfileで明示します。

アーカイブを展開した後の中身を、元の成果物のDigestと取り違えません。

---

## 署名付き認可判断のプロファイル

### ペイロード

認可判断のペイロードは、決定的CBORでエンコードします。

### スキーマ

各バージョンで認めるマップ、フィールド、型をCDDLで定義します。

### 外枠

COSE_Sign1を使います。

保護されたメタデータでは、少なくとも次の項目を扱える構造にします。

- アルゴリズムの識別子
- キーの識別子
- 内容または認可判断の種類

権限主体 ID、判断の種類（Decision Kind）、スキーマのバージョンは、署名で保護される意味の中に必ず含めます。

### 暗号アルゴリズム

このADRでは固定しません。

次の観点を、別のセキュリティプロファイルで比較するためです。

- 企業のPKIやKMSとの適合性
- プラットフォームが対応する暗号
- アルゴリズムを後から替えられること
- 現行の標準

ワーカーが、クライアントからの入力に従ってアルゴリズムを選ぶ構造にはしません。

---

## フィンガープリントのプロファイル

冪等性の判定や結び付け用のダイジェストには、用途ごとの射影（Projection）を定義します。

たとえば次のようなものです。

```text
TaskRequestFingerprintV1
  principal scope
  logical executor
  normalized inputs
  normalized params
  resource request
  reliability semantics
```

External JSONの次のような違いでは、フィンガープリントが変わらないことを目指します。

- 空白
- オブジェクトのプロパティの順序
- 同じ意味になる表記の違い

一方で、未知のフィールド、省略されたフィールド、既定値のフィールドは、意味が違うことがあります。これらを誤って同じものとみなさないよう、Projectionのバージョンを固定します。

---

## パーサのセキュリティ境界

External JSONのパーサ、Protobufのデコーダ、CBORのデコーダは、いずれも攻撃を受ける入口です。

共通して次の制約を求めます。

- メッセージの最大バイト数
- 入れ子の最大の深さ
- 繰り返しフィールドの数の上限
- 文字列とバイトの長さの上限
- 展開後のサイズの上限
- 際限なく再帰する拡張を認めない
- 未知のcriticalな意味を拒否する
- パーサのパニックの隔離とファジング

---

## 圧縮

Controlメッセージの圧縮は任意です。

圧縮爆弾（展開すると巨大になるデータ）を避けるため、次の制約を適用します。

- 圧縮後のサイズの上限
- 展開後のサイズの上限
- 対応するアルゴリズムの許可リスト
- 入れ子になった透過的な圧縮を認めない

大きな成果物の圧縮は、成果物のプロファイルとSafe Processing Budgetで別に扱います。

---

## 互換性のルール

### External API

- 任意で追加されるフィールドは、小さな変更の候補とする。
- 意味を変える場合は、バージョンを上げる。
- MVPの厳格モードでは、未知の中核フィールドを拒否する。
- 名前空間付きの任意の拡張だけを、前方互換として扱う。

### Protobuf

- フィールド番号を再利用しない。
- 削除したフィールドは予約済みにする。
- セキュリティ認可判断では、未知の列挙値を、権限を与えない側の値として処理する。
- セキュリティに必須の意味を、未知のフィールドに持たせない。

### 署名付きCBOR 認可判断

- 認可判断のスキーマのバージョンを必須にする。
- 未知のフィールドの扱いを、バージョンごとに定義する。
- セキュリティに関わる未知の要素は拒否する。
- 署名済みの古いバージョンを、知らないうちに別の意味で解釈しない。

## 影響

### 良い点

- External クライアントは特定のSDKに依存しない。
- ワーカープレーンは型付きで、ストリーミングを扱いやすい。
- 将来のブラウザワーカーで、同じProtobufのサービスモデルを使い回しやすい。
- 署名付き認可判断が、Protobufのシリアライズの安定性に依存しない。
- Controlのメタデータと大きなデータが分かれる。
- 特定の言語に依存しない性質を保ちながら、Goの参照実装を簡潔にできる。

### コスト

- JSON、Protobuf、CBORの3つのデータ表現を扱う必要がある。
- 意味のモデルと通信路上のモデルの間の変換をテストする必要がある。
- CDDLとCOSEのツールチェーンが加わる。
- どのスキーマを正本とするかの管理ルールが必要になる。

署名のバイトと、公開APIやワーカーの使いやすさを、一つの形式へ無理に押し込むことはしません。この複雑さを抱える方が、それより明示的だと判断しました。

## 必須の適合性テスト

### JSON / OpenAPI

- 重複したプロパティ
- 未知の中核フィールド
- 数値の境界
- 大きすぎるボディ
- 不正なUTF-8と文字列の制約
- 意味上のフィンガープリントの安定性

### Protobuf / Connect

- 未知の列挙値に対するセキュリティ上の振る舞い
- 重複した配送
- ストリームの再接続
- HTTP/1.1でのフォールバック
- メッセージのサイズの上限
- 期限とキャンセル

### CBOR / COSE

- 決定的でないエンコーディングを拒否するか、正規の形に再エンコードするかの方針
- マップの重複したキー
- 誤った判断の種類
- 誤ったキーIDや権限主体
- 改変されたペイロード
- 古いバージョン
- 未知のcriticalフィールド
- 署名アルゴリズムの許可リスト
