# ADR-0021 観測の面を権限の状態から分け、開示を三段階に分ける

- 状態: **採用**
- 日付: 2026-10-21
- 関連: Issue [#109](https://github.com/hat47x/eki-fabric/issues/109)、[#112](https://github.com/hat47x/eki-fabric/issues/112)、[#145](https://github.com/hat47x/eki-fabric/issues/145)、[ADR-0013](0013-product-core-and-faces.md)、[ADR-0014](0014-authorities-for-delegation-budget-capacity.md)、[Control / Data Plane](../../architecture/CONTROL_DATA_PLANE.md)、RQ-008、RQ-018、RQ-039、RQ-040、RQ-051、RQ-057、RQ-058

## 1. 背景

ADR-0013で、EKIに管理画面を持たせ、全資源プールと仕事の状況を横断して見られるようにする方向を定めました。RQ-058では、委任先ごとの運用の実績（予実）を、Control Planeが自分で観測した出来事から作ること、開示を利用者、委任先の管理者、Fabric全体の管理者で段階に分けることを求めました。RQ-057では、資源の消費を物理量で記録することを求めました。

これらの情報は量が多く、集計の負荷も高く、管理画面から頻繁に読まれます。権限の判断に使う状態（Task、Lease、Fence、Policyの版、予算の予約）と同じ保存先に置くと、次の問題が起きます。

- 管理画面の集計が、受理やLeaseの処理を遅らせる。
- 観測の保存先が壊れると、権限の判断まで止まる。
- 観測の値が、権限の判断の根拠に紛れ込む。

また、TEIの投影Spike（#112）で、ビルドキャッシュの有無で約15倍の時間差が出たように、配置の費用の入力が足りていませんでした。

## 2. 決定

1. Control / Data Planeに、観測の面（Observation Plane）を加える。観測の面は、予実、資源の消費の記録、仕事と枠の一覧、端末と委任先の状況を扱う。
2. 観測の面には、Control Plane、Data Plane、Workerから一方向に書き出す。権限の判断に使う状態とは、保存先を分ける。観測の保存先が使えなくなっても、受理、配置の承認、Lease、結果の確定は影響を受けない。
3. 観測の値は、Authorityを持たないObservationである。Schedulerや広域の最適化は入力に使えるが、委任の等級、予算の権限、結果の確定の根拠にはしない。Workerが申告した値は、申告であることを示して保持する（Assurance ModelのAxis G）。
4. 予実は、Control Planeが自分で観測した出来事（受理、配置、ResultClaimの受信、Leaseの失効、検証の不一致）から作る。
5. 資源の消費は、依頼ごとに、物理量と観測者を付けて記録する。金額への換算は、観測の面の外（会計の仕組み）で行う。
6. 開示を三段階に分ける。利用者は、自分の依頼の状態と、等級ごとの見込みだけを見る。委任先の管理者は、自分の委任先の予実と負荷を見る。Fabric全体の管理者は、全体を見る。どの段階でも、依頼の中身（入力のArtifact）は、Data authorityを別に持たない限り見せない。
7. 管理画面は、観測の面と、読み取り専用の照会だけを読む。予算の付与、委任先の停止などの操作は、管理者権限の経路（Administrative Plane）を通し、閲覧とは別の権限とする。管理画面はEKIに依存しない場所で動かし、EKIが止まった場合のためにCLIによる最小の運用手段を残す。
8. 配置の費用の入力に、ビルドキャッシュ、toolchain、依存モジュールの局所性、温めた枠（SessionとSandbox）の空き、費用を生む容量の費用の区分と予約の状況、委任先の予実の見込みを加える。toolchainと依存は、Workerが実行中に取得するものではなく、事前に配置するArtifactとして扱う（RQ-029）。
9. Control / Data PlaneをBaseline 0.2へ上げる。これで、設計基準の6文書はすべて0.2になる。

## 3. 移行

- M0とMVPの優先順位は変えない。いまの`eki-control`は、1要求ごとに一行のログを出すだけで、メトリクスの出口がない。観測の面は、MVP計画のM4（OTLP）を出発点に実装する。
- 小さな構成（DP-1、DP-7）では、観測の保存先を同じ機械の別のfileにしてよい。保存先と書き込みの権限は分ける。

## 4. 影響

### 良い点

- 管理画面の集計と、権限の判断の処理が、互いに影響しない。
- 観測の値が権限の根拠に紛れ込む経路を、設計の段階で閉じられる。
- 予実と消費の記録の置き場所が決まり、広域の最適化（#140）と予算の執行（#142）の入力が揃う。

### 悪い点と制約

- 保存先が一つ増える。観測の面の記録と、権限の状態の記録が食い違った場合は、権限の状態を正とする。
- 観測の面は一方向の書き出しなので、取りこぼしが起こり得る。予実は見込みであり、正確な台帳ではない。

## 5. 未決事項

- 予実の見込みを、利用者にどの程度の精度で返すか（精度を上げるほど、内部構成が推測しやすくなる）。
- 観測の面の保持期間と、集計の粒度。
- 分散認知としての利用で何を測るか（[プロダクトの外面とコア](../../research/topics/product-scope-direction.md)の候補）を、Quality AttributesとADR-0008でどう採るか。
