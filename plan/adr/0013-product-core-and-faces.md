# ADR-0013 EKIのコアを信頼の水準に応じた「委任の核」と定め、その上に四つの外面を置く

- 状態: **採用**
- 日付: 2026-10-20
- 関連: Issue [#137](https://github.com/hat47x/eki-fabric/issues/137)、[プロダクトの外面とコア](../../research/topics/product-scope-direction.md)、[Product Value](../../product/value.md)、ADR-0009、ADR-0010、RQ-001、RQ-004、RQ-005〜007、RQ-014〜019、RQ-023、RQ-031、RQ-039、RQ-047、RQ-048、RQ-051

## 1. 背景

EKIは「遊休資源と管理クラスタを扱う分散計算基盤」として企画されてきました。この企画には三つの弱点がありました。

- 分散が導入の前提になっていた。分散が不利な場面（RQ-014）では、EKIを使う理由そのものが消えていた。
- 推論の呼び出し、AIが生成したコードの実行、常駐する認知処理が、目標外としてEKIの統治の外に残っていた。AIの時代の計算の多くは、まさにこれらの流れを通る。
- 設計の重心が「信頼しない相手」の守りにあり、信頼の水準が高い委任先（自組織の専用サーバなど）へ速く任せることや、資源の全体を最適に使うことを、価値として表していなかった。

TEIは、ローコード開発基盤という外面の下に、プラグイン機構というコアを持ちます。EKIも、利用者が導入する理由になる外面と、どの外面からも共通に使われるコアを分けて定める必要があります。

## 2. 決定

1. EKIのコアを「委任の核」と定める。委任の核とは、委任先ごとに信頼の水準を定め、仕事の条件とその水準が合う委任先へ、範囲と期限を限って仕事を任せ、結果を確かめて記録する仕組みである。次の要素から成る。
   - 委任先と信頼の水準を定める（管理者が根拠とともに定める。自己申告や評判だけを根拠にしない）
   - 依頼を受ける（内容を検証してから、予算と方針の範囲で受理する。委譲の連鎖でも予算は縮む）
   - 委任先を決める（目的による指名、またはEKIによる自律的な選択）
   - 範囲と期限のある権限を渡す（署名付きのLeaseとfencing）
   - 資源の持ち主が拒める（Local Governor）
   - 申告と確定を分ける（委任先の信頼の水準に応じた検証を経て確定する）
   - 経緯を残し、取り消せる（来歴と、失効に伴う結果の洗い出し）
   - 資源を最適に活かす（持ち主が許した余力、管理資源、クラウドの自動拡張を、予算と期限の範囲で全体として最適に使う）
   - 提供の事実を記録する（Contribution Record）
2. 信頼の原則を言い直す。「ClientもWorkerも信頼しない」を、「暗黙には信頼しない。信頼は委任先ごとに、管理者が根拠とともに明示して定める」と言い直す。Principle 1、10とRQ-015、RQ-019、RQ-023、RQ-047の内容は変えない。信頼の水準が高い委任先には、検証を軽くして任せられる。
3. 委任先の決め方を二通りとする。
   - 指名: 仕事の目的に応じて、管理者が登録しその利用者に許した委任先（資源のプール、資源提供者）を指名する。指名は許された範囲を狭める操作であり、予算、Data Class、信頼の水準の要求を緩めない。個々のWorker、hostname、IPアドレスは引き続き指定できない（RQ-016）。
   - 自律: 指名しない場合、EKIは、その依頼に許されたすべての委任先から、条件を満たし全体として最適な委任先を選ぶ。持ち主の拒否権、Compute Grantの範囲、予算は、自律の判断より優先する。選んだ理由は記録する。
4. 広域の資源最適化を価値の柱とする。持ち主が許した余力、管理資源、クラウドの自動拡張と予算を一元的に管理し、取りこぼさずに活かす。最適化の判断は提案であり、配置の権限が信頼の水準、Data Class、予算、持ち主の上限を確かめてから承認する。「すべての資源を常に最大限まで使うことは目標にしない」という非目標は、「持ち主が許した範囲を超えて使い切ることは目標にしない」と言い分ける。
5. 分散はコアの使い道の一つとする。委任の核は、一台のコンピューターの中でも使える。導入の入口を分散処理に限らない。一台で完結する配備形態を用意する。
6. 外面を四つに広げる。どの外面も同じ委任の核を通る。
   - 広域の資源最適化と分散計算（仕事の型: 投げる）
   - AIの推論とツール実行の統治（仕事の型: つなぐ）
   - AIが生成したコードの隔離実行（仕事の型: 隔離して試す）
   - 常駐する軽量な認知処理の実行面（仕事の型: 住まわせる）
7. 常駐は「存在は終わらないが、権限は有限」として扱う。常駐する処理には、期限つきで更新されるLeaseの連なりとして権限を渡す。更新のたびに予算、方針、失効を確かめ、fencingの番号を進める。業務端末では、持ち主がいつでも止められる。EKIに住まわせるのは、止められても利用側の正しさが失われず、状態の正本を持たない常駐に限る。可用性の約束や状態の正本を持つ業務アプリケーション本体は、引き続き既存のオーケストレータに任せる。これはADR-0009の決定4（終わりのない常駐サービスは対象外）を、この条件の範囲で改める。
8. 核は自前で持ち、部品は外部のOSSと連携する。権限や受理を決めるもの、端末を守る判断、委任先と信頼の水準の定義は、自前で持つ。推論エンジン、隔離実行の仕組み、LLMのゲートウェイ、ビルドの遠隔実行、クラスタの管理、クラウドの自動拡張、ワークフロー、識別、観測は、拡張SPIのAdapterとして連携する。特定のOSSを核の必須の依存にしない。一つの領域で、性質の異なる二つ以上の連携先で契約が成り立つことを確かめてから、EKIの契約と呼ぶ。
9. 利用側の意味は、引き続き持たない。「軽量認知基盤」と呼ぶ外面でも、EKIは認知の意味、エージェントの計画、ワークフローの意味、業務モデルを持たない（Principle 7）。
10. 組織レベルの意思決定は、SEIに委任された管理者権限として受ける。将来は、全社・全組織の資源管理を一元化し、SEIの生成AIによる組織機能と連動した自動のオーケストレーションを目指す。EKIのオーケストレーションには、SEIによる組織レベルの意思決定（部門間の優先度、予算の配分、引き上げの方針など）を入れる。SEIは、人間の管理者から管理者権限の一部を範囲と期限を限って委任された委任先であり、その決定は署名されたPolicyの版として管理者権限の経路で入る。Clientの依頼の経路では入らない。SEIの委任された権限では、Data Classの下限を下げること、持ち主の拒否権を上書きすること、Federationを広げること、人間が定めた予算の総額を超えることはできない。影響の大きい変更は人間が承認する。SEIが止まった場合は、期限内の最後の有効なPolicyで動き続け、期限が切れたら人間が定めた既定値へ戻る。Local Governorの判断はSEIを待たない。
11. M0とMVPの優先順位を変えない。核の縦断スライスを先に通し、外面は段階的に足す。段階の案は調査メモ§12にある。

## 3. 影響

### 良い点

- 分散が不利な場面や、遊休資源がない環境でも、EKIを導入する理由が残る。
- 信頼の水準が高い委任先には速く任せ、低い委任先にも条件の合う処理を任せられる。信頼の幅全体を一つの仕組みで扱える。
- 指名しない依頼をEKIに委ねることで、余力、管理資源、クラウドを予算の範囲で取りこぼさずに活かせる。
- AIの推論、エージェントのコード実行、常駐の認知処理が、信頼の水準、Data Class、予算、来歴の統治の内側に入る。
- 外面を増やしても、核の負担は増えにくい。増えるのは入口とAdapterである。
- 組織レベルの意思決定をSEIから受けられる。それでも、SEIの誤りや停止が、端末の保護や配置の権限まで及ばない。

### 悪い点と制約

- 原則と目標外の一部を言い直すため、`product/value.md`、`product/principles.md`、Product Requirementsの非目標とRQ-016、既存の調査メモの記述を合わせる必要がある。要件の変更は、GitHub Issueで個別に扱う。
- 信頼の水準を誤って高く定めると、検証が軽くなった分だけ被害が広がる。水準の定義と失効（#122）を、管理者権限の操作として監査する必要がある。
- 自律的な選択では、利用者に「どこで動いたか」をどこまで示すかと、内部構成を列挙させない要求（RQ-018）の釣り合いを決める必要がある。
- 常駐を扱うことで、業務端末での人の優先との釣り合いを新たに決める必要がある。
- 外部のOSSの寿命と安全性に影響を受ける。版の固定、署名と来歴の確認、Adapterの差し替えを前提にする。

## 4. 未決事項

- 信頼の水準を、Assurance Modelの軸の組み合わせで表すか、管理者が名前を付けた段階で表すか。
- 外面ごとの型を、Requirementとしてどの粒度で書くか。
- 自律的な選択で、利用者へどこまで開示するか。
- 一台で完結する配備形態を、Deployment Profileのどこに置くか。
- 常駐の更新の判断を、どの権限が行うか。業務端末に常駐をどこまで許すか。
- 委任の核を、TEIのプラグイン機構の権限のleaseと共通化する余地があるか。
- SEIに委任する管理者権限の範囲と、人間の承認を求める変更の境界。
