# ADR-0023 EKIの自律の判断の範囲と、外部の要求に応える五つのインターフェース

- 状態: **採用**
- 日付: 2026-10-21
- 関連: Issue [#145](https://github.com/hat47x/eki-fabric/issues/145)、[ADR-0013](0013-product-core-and-faces.md)、[ADR-0014](0014-authorities-for-delegation-budget-capacity.md)、[ADR-0021](0021-observation-plane-and-disclosure-tiers.md)、[ADR-0022](0022-mandate-operation-classes-and-thresholds.md)、[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)、[Contract Boundaries](../../architecture/CONTRACT_BOUNDARIES.md)、RQ-016、RQ-018、RQ-039、RQ-059、RQ-061

## 1. 背景

ADR-0013の決定11で、EKIは自身の判断で自律的にオーケストレーションしつつ、SEIや人間の外部の要求に応えるインターフェースを持つことにしました。要求は、依頼、方針、照会、承認、通知の五種類です。

決まっていなかったのは、次の二点です。

- EKIが、人間に尋ねずに自分で判断してよい範囲はどこまでか。
- 五種類の要求を、外部契約の上でどう表すか。特に、承認と通知の形と、受けられない依頼に何を返すか。

ADR-0022で、管理の操作を四つの区分（安全側、範囲内の拡大、人間の承認、委任できない）に分けました。EKI自身の自律の判断も、同じ考え方で分けられます。

## 2. 決定

1. EKIの自律の判断を、次の三つに分ける。

   | 区分 | 例 |
   | --- | --- |
   | 承認なしで行う | 自律に委ねた依頼の委任先の選択、待っている仕事や中断してよい仕事の配置し直し、予算の範囲での枠の事前の温め、閾値以下の容量の確保と解放、内部の需要が増えたときの外部への提供の縮小（方針が許す場合）、抜き取りの検証で不一致が出た委任先を一時的に候補から外すこと、失効に伴う再実行の候補づくり |
   | 人間の承認を求める | 閾値を超える容量の確保、ADR-0022で「人間の承認が要る操作」とした操作 |
   | 行わない | ADR-0022で「委任できない操作」とした操作。副作用のある仕事の自動の再実行 |

   どの判断も、委任の核の中で行い、最適化は提案、配置の権限が承認する構造（Authority Boundaries §3.2）を変えない。自律の判断は、理由とともに記録する（RQ-039）。

2. 外部の要求を、次の五つのインターフェースとして表す。経路ごとに権限が違う。

   | 種類 | 経路 | 要点 |
   | --- | --- | --- |
   | 依頼 | Client Plane | いまのTask API。入口（MCPなど）も同じ意味に写す（ADR-0019） |
   | 方針 | Administrative Plane | 人間の管理者か、委任状を持つ主体が出す。出どころ（人間か、どの委任状か）を必ず記録する |
   | 照会 | 読み取り専用の経路 | Observation Planeから答える。開示の段階に従う（ADR-0021）。見込みは見込みと示す |
   | 承認 | Administrative Plane | 承認の要求を一件の記録として出す。人間の管理者のcredentialでだけ承認できる |
   | 通知 | EKIから外部へ | 受け手の権限に応じて内容を絞る。通知そのものは権限を持たない |

3. 承認の要求は、提案した主体（EKIの自律の判断か、委任状を持つ主体か）、操作、影響の要約、承認の期限を持つ。期限までに承認されなければ、承認されなかったものとして扱う。承認を待つ間、操作は有効にならない。
4. 通知は、少なくとも、期限に間に合わない見込み、外部への提供の縮小、結果の取り消し、委任状の期限切れと既定の方針への切り替え、承認の要求を扱う。通知は、届かないことや二度届くことがある。受け手は、通知を受けたら照会で現在の状態を確かめる。通知の内容を権限や事実の根拠にしない。
5. 受けられない依頼や、期限に間に合わない見込みの依頼には、理由と、拘束力のない代わりの案（期限を延ばせば余力で間に合う、等級を変えれば受けられる、など）を返せる。代わりの案は自動では適用しない。依頼者が新しい依頼として出し直す。代わりの案から、内部構成を推測できる情報を出さない（RQ-018）。
6. Authority Boundariesに§7A（EKIの自律の判断の範囲）を、Contract Boundariesの§31と§33に代わりの案、方針の出どころ、承認の要求、照会、通知を加える。版は0.2のままとし、追記の日付を記す。

## 3. 移行

- M0とMVPの優先順位は変えない。依頼のインターフェースは、いまのTask APIのままでよい。方針、照会、承認、通知は、ADR-0013の段階のS4（広域の最適化）以降で実装する。

## 4. 影響

### 良い点

- EKIが人間に尋ねずに判断してよい範囲が、ADR-0022の委任状の区分と同じ考え方で決まる。SEIへの委任とEKI自身の自律を、一つの基準で説明できる。
- 承認と通知の形が決まり、案件の予算の執行（#142）と外部への提供（#143）を設計できる。
- 受けられない依頼に代わりの案を返すことで、利用者が「EKIに投げる」だけで次の手を選べる。

### 悪い点と制約

- 承認を待つ判断が多いと、自律の利点が減る。閾値の調整が運用の要になる。
- 通知は届かないことがあるため、受け手は照会を併用する必要がある。

## 5. 未決事項

- 承認の要求の期限の既定値と、承認する人の役割（multi-party approvalと合わせる）。
- 通知の配送の手段（webhook、メッセージ、SEIへの連携など）。
- 代わりの案の形式と、どこまで具体的に示すか。
