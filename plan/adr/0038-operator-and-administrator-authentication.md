# ADR-0038 Operator と Administrator の認証と権限

- 状態: 提案中（**仮承認**。利用者の包括承認 2026-11-03 による）
- 日付: 2026-11-03
- 関連: ADR-0036（Trust Bundle の承認）、#433、#494、#505

## 1. 問題

EKI には、Worker でも External Client でもない**人の役割**があります。

- **Operator**: Trust Bundle の版を承認する（発行者の追加・削除）。ADR-0036 §3 は「操作者の承認」を要求していますが、その操作者が誰で、どう認証されるかを決めていません。
- **Administrator**: Worker の登録、Principal の管理、保持期間のような配備の設定を扱います。

いまはこの2つの役割の入口がありません。Trust Bundle の承認は記録の形（`Approval`）だけが決まっており、承認者が本人かどうかを確かめる手段がありません。**誰でも `approved_by` に名前を書けるなら、承認は記録の装飾になります。**

## 2. 決定

**Operator と Administrator は、専用の認証局（Operator CA）が発行したクライアント証明書で認証します。** 役割は証明書に入れます。

- **別の認証局にする。** Worker の CA（`workerca`）と Operator の CA を分けます。理由は**被害の範囲**です。Worker の CA が漏れても、Trust Bundle の発行者を書き換えられてはいけません。逆も同じです。
- **役割は証明書の URI SAN に置く**（例: `eki://example.org/operator/alice` と `eki://example.org/role/operator`）。拡張領域ではなく既存の形（`workercert.ParseURI`）に合わせられます。
- **EKI は Operator の身元を、証明書の名前からだけ取ります。** リクエスト本文の `approved_by` は**使いません**（記録のために受け取りますが、証明書の名前と一致しなければ拒否します）。
- **2つの役割は別のことを許されます。**
  - Operator: Trust Bundle の承認、承認の取り消し、版の一覧の閲覧。
  - Administrator: Worker の登録・失効、Principal の管理、保持期間の変更、監査の閲覧。
  - **Operator は Principal を管理できず、Administrator は Trust Bundle を承認できません。** 1つの証明書に両方の役割を入れることは**できません**（実装で拒否します）。
- **両方の役割に、すべての操作の監査を要求します。** 誰が・いつ・何を・どの対象に・結果。成功だけでなく拒否も残します（成果物の監査と同じ理由、#494）。
- **Operator CA が設定されていないプロセスでは、Operator の経路は存在しません**（404）。「認証が無いから通す」経路を作りません。

## 3. なぜ mTLS か（OIDC ではなく）

- EKI の Control Plane はすでに mTLS を持っており（ADR-0027）、証明書の発行・更新・失効の運用があります。Operator のために別の仕組み（OIDC プロバイダ、トークン検証、鍵の管理）を増やすと、**守るべき入口が2種類**になります。
- Operator は人数が少なく、高い権限を持ちます。「業務端末のブラウザから操作する」必要がまだありません。
- **将来 OIDC を足す余地は残します。** 認証の結果を `Identity{Principal, Role}` に落とす層を分けているので（既存の `Authenticator`）、OIDC の実装を差し替えで足せます。**契約（役割の意味と監査の項目）は変えません。**

## 4. 何を保証しないか

- **証明書の失効は、次の接続から効きます。** 接続中のリクエストは取り消せません（Worker の mTLS と同じ性質）。
- **Operator の操作を、別の Operator が承認する仕組み（4-eyes）は入れません。** Trust Bundle の変更は「承認の記録」を要求しますが、同じ人が2回承認しても通ります。必要になったら足します。
- **端末の安全は保証しません。** Operator の鍵が端末にある以上、端末が乗っ取られれば Operator になります。

## 5. 未決

- Operator CA の運用（誰が発行するか、何年で更新するか、失効の配布）。
- 監査の保存先（ファイル、SIEM、DB）と保持期間。
- Administrator の操作を**複数人**で承認する要求を足すか（本番配備では検討する）。
- OIDC を採る配備のための契約（スコープ名、トークンの検証）。

## 6. 署名鍵の置き場所（2026-11-03）

版に署名する鍵は、**Administrator の手元にだけ置き、Control Plane は持たない**。

- Control Plane が持つのは**公開鍵（鍵指紋）だけ**。`POST /v1/admin/trust-bundles` は、提出された署名をその公開鍵で検証し、承認が揃っていれば受理する。
- 秘密鍵を Control Plane に置くと、**プロセスが乗っ取られた時点で「信頼の根を書き換える」権限まで奪われる**。署名を手元に残せば、乗っ取りでできるのは「署名の検証をすり抜ける」ことではなく、**受理を止める**ことまでにとどまる（fail closed 側に倒れる）。
- 引き換えに、版の作成は**手作業の運用**になる。頻度が低い操作なので許容し、自動化が必要になったら別の仕組み（HSM など）を検討する。

**未決**: 鍵の更新（Administrator の交代時に、公開鍵をどう入れ替えるか）。
