# ADR-0031 端末で実行する単位を決め、資源は予約の合計で判定する

- 状態: **提案中**
- 日付: 2026-11-01
- 関連: Issue [#354](https://github.com/hat47x/eki-fabric/issues/354)、[#351](https://github.com/hat47x/eki-fabric/issues/351)、[#296](https://github.com/hat47x/eki-fabric/issues/296)（項目4を#354へ）、[#316](https://github.com/hat47x/eki-fabric/issues/316)、[ADR-0017](0017-start-and-stop-authority.md)、[ADR-0025](0025-lease-policy-currentness-and-key-rotation.md)、[ADR-0030](0030-assignment-delivery-pull-and-lease-currentness.md)、`architecture/TASK_STATE_MODEL.md`

## 1. 背景

### 1.1 いまの動作

Agentは、Control Planeから受け取った割当を**1件ずつ、順番に**実行します。`runAssignments`（`internal/agent/service/assignments.go`）はpollごとに`Service.Poll`を呼び、`Handler.Start`を同期で実行します。実行が終わるまで次のpollは始まりません。heartbeat（ADR-0030 §2.2）も「いま実行中のLease」を1件だけ報告する形で、`leaseReporter`のコメントに「the Agent runs one Handler at a time」と書いてあります。

開始の関門（`startgate.Gate.Check`）は、Control PlaneがWorkOrderで認めた上限、Local Governorの割合、`MachineProfile`（端末の全容量）の3つから、実効の上限を決めます。ここには**他の実行が使っている分**が入りません。

### 1.2 何が問題か

1件ずつ実行している間は、この2つは同じ結果になります。問題は、同時実行を入れた瞬間に現れます。

- 2件の割当がそれぞれ機械の60%を要求していても、両方が関門を通ります。合計120%を1台で走らせることになります。端末の持ち主の資源を守るという約束（RQ-005、RQ-006、ADR-0017）に対して、判定が誤ります。
- 逆に、合計が上限を超えるときに「どちらを待たせるか」を決める場所がありません。2件目は`deferred`にも`rejected`にもならず、単に実行が遅れます。待っている割当のLeaseの期限は進みます。
- Control Planeは、Workerの受け入れ能力を知りません（`internal/control/dispatch`はTaskとWorkerを選ぶが、容量の申告を受け取らない）。配置は進み、Leaseの期限だけが過ぎます。
- heartbeatが1件のLeaseを報告する形なので、同時に2件走らせると、報告の形が実態と合いません。

単純な方法（同時実行を許し、実行のたびに空きを計算する）では足りません。空きを計算するには「いま何がどれだけ予約しているか」を知る必要があり、その記録が無いからです。実測（実際に使ったCPUやメモリ）では代用できません。実測は実行を始めた後でしか分からず、始める前の判断には使えないからです。

### 1.3 用語

- **実行slot**: この端末で同時に走らせてよい実行の枠。1つのslotに1つのAttemptが入ります。
- **予約（reservation）**: 実行を始めるときに、そのPlanのlimitsを「この端末で使う」と記録したもの。実行が終われば解放します。
- **関門（start gate）**: 予約とGovernorの判断から、この割当をいま始めてよいかを決める検査。

## 2. 決定

### 2.1 参照実装のAgentは、実行slotを1つ持つ。同時実行は明示的な設定でのみ許す

参照実装のAgentの実行slotは**1**とします。同時実行は、Worker設定で明示的に指定した場合だけ許します。設定が無い、読めない、値が不正な場合は1として扱います。

根拠: 端末の持ち主の資源を守ることを最優先にするためです（ADR-0017の停止権限と同じ向き）。合計の予約を判定する仕組みが無い状態で同時実行を既定にすると、上限を超えた実行を許すことになります。fail closedに倒します。

これは「同時実行をしない」という製品判断ではありません。slot数を増やす道は残し、増やすときに必要になる予約の判定（2.2）と、その記録の置き場所（5章）を先に決めておきます。

### 2.2 関門は「予約の合計 + 新しい割当」で判定する

実行を始めるとき、次の順で判定します。

```text
実行中の予約の合計 + 新しい割当のlimits
  <= min(Local Governorの天井, MachineProfile × 割合)
かつ 実行中のslot数 < slot数の上限
```

- 予約は、Planのlimits（`Plan.Limits()`）をそのまま使います。WorkOrderの上限ではなく、関門が決めた実効の上限です。
- 予約は、実行の終了（完了、失敗、停止、回収）で解放します。解放は1回だけ行い、二重に解放しないようにします。
- 予約の記録が読めない、壊れている、Agentの再起動で内容が分からない場合は、**新しい実行を始めません**。不明を「空き」と解釈しません。

### 2.3 CPUの予約は上限で数える

CPUの予約は、Planの`CPUMillis`（実行に許した上限）で数えます。実行中の平均や実測値では数えません。

根拠: 予約の目的は「始める前に、超えないと言えること」です。平均で数えると、短時間だけ上限まで使う実行を過小に数え、合計が天井を超えます。実測は実行後の記録（RQ-057、RQ-058）と、上限を超えた実行を止める境界（#351）の仕事であり、予約とは別の境界です。同じ値を両方の代用にしません。

メモリとGPUは実行中ずっと占有するので、Planの値をそのまま予約します。

### 2.4 容量が無いときは`deferred`にし、nonceを消費しない

容量が無いために始められない割当は、`deferred`として次のpollで再判定します。`rejected`にはしません。nonceもfenceも消費しません。

根拠: 拒否（`rejected`）は監査上「この割当は不正、または受け入れられない」という意味になります。容量が無いのは割当の性質ではなく、この端末の今の状態です。`deferred`なら、Control Planeは同じWorkOrderをそのまま残しても、新しいnonceで再発行しても、どちらでも扱えます。関門をnonce消費の前に走らせる順序（#308）と同じ考え方です。

### 2.5 1つのslotに1つのAttempt。同じTaskの並行Attemptは別のslotとして数える

1つのslotが同時に2つのAttemptを持つことはありません。`architecture/TASK_STATE_MODEL.md`が認めている「同じTaskの複数のAttemptを並行して実行する」場合は、それぞれが別のslotを使い、それぞれが予約を持ちます。同じTaskだからといって予約をまとめません。実行している主体も、使う資源も別だからです。

### 2.6 heartbeatは、slotが1つの間は現行の1件報告のまま

slotが1つの間は、ADR-0030 §2.2の「実行中のLeaseを1件報告する」形を変えません。slotを2以上にするときに、報告を複数Leaseへ広げるか、slotごとに分けるかを決めます（#354）。実装より先に契約を変えません。

### 2.7 Control Planeへの容量の申告は、このADRでは決めない

「このWorkerはあと何件受け入れられるか」をControl Planeへ伝える経路は、このADRでは決めません。#354と#316で扱います。

ただし、申告が無い間は**Control Planeが容量を知らないまま配置する**ことを明記します。その状態でも、実行できない割当は2.4の`deferred`として残り、Leaseの期限が切れれば自然に取りやめになります（ADR-0030 §2.2の「期限が取りやめになる」）。即時の取りやめを要求しません。

## 3. 影響と移行

- `startgate.Request`に、実行中の予約の合計（と現在のslot数）を渡す形へ変えます。予約が0件の呼出しは、いまと同じ結果になります。既存の呼出し側は、0件を渡すことで挙動を変えずに移行できます。
- 実行slotの管理（どのAttemptがどのslotに居るか、予約の合計）をAgentが持ちます。耐久にするかは5章の未決です。まずはメモリで持ち、Agentの再起動後は「予約が不明」として新しい実行を始めない形にします。
- 試験: (a) 2件の割当の合計が天井を超えるとき、2件目が`deferred`になりnonceが消費されないこと、(b) 1件目が終わると次のpollで2件目が始まること、(c) 予約の記録が読めないときは始めないこと、(d) slot数が1のとき2件目が始まらないこと。
- 文書: `internal/agent/startgate/README.md`、`internal/agent/assignment/README.md`、`internal/agent/service`の「1件ずつ」という記述を、このADRを参照する形にします。
- `internal/agent/nativerunner`の資源の観測（#351）と、このADRの予約は別の境界です。予約は「始める前の合計」、観測は「実行中の実測」を扱います。片方が他方を代用しないことを、両方の文書に書きます。

## 4. 選ばなかったもの

1. **同時実行を既定にする**: 合計の予約の判定が無いまま、1台で上限を超える実行を許すことになります。2.1のとおり、参照実装は1つにします。
2. **実測値で予約する**: 実測は実行を始めた後でしか分からず、「始める前に超えないと言えること」に使えません。2.3のとおり、予約は上限で数えます。
3. **容量不足の割当を`rejected`にして一覧から消す**: Control Planeに再発行の機会を残さず、監査の理由も実態と食い違います。2.4のとおり`deferred`にします。
4. **Control Planeへ容量をpushで申告する**: ADR-0030 §2.1で配送をpullと決めた向きと衝突します。申告の経路は#354と#316で、poll答えに載せる形を第一候補にします。
5. **slot数を無制限にする**: 端末の持ち主の資源を守るという約束に反します。

## 5. 未決

- 予約を耐久にするか。メモリだけにすると、Agentの強制終了で予約が消え、再起動後に「不明」として新しい実行を止め続けます。SQLiteに置く場合の置き場所（replay guardと同じDBか別か）と、強制終了した実行の予約を回収する方法（Leaseの期限を根拠にするか）。
- CPUの予約の粒度。上限で数えると過大に予約し、端末の余力を十分に使えない可能性があります。実行中の残り時間で数える案と比べます。
- Local Governorの割合が実行中に下がったとき、実行中のAttemptを止めるか、新しい割当だけを止めるか（ADR-0017の停止権限との関係）。
- Control Planeへの容量の申告の経路と形（#354、#316）。
- slot数が2以上のときのheartbeatの形（#198のWorker Protocolと合わせる）。
- slot数を増やすときに、Control Planeが同じWorkerへ複数のAttemptを出してよい条件（配置側の判断）。
