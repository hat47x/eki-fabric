# 委任の核の概念モデル

## 役割

[ADR-0013](../../plan/adr/0013-product-core-and-faces.md)で定めたEKIのコア（委任の核）を、一つの概念モデルとして固めるための調査メモです。ADR-0013から生まれた子Issue（#137の配下）は、どれもこのモデルの一部を扱っています。共通の概念、不変条件、権限の対応を先に揃えることで、子Issueの判断が互いに食い違わないようにします。

あわせて、既存の[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)（Architecture Baseline 0.1）と突き合わせ、足りない権限と、改める必要がある境界を洗い出します。Requirement・Architectureの正本ではありません。結論は子Issueへ返し、整理し切ったものからADRに起こします。

## 1. 先に結論

1. 委任の核は、**委任先、利用の許可、予算の枠、依頼、委任の決定、権限、申告と確定、記録**の八つの概念で表せます。四つの仕事の型（投げる、つなぐ、隔離して試す、住まわせる）は、このうち「依頼」と「権限」の形が違うだけです。
2. どの外面、どの型、どの経路から来た依頼でも守る**不変条件を八つ**定めます（§3）。この八つが、ADR-0013で広げたスコープを安全に保つための線です。中でも重要なのは、「実行の権限も管理の権限も、すべて有限である」ことです。常駐する処理も、SEIへの委任も、この条件の例外にしません。
3. 制御は、**SEI（組織の判断、遅い）、EKI（資源の判断、中くらい）、Local Governor（端末の判断、速い）の三層**と、すべての層の上に立つ人間の管理者で成り立ちます。速い層は遅い層を待ちません。
4. 既存の権限モデルは、自律の最適化（Schedulerは提案だけ）と持ち主の拒否権（GOV-1）を、そのまま受け止められます。一方で、次の四つの権限が足りません。
   - 予算の全体と配分を持つ権限（BUD-1、仮称）
   - 費用を生む容量（クラウドの拡張など）の確保と解放を承認する権限（CAP-1、仮称）
   - 委任先と信頼の水準、利用の許可を登録する権限（DLG-1、仮称）
   - 人間の管理者からSEIなどへ、管理者権限の一部を委任する委任状（ADM-1の拡張）
5. 既存の権限のうち、LSE-1（Lease）の対象をTask AttemptからSessionと常駐へ広げる必要があります。ADM-2（受理）は、委任先の指名を「許された範囲を狭める」条件として扱うよう改めます。RAC-1（結果の受理）は、検証の強さを委任先の信頼の水準から決めるよう改めます。

## 2. 概念

### 2.1 八つの概念

| 概念 | 内容 | 誰が定めるか | 既存の概念との関係 |
|---|---|---|---|
| 委任先（Delegate） | 仕事を任せる相手の単位。資源のプール、資源提供者、Workerの区分、外部の提供枠 | 管理者 | Worker Class、Resource Provider、Compute Grantを束ねる。#109の資源プール |
| 信頼の水準（Trust Profile） | 委任先ごとの保証の水準と、その根拠 | 管理者。根拠は登録、Attestation、運用の記録 | Assurance ModelのAxis A〜I。#138 |
| 利用の許可（Entitlement） | どの利用者が、どの委任先と等級を、どの予算の枠で使えるか | 管理者、または委任されたSEI | 等級（#107）、部門間の配分（#125） |
| 予算の枠（Budget Envelope） | 期間ごとに使える資源の量。組織、部門、案件、利用者、依頼の群へと入れ子になる | 総額は人間。配分は人間か委任されたSEI | RQ-017、委譲の連鎖（#117）、案件の予算（#142） |
| 依頼（Request） | 任せたい仕事と条件。型（Task、Task Group、Session、Sandbox、常駐）、信頼の水準の下限、Data Class、期限、保証の要求、任意の指名 | 利用者（Client） | TaskRequest。#106、#126、#129 |
| 委任の決定（Delegation Decision） | どの委任先へ任せるか。指名か自律かと、選んだ理由 | EKI（提案はScheduler、承認はPlacement Authority） | Placement Proposal / Approval。#139、#140 |
| 権限（Mandate） | 委任先へ渡す、範囲と期限のある実行の権限。更新とfencingを持つ | EKI（Lease Authority） | Lease、WorkOrder。#130 |
| 申告と確定（Claim / Acceptance） | 委任先が返す申告と、信頼の水準に応じた検証を経た確定 | EKI（Verification / Acceptance Authority） | Result Claim、Accepted Result |

これに加えて、すべての概念の動きを**記録**として残します。記録には、来歴（Provenance）、資源の消費（物理量）、提供の事実（Contribution Record）、判断の理由が含まれます。

### 2.2 管理の権限も委任の対象にする

SEIに組織レベルの意思決定を委ねる（ADR-0013の決定10）とき、SEIに渡すのは「管理者権限の一部」です。これも委任の一種なので、同じ概念で表します。

| 実行の委任 | 管理の委任 |
|---|---|
| 委任先：資源のプール | 委任先：SEI（の特定のコンポーネント） |
| 信頼の水準：Assuranceの軸 | 信頼の水準：委任できる操作の範囲 |
| 権限：Lease（期限と範囲のある実行の権限） | 権限：委任状（期限と範囲のある管理の権限） |
| 申告と確定：結果の検証 | 申告と確定：影響の大きい決定は人間が承認して初めて有効 |
| 記録：来歴 | 記録：どの委任状のもとで、どの方針を出したか |

委任状は、人間の管理者が署名し、期限、委任できる操作、越えさせない線（Data Classの下限、持ち主の拒否権、予算の総額、Federationの範囲）を持ちます。期限が来れば、更新されない限り失効します。

### 2.3 四つの仕事の型と概念の対応

| 型 | 依頼の形 | 権限の形 | 予算の消え方 |
|---|---|---|---|
| 投げる | Task、Task Group | Attemptごとの一度きりのLease | 依頼ごとに予約し、終われば精算 |
| つなぐ | Session | 期限のある枠のLease。枠の中の小さな依頼は来歴だけを記録 | 枠を開くときに予約 |
| 隔離して試す | Sandbox | 期限のある枠のLease。資源と通信の上限が厳しい | 枠を開くときに予約 |
| 住まわせる | 常駐 | 期間ごとに更新されるLeaseの連なり | 期間ごとに予約し直す |

## 3. 不変条件

どの外面、どの型、どの経路から来た依頼でも、次の八つを守ります。

| ID | 不変条件 | 根拠となる既存の要件 |
|---|---|---|
| I-1 | 依頼は、自分の権限を広げられない。指名や等級の選択は、許された範囲を狭める操作に限る | RQ-016 |
| I-2 | 信頼は明示して定める。委任先の自己申告や評判だけで、信頼の水準は上がらない | RQ-023、RQ-047、Principle 1、10 |
| I-3 | 実行の権限も管理の権限も、すべて有限である。期限、範囲、予算を持たない権限を発行しない。常駐の処理と、SEIへの委任状も例外にしない | RQ-048、ADR-0013の決定7、10 |
| I-4 | 資源の持ち主の拒否権は、すべての判断（自律の最適化、SEIの方針、人間の管理者の方針）より優先する | RQ-005〜007 |
| I-5 | 申告は、委任先の信頼の水準に応じた検証を経るまで確定しない。水準が高くても、検証を省けるのは管理者がそう定めた場合に限る | RQ-019、RQ-044 |
| I-6 | すべての判断（自律の判断、SEIの方針、人間の承認を含む）は、理由とともに記録し、後から失効させ、それに依存した結果を洗い出せる | RQ-039、#122 |
| I-7 | 費用を生む権限（クラウドの拡張、有償の外部の資源）は、ほかの権限から分け、EKIの予算と資源の提供元の上限の二重で守る | RQ-051、#108 |
| I-8 | 予算の総額は人間が定める。委任されたSEIは、その中で配分するだけである | ADR-0013の決定10 |

I-3は、ADR-0013でスコープを広げても安全を保つ要です。常駐の処理を受け入れても、SEIに管理の一部を委ねても、「期限が来て更新されなければ止まる」性質が保たれます。誤りや侵害が起きた場合の影響を、時間の上でも閉じ込められます。

## 4. 三層の制御

```text
人間の管理者 ── 予算の総額、委任状、信頼の水準、越えさせない線を定める。影響の大きい判断を承認する
   │
SEI（組織の判断）── 遅い：時間〜日
   │ 委任状の範囲で、部門と案件への予算の配分、優先度、外部への提供の方針を出す
   ▼
EKI（資源の判断）── 中くらい：秒〜分
   │ 委任の決定（指名と自律）、容量の確保と解放、再配置、提供の縮小
   ▼
Local Governor（端末の判断）── 速い：反射
     この端末で、いま動かしてよいか
```

- 速い層は、遅い層を待ちません。端末の判断はEKIの中央もSEIも待たず、EKIの資源の判断はSEIを待ちません。
- 遅い層が止まっても、速い層は最後の有効な方針で動き続けます。方針の期限が切れたら、人間が定めた既定値へ安全側に戻ります。
- 遅い層は、速い層の上限を広げられません。SEIの方針も、EKIの最適化も、持ち主の上限を超えて資源を使わせられません（I-4）。

## 5. 既存の権限との突き合わせ

### 5.1 そのまま使えるもの

| 既存の権限 | ADR-0013との関係 |
|---|---|
| SCH-1（Scheduler） | Security Authorityではなく、提案だけを出す。自律の最適化と広域の最適化は、SCH-1の提案の範囲を広げたものとして扱える。学習した予測のscoreを権限に変えない境界も、そのまま当てはまる |
| PLC-1（Placement Authorization） | 提案を、Data Class、Assurance、Grantの制約に照らして承認する。信頼の水準を入力に加えるだけで、指名と自律の両方を受け止められる |
| GOV-1（Local Governor） | 持ち主の拒否権。I-4そのもの |
| TSK-1（Task State / Recovery） | 親と子の予算をすでに扱う。Task Groupと委譲の連鎖の受け皿になる |
| CON-1（Contribution） | 外部への提供の記録をそのまま扱える |
| FED-1（Federation） | 外部の資源の利用と提供の、信頼の境界をそのまま扱える |

### 5.2 改める必要があるもの

| 既存の権限 | 改める点 | 関係するIssue |
|---|---|---|
| ADM-1（Trust / Policy Administration） | 管理者権限の一部を、委任状として範囲と期限を限って委任できるようにする。いまの「持たせない権限」（ClientとしてTaskを出すこと等）は、委任状を持つ主体にも、識別を分けたうえで当てはめる | #116、#141 |
| ADM-2（Task Admission） | 委任先の指名を、利用の許可と照らして「許された範囲を狭める」条件として受理する。「具体的なWorkerの選択」を持たせない境界は変えない。Session、Sandbox、常駐の受理を加える | #129、#139 |
| LSE-1（Lease） | いまはTask Attemptを特定のWorkerに一定時間割り当てるLeaseだけを扱う。Sessionと常駐のLease、期間ごとの更新とfencingの進め方を加える | #106、#130 |
| RVR-1、RAC-1（Result Verification / Acceptance） | 確定に要る検証の強さを、委任先の信頼の水準から決める。水準はDLG-1の登録から読み、委任先の申告から読まない | #138 |

### 5.3 足りない権限

| 仮称 | 役割 | 持たせない権限 | 関係するIssue |
|---|---|---|---|
| DLG-1 委任先と信頼の水準の登録 | 委任先、信頼の水準とその根拠、利用の許可を登録し、失効させる | 依頼の受理、Workerの直接の選択、結果の確定 | #109、#138、#139 |
| BUD-1 予算 | 予算の総額（人間が定める）と、入れ子の枠への配分（人間か委任されたSEI）を持つ。ADM-2とCAP-1からの予約を受ける | 委任先の選択、容量の確保、総額の変更（人間だけ） | #108、#125、#142 |
| CAP-1 容量 | 費用を生む容量（クラウドの拡張、有償の外部の資源）の確保と解放を、BUD-1の枠と資源の提供元の上限の範囲で承認する。資格情報はAdapterが持ち、範囲を限る | 依頼の受理、結果の確定、予算の配分 | #140 |
| ADM-1の委任状 | 管理者権限の一部を、期限、委任できる操作、越えさせない線とともに委任する。影響の大きい決定には人間の承認を求める | 越えさせない線の変更、委任状の自己更新 | #141、#145 |

BUD-1とCAP-1を分けるのは、I-7のためです。予算を配分する権限と、実際にお金を使って容量を確保する権限が同じだと、一つの侵害で予算の配分と支出の両方を操作できます。

## 6. 指名と自律の判断の流れ

```text
依頼（条件：信頼の水準の下限、Data Class、期限、保証、予算の枠、任意の指名）
  │
  ▼ ADM-2：利用の許可（DLG-1）と予算の枠（BUD-1）に照らして受理する
  │        指名があれば、許された委任先と照らして範囲を狭める（I-1）
  ▼
候補の委任先 = 許された委任先 ∩ 条件を満たす信頼の水準 ∩（指名があれば指名）
  │
  ▼ SCH-1：候補の中から、期限、費用、転送量、持ち主への影響、予実を見て提案する
  │        容量が足りなければ、CAP-1へ容量の確保を提案する
  ▼ PLC-1：提案を承認する（信頼の水準、Data Class、Grant、持ち主の上限）
  ▼ LSE-1：範囲と期限のある権限を発行する
  ▼ GOV-1：端末で、いま動かしてよいかを最後に判断する
```

指名と自律の違いは、「候補の委任先」を利用者が狭めるかどうかだけです。指名しても、その後の受理、承認、権限、持ち主の拒否権は同じように働きます。

## 7. 外部の要求の経路と権限

ADR-0013の決定11で定めた五種類の要求は、次の権限に入ります。

| 要求 | 入口の権限 | 例 |
|---|---|---|
| 依頼 | ADM-2 | 利用者やSEIのClientとしてのコンポーネントが、仕事を任せる |
| 方針 | ADM-1、DLG-1、BUD-1（人間か、委任状を持つSEI） | 部門への予算の配分、案件の予算の枠、外部への提供量 |
| 照会 | 開示の段階に応じた読み取りの経路。観測情報の保存先から答える | 「この案件は期限に間に合うか」 |
| 承認 | CAP-1、BUD-1、FED-1が、影響の大きい判断について人間に求める | 予算の総額に近いクラウドの拡張 |
| 通知 | 各権限から、受け手の権限に応じて | 間に合わない見込み、提供の縮小、結果の取り消し |

## 8. 候補Scenarioによる確かめ

広げたスコープに特有の失敗を、候補Scenario PAS-CAND-24〜30として[Acceptance Scenarios](../../requirements/ACCEPTANCE_SCENARIOS.md)に加えました。評価は[#148](https://github.com/hat47x/eki-fabric/issues/148)にあります。7件とも、不変条件と既存の要件の組み合わせで方向は扱えます。足りないのは要件より権限の設計で、§5.3の権限を加える設計は[#147](https://github.com/hat47x/eki-fabric/issues/147)で扱います。評価から新しく分かった点は次の三つです。

- 抜き取りの検証で不一致が出たら、その委任先を自動で一時的に候補から外す仕組みが要る（PAS-CAND-24）。
- クラウドの拡張の費用は、拡張を提案する時点で依頼者の予算の枠から予約する。後から精算すると、組織に費用を負わせる攻撃を止められない（PAS-CAND-27）。
- 業務端末で常駐に回してよい余力の上限を、持ち主の上限とは別に管理者が定める（PAS-CAND-30）。

## 9. Open Question

1. DLG-1、BUD-1、CAP-1を、Authority Boundariesに正式な権限として加えるか（[#147](https://github.com/hat47x/eki-fabric/issues/147)）。小さな構成（DP-1）で、一つのプロセスの中に権限の境界をどう保つか（RQ-051）。
2. 委任状で委任できる操作の一覧と、人間の承認を求める判断の境界。
3. 信頼の水準を、Assuranceの軸の組み合わせで表すか、名前を付けた段階で表すか（#138）。
4. 予算の枠の入れ子（組織、部門、案件、利用者、依頼の群）を、どこまで深くするか。
5. 自律の判断の理由を、利用者にどこまで示すか（RQ-018との釣り合い）。
