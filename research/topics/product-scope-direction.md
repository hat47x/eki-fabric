# EKI Fabricの外面とコア、プロダクトの方向性

## 役割

EKI Fabricのプロダクトスコープを見直し、方向性を定めるための調査メモです。結論は[ADR-0013](../../plan/adr/0013-product-core-and-faces.md)として採用し、[Product Value](../../product/value.md)へ反映しました。この文書は、その判断に至った比較と根拠を残します。Requirementの正本ではありません。要件の変更は、末尾のGitHub Issueで個別に扱います。

## 1. 先に結論

1. EKIを、**外面（利用者が導入する理由になる製品の顔）**と、**コア（どの外面からも共通に使われる本質）**に分けて捉えます。TEIが、ローコード開発基盤という外面の下に、プラグイン機構というコアを持つのと同じ構造です。
2. EKIのコアは、分散処理そのものではありません。**「委任先ごとに信頼の水準を定め、仕事の条件とその水準が合う委任先へ、範囲と期限を限って仕事を任せ、結果を確かめて記録する仕組み」**です。本書ではこれを「委任の核」と呼びます。委任先には、管理された専用サーバのように信頼の水準が高いものも、匿名の参加者のように低いものもあります。信頼の水準は暗黙に決まるのではなく、管理者が根拠とともに定めます。
3. 委任先の決め方は二通りです。通常は、仕事の目的に応じて委任先を**明示的に指名**します。十分な資源がある場合は、あえて指名せず、EKIに関連する資源の全体での**自律的な協調**に委ねることもできます。後者で、持ち主が許した余力、管理された資源、クラウドの自動拡張を、予算の範囲で一元的に最適化し、取りこぼさずに活かせることが、プロダクトとしての大きな価値になります。
4. 委任の核は、一台のコンピューターの中でも価値を持ちます。そのため、EKIは**分散のためでなくても導入される**ものになり得ます。分散と広域の最適化は、委任先が増えたときに現れる能力です。
5. 外面は四つに広げます。広域の資源最適化と分散計算、AIの推論とツール実行の統治、AIが生成したコードの隔離実行、常駐する軽量な認知処理の実行面です。どの外面も、同じ委任の核を通ります。
6. 常駐との折り合いは、**「存在は終わらないが、権限は有限」**とします（§8）。常駐する認知処理は、期限つきで更新され続けるLeaseの連なりとして扱います。可用性の約束や状態の正本を持つ業務アプリケーション本体は、引き続き既存のオーケストレータに任せます。
7. 外面を広げても、核は小さく保ちます。推論エンジン、隔離実行の仕組み、LLMのゲートウェイ、ビルドの遠隔実行、クラスタの管理、ワークフロー、識別、観測は、**外部のOSSと連携して実現します**。
8. 将来は、全社・全組織の資源管理を一元化し、SEIの生成AIによる組織機能と連動した自動のオーケストレーションを目指します。EKIのオーケストレーションには、SEIによる組織レベルの意思決定を入れます。その入れ方は、**SEIを、管理者権限の一部を範囲と期限を限って委任された委任先として扱う**ことです。委任の核を、EKI自身の統治にも当てはめます。端末を守る判断はSEIを待たず、SEIが止まってもEKIは動き続けます（§7）。
   EKIは、SEIの判断をただ執行するのではありません。**自身の判断で自律的にオーケストレーションしつつ、SEIや人間の外部の要求に応えるインターフェースを持ちます**（§7.6）。この形で、EKIは単なる分散基盤ではなく、**組織の計算資源についての意思決定を、委任された権限で安全に執行し、証跡を返す基盤**になります。たとえば、SEIが自動で立ち上げた案件に予算の枠を割り当てて執行することや、組織の余力をEKIのネットワークを介して外部へ安全に提供することです（§7.5）。
9. 段階は、M0とMVPの優先順位（mainline priority guard）を変えません。核の縦断スライスを先に通し、そのあとで外面を一つずつ足します。

## 2. 外面とコアを分ける理由

### 2.1 TEIとの対比

TEIは、利用者から見ればローコード開発基盤です。しかし、その下には、意味の正本、能力の契約、権限のlease、来歴を扱うプラグイン機構があり、標準機能もこの機構の上に載る設計を目指しています。外面は時代や顧客に合わせて変わっても、コアが変わらないので、製品として持続します。

EKIのこれまでの文書は、「分散計算基盤」という外面と、その下にあるべきコアを区別していませんでした。そのため、「分散するかどうか」が導入の前提になり、分散が不利な場面（RQ-014）ではEKIを使う理由そのものが消えていました。

### 2.2 外面だけで考えると起きること

外面だけでスコープを考えると、二つの失敗が起きやすくなります。

- 外面を一つに絞ると、その外面の市場が縮んだときに製品の価値も縮みます。[AI時代の価値と位置づけ](ai-era-value-positioning.md) §7のシナリオB（計算が潤沢になる）では、遊休資源を安く使うという外面の価値は下がります。
- 外面を増やすたびに中身を作ると、推論配信、サンドボックス、ワークフローを全部抱えた、まとまりのない製品になります。

コアを先に定めれば、外面を増やしても、増えるのは入口とAdapterだけです。

## 3. EKIのコアは何か

### 3.1 候補の比較

| 候補 | 内容 | コアとして弱い点 |
|---|---|---|
| 分散スケジューラ | 資源へ仕事を配置する | Kubernetes、Slurm、Rayなど成熟した製品が多く、EKIにしかない性質ではない |
| 信頼しない相手への限定委任 | 悪意を前提に、範囲を限って任せる | 信頼の高い委任先（管理クラスタ、自組織の専用GPU）への委任を、過剰な検証で遅くする。信頼の幅を表せない |
| 結果の検証 | 申告を確かめて確定する | 重要だが、受理や権限の付与と切り離すと、何を確かめるべきかを決められない |
| **信頼の水準に応じた委任の核** | 委任先ごとに信頼の水準を定め、条件の合う委任先へ範囲と期限を限って任せ、結果を確かめて記録する | 上の三つを含み、信頼の高い委任先から低い委任先までを一つの仕組みで扱える |

### 3.2 信頼の水準は明示して定める

「信頼の水準に応じて任せる」ことは、「信頼できる相手なら何でも任せる」ことではありません。既存の原則（Principle 1、10、RQ-015、RQ-019、RQ-023、RQ-047）は、そのまま保ちます。変えるのは言い方です。

- これまでの言い方: ClientもWorkerも信頼しない。
- これからの言い方: **暗黙には信頼しない。信頼は、委任先ごとに、管理者が根拠とともに明示して定める。**

信頼の水準は、[Worker Assurance Model](../../requirements/ASSURANCE_MODEL.md)の軸（識別、実行環境、機密性、結果の完全性、独立性など）で表します。根拠は、管理者の登録、Attestation、管理された資源の運用の記録などで、委任先の自己申告や評判だけを根拠にしません。たとえば次のようになります。

| 委任先 | 信頼の水準の例 | 任せられる処理の例 | 検証の強さの例 |
|---|---|---|---|
| 自組織の専用GPUサーバ（管理者が登録、署名済みの実行環境） | 高 | 機密データの処理、確定までの検証を軽くした推論 | 抜き取り |
| 社員の業務端末（組織の端末管理下） | 中 | 社内限定のデータで、再実行してよい処理 | 必要に応じて複製 |
| 他組織の提供枠（Federation、Compute Grant） | Grantの範囲で定める | Grantが許すData Classの処理 | 運営者の異なる経路での照合 |
| 匿名のボランティア、Browser | 低 | 公開データで、結果を検証できる処理だけ | 複製と独立性の確認 |

水準が高い委任先には、検証を軽くして速く任せられます。水準が低い委任先にも、条件の合う処理なら任せられます。これまでの設計は低い側の守りに重心がありましたが、これからは**信頼の幅全体を一つの仕組みで扱う**ことがコアになります。

### 3.3 委任の核の要素

| 要素 | 内容 | 既存の要件・実装 |
|---|---|---|
| 委任先と信頼の水準を定める | 委任先（資源のプール、資源提供者、Workerの区分）ごとに、信頼の水準と根拠を管理者が定める | RQ-003、RQ-047、Assurance Model、#109 |
| 依頼を受ける | 依頼の内容は検証してから受け、予算と方針の範囲でだけ受理する。委譲の連鎖でも予算は縮む | RQ-015〜017、`internal/core/admission` |
| 委任先を決める | 仕事の目的による指名か、EKIによる自律的な選択で、信頼の水準と条件が合う委任先を決める | RQ-008、RQ-016、§5 |
| 範囲と期限のある権限を渡す | 実行の権限を、資源、データ、通信、時間の範囲を限った署名付きのLeaseとして渡す。古い権限はfencingで無効にする | RQ-048、LSE-1、`leaseissue`、`decisiontrust` |
| 資源の持ち主が拒める | 端末の利用者や提供者は、中央の判断を待たずにいつでも止められる | RQ-005〜007、`internal/agent/governor` |
| 申告と確定を分ける | 実行者が返すものは申告であり、委任先の信頼の水準に応じた検証を通って確定する | RQ-019、RQ-021、RQ-044、`resultaccept` |
| 経緯を残し、取り消せる | 誰の依頼を、どの委任先に、どの権限で任せ、何を根拠に確定したかを残す。後から失効したものに依存した結果を洗い出せる | RQ-039、#122 |
| 資源を最適に活かす | 許された余力、管理資源、クラウドの自動拡張を、予算と期限の範囲で全体として最適に使う | §6、#108、#109 |
| 提供の事実を記録する | 資源を提供した事実を、価値の判断から切り離して記録する | RQ-036〜038、`contribution` |

### 3.4 一台でも価値がある例

開発者が、自分の端末でAI Agentを使っているとします。Agentは、生成したコードを実行し、外部のLLM APIを呼び、ファイルを書き換えようとします。

委任の核を通すと、分散を一切しなくても、次のことができます。

- Agentが一時間に使える計算と外部APIの呼び出しを、予算として限る。Agentが別のAgentへ依頼しても、予算は増えない。
- 生成したコードの実行に、通信を禁じた範囲と、10分の期限を付ける。
- 機密のフォルダを含む入力を、外部のLLM APIへ送らない。外部APIは、機密データについては信頼の水準が足りない委任先として扱う。
- Agentが「テストが通った」と返しても確定とは扱わず、別の実行で確かめたものだけを確定として記録する。
- 端末の利用者が会議を始めたら、Agentの背景の計算を止める。

この使い方で導入した組織は、あとで同じ核のまま、遊休資源や管理クラスタへ委任先を広げられます。

## 4. 外面

### 4.1 四つの外面

| 外面 | 利用者から見た姿 | 仕事の型 | 導入の動機の例 |
|---|---|---|---|
| 広域の資源最適化と分散計算 | 遊休資源、管理クラスタ、クラウドを一元管理し、予算の範囲で最大限に活かす計算基盤 | 投げる | 夜間の一括検証、評価の大量実行。クラウドの費用を抑えつつ期限を守りたい |
| AIの推論とツール実行の統治 | 組織のAI利用を、信頼の水準、データの種別、予算、来歴で統治する入口 | つなぐ | 機密データが外部APIへ出ないようにしたい。ローカルの推論資源を共用したい |
| 隔離実行 | AI Agentが生成したコードを、範囲を限って安全に試せる場所 | 隔離して試す | エージェントにコードを実行させたいが、端末や社内ネットワークを危険にさらしたくない |
| 常駐する軽量な認知処理 | 監視、索引の更新、推論の待ち受け、背景の思考の繰り返しを住まわせる実行面 | 住まわせる | SEIやTEIの背景処理を、空いている資源で動かし続けたい |

「軽量認知基盤」と呼ぶ場合も、EKIは認知の意味を持ちません（Principle 7）。EKIが提供するのは、認知処理を住まわせる実行面と、その統治です。何を考えるか、結果をどう使うかは、SEIなどの利用側が決めます。

### 4.2 仕事の型

四つの型は、同じ核の上で、権限を渡す単位と期間が違うだけです。

| 型 | 権限の単位 | 核が一件ごとに行うこと | 期間 |
|---|---|---|---|
| 投げる | Task、Task Group | 受理、委任先の決定、Lease、検証、受理の判定 | 終わりがある |
| つなぐ | Session | 形式の確認と来歴の記録。検証は委任先の信頼の水準に応じて抜き取りか利用者側 | 期限のある枠 |
| 隔離して試す | Sandbox | 資源と通信の上限、出力の取り込みの上限 | 期限のある枠 |
| 住まわせる | Resident（更新されるLeaseの連なり） | 期間ごとの予算の更新、正当性の確認、fencing | 存在は終わらないが、権限は期間ごとに有限 |

### 4.3 入口

利用者が「EKIに投げる」「EKIとつなぐ」だけで実装できるよう、標準の入口を用意します。どの入口から来た依頼も、同じ委任の核を通ります。

| 入口 | 受ける仕事 | 利点 |
|---|---|---|
| EKIのAPI（OpenAPI） | すべての型 | すでにある。言語中立 |
| OpenAI互換の推論API | つなぐ | 既存のLLMアプリをそのまま向けられる。外部APIとローカル推論を、信頼の水準、Data Class、予算で振り分けられる |
| MCP（AI Agentのツール接続） | 隔離して試す、投げる | AI Agentが、委任の核の下でコードを実行し、計算を依頼できる |
| REAPI（Bazelなどの遠隔実行の標準） | 投げる | TEIのビルドや、Bazel、Buck2、Pantsのビルドをそのまま受けられる。二経路の照合と相性がよい |
| ジョブ投入の互換API | 投げる | Kueueなど既存の上位製品から、EKIを資源の供給元として使える |

## 5. 委任先の決め方：指名と自律

### 5.1 二つの決め方

| 決め方 | 使う場面 | 利用者が書くこと | EKIが決めること |
|---|---|---|---|
| 指名 | 仕事の目的から委任先が決まる。たとえば「この評価は社内のGPUクラスタで」「この推論はローカルのモデルで」 | 委任先（管理者が登録した資源のプールや資源提供者）と、仕事の条件 | 指名された範囲の中での配置、権限、検証 |
| 自律 | 十分な資源があり、どこで動いても条件を満たせばよい | 仕事の条件（信頼の水準の下限、Data Class、期限、予算）だけ | 関連する資源の全体から、条件を満たし、全体として最適な委任先 |

通常は指名を使います。指名しない場合、EKIは、その依頼に許されたすべての委任先の中から選びます。遊休の端末、管理クラスタ、他組織の提供枠、クラウドの自動拡張する資源を区別せず、条件と予算と全体の状況から判断します。

### 5.2 指名とRQ-016の関係

RQ-016は、Clientが値を書くだけで「特定のWorkerを直接指定する」ことを禁じています。目的は、Clientが特定の端末を狙ったり、自分に許されていない資源を使ったりすることを防ぐことです。

指名は、この目的と両立する形にします。

- 指名できるのは、管理者が登録し、その利用者に許した委任先（資源のプールや資源提供者）に限る。個々のWorker、hostname、IPアドレスは指名できない。
- 指名は、許された範囲を**狭める**操作として扱う。指名によって、予算、Data Class、信頼の水準の要求が緩むことはない。
- 指名した委任先が条件を満たさない場合（Data Classに対して信頼の水準が足りないなど）は、受理を拒否する。

この整理により、[TEIから使う分散基盤としてのEKI](../integration/tei-usage-requirements-review.md) §4.3で「利用者が選ぶのは等級であり、プールではない」とした判断を改めます。等級（#107）は引き続き使えますが、許された委任先の指名も認めます。

### 5.3 自律的な協調が価値になる理由

指名だけでは、利用者は自分が知っている資源しか使えません。業務端末の余力がある時間帯にクラウドを使い続けたり、ある部門のGPUが空いているのに別の部門が順番を待ったりします。

自律に委ねると、EKIは、関連する資源の全体を見て判断できます。たとえば、期限が明日の朝の評価なら、今夜の業務端末の余力を先に使い、足りない分だけクラウドを自動拡張させます。期限が迫り、予算に余裕があれば、早めにクラウドへ移します。これが、持ち主が許した余力と予算を取りこぼさずに活かすという価値です。

この価値は、信頼の水準を明示して定めることで初めて成り立ちます。水準を定めていなければ、EKIは機密の仕事をどの委任先へ任せてよいかを自律的に判断できないからです。

### 5.4 自律にも越えない線

- 資源の持ち主の拒否権（RQ-005〜007）は、全体の最適化より優先する。
- Federationした他組織の資源は、Compute Grantで許された範囲でだけ使う。Federationの関係を推移的に広げない（RQ-031）。
- クラウドの費用は、管理者が付与した予算の範囲でだけ使う（#108）。
- 自律の判断は、記録として残し、なぜその委任先を選んだかを後から説明できるようにする（RQ-039）。

## 6. 広域の資源最適化

### 6.1 何を一元管理するか

広域の資源最適化とは、性質の異なる資源と予算を一つの視点から管理し、全体として最も良い使い方を選ぶことです。

| 管理の対象 | 内容 |
|---|---|
| 余力 | 持ち主が許した業務端末や個人の端末の余力。時間帯や利用者の復帰で変わる |
| 管理資源 | 専用サーバ、管理クラスタ。部門ごとの配分（#125）がある |
| 拡張できる資源 | クラウドの自動拡張、関数実行。費用がかかる |
| 予算 | 利用者、部門、仕事ごとの予算。物理量で記録し、金額への換算はCoreの外で行う（ADR-0010） |
| 予実 | 資源のプールごとの、期限内の完了割合や所要時間の見込みと実績（#109） |

### 6.2 判断の例

- 余力を先に使い、費用のかかる資源は後に回す。ただし、期限に間に合わない見込みが高まったら、予算の範囲でクラウドを拡張する。
- データの近くで計算する。大きなデータをクラウドへ運ぶより、データのある社内のクラスタで待つ方が早い場合がある（RQ-008）。
- クラウドの資源を、需要の見込みに合わせて先に温めるか、需要が来てから拡張するかを、予算と期限から決める。
- 資源の持ち主が一斉に戻る始業時刻の前に、再配置が集中しないように計画する（RQ-052）。

### 6.3 権限との関係

最適化の判断は、提案として扱います。最適化の仕組み（学習した予測を含む）は、どの委任先が良いかを提案し、配置の権限（Placement Authority）が、信頼の水準、Data Class、予算、持ち主の上限を確かめてから承認します。これは、既存の設計で「Scheduler Proposalを信用しない」とした考え方と同じです（[Authority Boundaries](../../architecture/AUTHORITY_BOUNDARIES.md)）。学習した予測の扱いは、#19で検討しています。

クラウドを拡張する権限は、費用を生む権限です。そのため、Adapterが持つクラウドの資格情報の権限を限り（RQ-051）、クラウド側の予算設定とEKIの予算の二重で上限を守ります。

## 7. 組織の意思決定との連動（SEI）

### 7.1 目指すところ

将来は、全社・全組織の計算資源を一元的に管理し、SEIの生成AIによる組織機能と連動して、オーケストレーションを自動で行うことを目指します。どの部門の仕事を優先するか、予算をどう配分するか、どの仕事を費用をかけてでも期限に間に合わせるかといった判断は、資源の配置の問題である前に、組織の意思決定の問題です。EKIのオーケストレーションには、SEIによる組織レベルの意思決定が入るべきです。

### 7.2 単純な入れ方では何が起きるか

SEIを通常の利用者（Client）として扱い、依頼に「経営上重要」と添えさせて予算を広げると、Clientが自分で権限を広げることになり、RQ-016に反します（PAS-CAND-16）。逆に、SEIにEKIの管理者権限を丸ごと渡すと、SEIの誤りや侵害が、そのまま組織全体の資源とデータの統治に及びます。SEIが止まったときに、EKIの配置や端末の保護まで止まる依存も生まれます。

### 7.3 入れ方：管理者権限の一部を委任する

委任の核を、EKI自身の統治に当てはめます。SEIは、管理者権限の一部を、範囲と期限を限って委任された委任先です。

```text
人間の管理者
  │ 委任する範囲と期限、越えさせない線を定める（Administrative Plane）
  ▼
SEI（組織レベルの意思決定）── 遅い：時間〜日の単位
  │ 部門間の優先度、予算の配分、引き上げの方針を、署名されたPolicyの版として出す
  ▼
EKIの広域の最適化と配置の権限 ── 中くらい：秒〜分の単位
  │ どの委任先へ、いつ任せるかを決める
  ▼
Local Governor ── 速い：反射
  │ この端末で、いま動かしてよいかを決める
```

- 速い層は、遅い層を待ちません。Local Governorの停止の判断は、SEIの稼働も承認も必要としません（[Product Value](../../product/value.md)の「端末を守る判断は、中央の仕組みを待たない」）。
- SEIの決定は、EKIの管理者権限の経路で、署名されたPolicyの版として入ります。Clientの依頼の経路では入りません。
- SEIに委任する権限には、越えさせない線があります。Data Classの下限を下げること、持ち主の拒否権を上書きすること、Federationの関係を広げること、人間の管理者が定めた予算の総額を超えることはできません。
- 影響の大きい変更（予算の総額に近い配分、新しい委任先の信頼の水準の引き上げなど）は、SEIが提案し、人間が承認します。
- SEIの委任された権限にも期限があり、更新されます。SEIが止まった場合、EKIは期限内の最後の有効なPolicyで動き続けます。期限が切れたら、人間が定めた既定値へ安全側に戻ります。
- SEIの決定を、EKIの記録で正しかったと証明することはしません。EKIの記録が示すのは、SEIのどの決定のもとで、どの配置が行われたかです（[SEI Cognitionとの対応ノート](../integration/sei-cognition-mapping.md)の読み替えの禁止）。

この形は、一つの製品がClient権限と管理者権限の両方を持つ構成を許すかという問い（#116）に、方向を与えます。両方を持つことは許しますが、識別と経路を分け、管理者権限は範囲と期限を限って委任されたものに限ります。

### 7.4 全社・全組織の一元化

全社の資源の一元管理は、資源プール（#109）、信頼の水準（#138）、部門間の配分（#125）、広域の最適化（#140）を、組織全体へ広げたものです。複数の組織にまたがる場合も、Federationの関係を推移的に広げない原則（RQ-031）と、Compute Grantで範囲を限る原則（RQ-034）は変えません。全組織の一元化とは、一つの管理者がすべての組織の資源を支配することではなく、各組織が自分の権限を保ったまま、合意した範囲を一つの視点で管理できることです。

### 7.5 判断から執行へ：SEIとEKIの輪

SEIとEKIの関係は、組織の判断と、その執行の輪として整理できます。ただし、EKIは執行だけを担うのではなく、執行の中で自身の判断を行います（§7.6）。

```text
SEI：判断する
  案件を立ち上げる／予算の枠を配分する／外部へ提供する方針を決める
        │ 委任された管理者権限の範囲で、署名されたPolicyの版として渡す
        ▼
EKI：執行する
  資源を割り当てる／クラウドを拡張する／外部への提供枠（Compute Grant）を発行する
        │
        ▼
EKI：証跡を返す
  予実（見込みと実績）／資源の消費の記録／提供の記録（Contribution Record）
        │
        └──▶ SEIが次の判断の材料にする
```

この輪で、EKIが担う高度な対応の例を三つ挙げます。

| 対応 | SEIが判断すること | EKIが執行すること | 越えさせない線 |
|---|---|---|---|
| 案件の立ち上げと予算の執行 | 新しい調査案件を立ち上げ、期間と予算の枠を配分する | 案件用の予算の枠と等級を作り、案件の依頼を受理し、余力と管理資源とクラウドで執行する。予実を返す | 人間が定めた予算の総額を超えない。金額の支払いと会計はEKIの外で行う（ADR-0010） |
| 外部への計算資源の提供 | 組織の余力のうち、どれだけを、いつ、どの相手（研究機関、公益団体、取引先）に提供するかを決める | Compute Grantを発行し、相手の仕事を隔離して受け入れ、提供の事実を記録する。方針が変われば提供を縮小し、Grantを失効させる | 提供先を組織の内部ネットワークに参加させない（RQ-033）。提供先へ組織のデータへの権限を与えない（RQ-034）。業務端末の持ち主の拒否権は提供より優先する |
| 外部の資源の利用 | 期限の厳しい案件について、他組織の提供枠を使うかを決める | Federationの範囲と相手のGrantの条件の中で、委任先として使う | Federationの関係を推移的に広げない（RQ-031）。Data Classが許さない入力は外へ出さない |

「予算の執行」は、EKIの中では、資源の消費を承認する枠を執行することとして扱います。EKIは消費を物理量で記録し、金額への換算、支払い、会計は、組織の会計の仕組みが担います。EKI Coreが通貨や価格を持たない原則（RQ-038、ADR-0010）は変えません。

SEIの判断が自動で行われる場合も、影響の大きい執行（予算の総額に近い配分、新しい外部の相手への提供の開始など）は、人間の承認を経ます。SEIの判断が誤っていた場合に備え、EKIは執行の記録から、どの判断のもとで何を執行したかを洗い出し、取り消せるようにします（#122）。案件の予算の執行は#142、外部への提供は#143で設計します。

### 7.6 EKIの自律と、外部の要求に応えるインターフェース

EKIは、自身の判断で自律的にオーケストレーションします。たとえば次のような判断です。

- 期限と予実の見込みから、余力を先に使うか、クラウドを先に温めるかを決める。
- 業務端末の持ち主が一斉に戻る前に、仕事を管理資源へ移しておく。
- 組織の内部の需要が増えたら、外部への提供を方針の範囲で縮小する。
- 失効した実行体に依存した結果を洗い出し、再実行の候補を作る。

この自律の判断は、委任の核の中で行います。最適化は提案であり、配置の権限が信頼の水準、Data Class、予算、持ち主の上限を確かめてから承認します（§6.3）。EKIの自律にも、越えない線があります（§5.4）。

そのうえで、EKIは、SEI、人間、ほかのシステムからの外部の要求に応えるインターフェースを持ちます。要求は五つの種類に分け、どの経路から来たかで持つ権限を変えます。

| 種類 | 内容 | 経路と権限 | 例 |
|---|---|---|---|
| 依頼 | 仕事を任せる | Clientの経路。許された予算と委任先の範囲でだけ受理する | TEIの一括検証、SEIの背景処理 |
| 方針 | 予算、優先度、提供の方針を定める | 管理者権限の経路。人間の管理者か、範囲と期限を限って委任されたSEI | 部門間の配分、案件の予算の枠、外部への提供量 |
| 照会 | 状況、予実、見込みを尋ねる | 開示の段階（利用者、プールの管理者、Fabric全体の管理者）に応じて答える | 「この案件は期限に間に合うか」「今週の余力の見込み」 |
| 承認 | EKIの自律の判断のうち、影響の大きいものに人間の承認を求める | EKIから人間の管理者へ。承認されるまで執行しない | 予算の総額に近いクラウドの拡張、新しい外部の相手への提供の開始 |
| 通知 | EKIから外部へ、判断や状況の変化を知らせる | 受け手の権限に応じて内容を絞る | 間に合わない見込み、提供の縮小、結果の取り消し |

外部の要求が、EKIの方針や資源の状況と合わない場合、EKIはそのまま従うのではなく、受けられない理由と代わりの案（期限を延ばせば余力で間に合う、予算を足せばクラウドで間に合う、など）を返せることが望ましいと考えます。どの要求にも、EKIの越えない線（持ち主の拒否権、Data Classの下限、予算の総額）を越えさせる力はありません。この設計は#145で扱います。

## 8. 常駐との折り合い

### 8.1 何が問題か

軽量な認知処理には、終わりのない常駐の側面があります。社内文書の変更を見張って索引を更新し続ける処理、ローカルLLMを温めたまま待ち受ける処理、SEIが背景で考え続ける処理などです。

一方、EKIの核は、範囲と期限を限った権限で仕事を任せることで、誤った実行者や中央の誤動作から全体を守っています。[ADR-0009](../../plan/adr/0009-managed-resources-as-providers.md)が終わりのない常駐サービスを対象外としたのは、終わりのない権限を渡すと、この守りが崩れるからでした。

### 8.2 折り合いの付け方

常駐を「終わりのない権限」ではなく、**「期限つきで更新され続ける、有限の権限の連なり」**として表します。

```text
常駐する認知処理
  Lease(期間1) → 更新の判断 → Lease(期間2) → 更新の判断 → Lease(期間3) → …
                  │                            │
                  予算・方針・正当性を確かめる     持ち主が止めれば、そこで終わる
```

- 権限は期間ごとに有限です。更新のたびに、予算、方針、委任先と実行体の失効の有無を確かめます。更新が止まれば、常駐は終わります。
- 更新のたびにfencingの番号が進みます。古い期間の実行者が残っていても、その出力は確定しません。
- 業務端末のLocal Governorは、いつでも止められます。常駐する処理の都合で、持ち主の拒否権は弱まりません。
- 自律に委ねた常駐は、広域の最適化によって、資源の状況に応じて別の委任先へ移ることがあります。

### 8.3 EKIに住まわせてよい常駐と、任せない常駐

| 条件 | EKIに住まわせる常駐 | 既存のオーケストレータに任せる常駐 |
|---|---|---|
| 止められたとき | 利用側の正しさは失われない。遅れるか、別の資源で再開するだけ | 顧客への約束（SLA）が破れる |
| 状態の正本 | 持たない。状態はArtifactやcheckpoint、利用側の保存先に置く | 自分で持つ（DB、セッション） |
| 可用性の目標 | 資源の持ち主の拒否権より上に置かない | 持ち主の都合より優先する |
| 呼び出し口 | 入口（EKIの入口や利用側）が持つ。実行体の所在は隠れる | 固定のエンドポイントを持つ |
| 例 | 索引の更新、推論の待ち受け、背景の思考、監視と通知の候補作り | TEIが生成した業務アプリケーション、取引の処理 |

高い可用性が必要な常駐の認知処理は、信頼の水準が高く、可用性の高い委任先（管理された資源のプール）を指名できます。その場合も、権限は期間ごとに更新されます。

## 9. スコープの選択肢

| 選択肢 | 内容 | 評価 |
|---|---|---|
| A. 絞る | 配置と検証の仲介層だけにする | 端末の保護を手放すことになり、人を優先する原則と両立しない。採らない |
| B. いまのまま | 分散のバッチを中心にする | 推論、エージェントの実行、常駐の認知処理が統治の外に残る。広域の最適化も扱えない。採らない |
| C. 核を定め、外面を広げ、部品は連携 | 信頼の水準に応じた委任の核を一つ持ち、四つの外面を同じ核で統治する | **採る** |
| D. 全部を作る | 推論配信、サンドボックス、ワークフロー、ストレージまで自前で持つ | 既存製品の置き換えになり、ロックインを避ける原則とも衝突する。採らない |

統治の価値は、統治の厳密さと、統治の届く範囲の掛け算で決まります。AIの時代の計算は、推論の呼び出しとエージェントのコード実行に多く流れます。EKIがバッチだけを統治すると、最も量が多く、最も危険な流れが統治の外を通ります。たとえばTEIが、バッチの検証はEKIへ出しながら、設計支援の推論は外部のLLM APIへ直接送ると、機密のワークスペースの内容が、Data Classの判定も予算の上限も来歴の記録も経ずに組織の外へ出ます。

## 10. 自前で作るか、連携するか

### 10.1 判断の基準

1. **権限か受理を決めるもの、端末を守る判断、委任先と信頼の水準の定義は、自前で持つ。** これは委任の核そのものです。外部のポリシー評価エンジンや最適化の仕組みを使う場合も、それは判断の入力であり、署名して記録する判断はEKIの核が行います。
2. **成熟したOSSがあり、その前提とEKIの不変条件の差をAdapterで埋められるものは、連携する。** Adapterは、相手の前提を宣言させ（Capability Negotiation）、EKIの不変条件を壊す既定の挙動を止めます。たとえば、下位の自動再試行を無効にします（#115）。
3. **利用側の意味を持つものは、どちらもしない。** ベクトルDB、エージェントの計画、ワークフローの意味、業務モデルは、利用する製品の責務です。

### 10.2 領域ごとの判断

| 領域 | 判断 | 候補となるOSS | 前提の差とAdapterの義務 |
|---|---|---|---|
| 委任の核の要素 | 自前 | なし | 核そのもの |
| 広域の最適化の判断 | 自前（提案の部分は差し替え可能） | 最適化ソルバ、学習した予測（#19） | 最適化は提案であり、配置の権限が承認する |
| 端末の資源の制御 | 自前（OSの機能を使う） | cgroup、Windowsのジョブオブジェクトなど | OSの仕組みは道具であり、止める判断はLocal Governorが持つ |
| 管理クラスタ | 連携 | Kubernetes＋Kueue、Slurm、Nomad | 自動再試行と横取りの扱い、成功の申告をClaimとして扱う（#67、#115） |
| クラウドの自動拡張 | 連携 | 各クラウドのオートスケール、Kubernetesのクラスタ自動拡張 | 拡張の権限は費用を生む。資格情報の権限を限り、クラウド側とEKIの予算で二重に上限を守る |
| 隔離実行 | 連携 | gVisor、Kata Containers、Firecracker、WASM実行環境、Kubernetesのagent-sandbox | 隔離の水準を自己申告で決めない（RQ-047）。agent-sandboxはAPIがv1alpha1で変わり得るため、必須の依存にしない |
| 推論エンジン | 連携 | vLLM、llama.cpp、Ollama、llm-d | 推論エンジンは信頼済みの専用GPUを前提にする。モデルの重みのdigest、出力の来歴、信頼の水準とData Classによる配置の制限をAdapterで付ける |
| LLMのゲートウェイ | 連携、または入口の参照実装 | LiteLLM、Envoy AI Gateway | 予算とData Classの判定をゲートウェイだけに任せず、核の受理を通す。供給網の侵害事例があるため、版の固定と検証を必須にする |
| ビルドの遠隔実行 | 連携（入口はREAPI） | NativeLink、Buildbarn | REAPIのキャッシュの結果は申告である。二経路の照合や、Executorのdigestの固定と組み合わせる |
| Artifactの保存 | 連携 | S3互換のストレージ、OCIレジストリ、REAPIのCAS | 保存先を信用することと、内容が期待どおりであることを分ける（RQ-027） |
| 識別と署名 | 連携 | SPIFFE／SPIRE、OIDC、Sigstore | 識別できたことを権限と同一視しない（RQ-015） |
| 観測と管理画面 | 連携 | OpenTelemetry、Prometheus、Grafana。統治の画面はTEIで作る候補 | 観測情報は権限の状態と分ける。管理画面はEKIの外で動かす |
| 組織レベルの意思決定 | 連携（SEI）。EKIは委任された権限として受ける | SEI Cognition | SEIの決定は署名されたPolicyの版として、管理者権限の経路で入る。越えさせない線と期限を付ける（§7） |
| ワークフロー | 連携（上位の呼び出し元として） | Temporal、Argo Workflows | ワークフローの意味はEKIに持ち込まない。委譲の連鎖として予算を縛る（#117） |
| 費用の換算 | 連携（Coreの外） | クラウドの請求データ、OpenCost | Coreは物理量だけを記録する（ADR-0010、#108） |

### 10.3 連携に伴う危険

外部のOSSと連携すると、そのOSSの寿命と安全性に影響を受けます。2026年の時点でも、次のような例があります。

- KubernetesのAgent Sandboxは、2025年11月に始まったプロジェクトで、APIはまだv1alpha1です。
- LiteLLMは、PyPIでの供給網の侵害が報告されています。
- 調べた比較記事の一つは、別のLLMゲートウェイが2026年6月に開発を終えた（アーカイブされた）と報じています。

そのため、連携は次の形にします。

- 特定のOSSを核の必須の依存にしない。Adapterを差し替えられるようにする（RQ-004）。
- 一つの領域で、性質の異なる二つ以上の連携先で契約が成り立つことを確かめてから、「EKIの契約」と呼ぶ（ADR-0009と同じ考え方）。
- 連携先の版と配布物のdigestを固定し、署名や来歴を確かめる（RQ-026の考え方を、連携先にも当てはめる）。

## 11. 目標外と原則の言い直し

| 項目 | これまで | これから |
|---|---|---|
| 信頼 | ClientもWorkerも信頼しない | 暗黙には信頼しない。信頼は委任先ごとに、管理者が根拠とともに明示して定める。信頼の水準が高い委任先には検証を軽くして任せる |
| 導入の前提 | 分散計算基盤として導入する | 委任の核として、一台からでも導入できる。分散と広域の最適化は能力の一つ |
| 資源の活用 | すべての資源を常に最大限まで使うことは目標にしない | 持ち主が許した余力と予算の範囲を、取りこぼさずに活かすことを目標にする。持ち主の上限を超えて使い切ることは、引き続き目標にしない |
| 委任先の指定 | ClientはWorkerを直接指定できない | 個々のWorkerは引き続き指定できない。管理者が許した委任先（資源のプール、資源提供者）は、目的に応じて指名できる |
| 推論 | 推論エンジンや配信基盤にならない。推論は対象外 | 推論エンジンにはならない（連携する）。推論の**呼び出しの統治**は対象にする |
| 低遅延の対話 | 置き換えない。主な対象は非同期・バッチ | 推論の速さでは競わない。温めた枠で、人が待つ処理にも使える程度の応答を目指す。ミリ秒単位の対話や、分散が不利な処理は引き続き対象外（RQ-014） |
| 常駐 | 終わりのない常駐サービスは対象外 | 期間ごとに更新される有限の権限として、止められても正しさが失われない常駐の認知処理を住まわせる。業務アプリケーション本体は引き続き対象外 |
| エージェント | Agent Frameworkにならない | 引き続き、計画や意味は持たない。エージェントが出す依頼と、生成したコードの実行は、統治の対象にする |
| クラスタ管理、ストレージ、通貨・市場 | 置き換えない、正本を持たない、作らない | 変えない |

## 12. 段階

M0とMVPの優先順位（[Upstream Plan](../../plan/UPSTREAM_PLAN.md)のmainline priority guard）は変えません。

| 段階 | 内容 | 前提 |
|---|---|---|
| S0 | 核の縦断スライス（悪意あるClientからの受理、2台以上のNative Workerへの配置、reclaim、retry、結果の検証） | いまの計画どおり |
| S1 | Artifactの経路、Task Group、委任先と信頼の水準の登録、指名。一台で完結する配備形態 | すべての外面が必要とする |
| S2 | 隔離実行の外面とMCPの入口 | S1。一台での導入の主な入口になる |
| S3 | 推論の統治の外面とOpenAI互換の入口 | S1 |
| S4 | 自律的な委任先の選択と、広域の資源最適化（余力、管理資源、クラウドの自動拡張、予算） | S1、#108、#109。管理クラスタの連携（#67）と並行 |
| S5 | 常駐する認知処理の外面（更新されるLease） | S3。SEIの背景処理で確かめる |
| S6 | REAPIの入口、ジョブ投入の互換API | 随時 |
| S7 | SEIの組織レベルの意思決定との連動（委任された管理者権限）と、全社・全組織の一元管理 | S4。#116、#141 |

## 13. Open Question

1. 信頼の水準を、Assurance Modelの軸の組み合わせで表すか、管理者が名前を付けた段階で表すか。
2. 外面ごとの型（つなぐ、隔離して試す、住まわせる）を、Requirementとしてどの粒度で書くか。
3. 自律的な選択で、利用者に「どこで動いたか」をどこまで開示するか。開示しすぎると内部構成が分かり（RQ-018）、開示が足りないとデータの所在を説明できない。
4. 一台で完結する配備形態を、既存のDeployment Profile（DP-0〜DP-6）のどこに置くか。
5. 常駐の更新の判断を、どの権限が行うか。業務端末に常駐をどこまで許すか。
6. OpenAI互換の入口を、外部のゲートウェイとの連携で済ませるか、EKIの入口の参照実装として持つか。
7. 委任の核を、TEIのプラグイン機構の権限のleaseと共通化する余地があるか。
8. 連携先の一覧（自前と連携の境界）を、どの文書で正本として保つか。
9. SEIに委任する管理者権限の範囲と、人間の承認を求める変更の境界をどう定めるか。
10. 外部への提供で、提供先の仕事が組織の端末やネットワークに与える危険を、どの隔離の水準で抑えるか。提供の開始と縮小を、どこまでSEIの判断に任せるか。
