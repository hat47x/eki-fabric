# TEIの一件の検証をEKIへ委任する：2026-11-11の観測

Spikeの役割、構成、実行方法、限界は[README](README.md)にあります。生の出力は`evidence/2026-11-11/`にあります。

## 条件

- EKI（eki-fabric）: `main`、`f3492f55bf0ec571f139d4b6153498d248c0d58d`。`eki-control`はこのrevisionから`go build`した。
- TEI（tei-platform）: `b8cbd432a`から`-trimpath -buildvcs=false`でビルドした`tei`。実行体のSHA-256は`673c511e362068874de192361bf4e96494720feb5a191d5bd4fb065cbfce6d75`。同じrevisionから取り直してビルドし直した実行体とdigestが一致することを確認した。
- 対象の操作: `tei validate -workspace reference/workspace -json`。読むだけで、外部への書き込みをしない。
- 入力: `reference/workspace`を決定的なtar.gzにしたもの。SHA-256は`4503dff3b38b21dc428f1842db86ab6ff5a748acf93cb9f5d0c1f61969776781`、14,507バイト。tar.gz自体は証拠に含めない。TEIのソースの複製をEKIの履歴へ持ち込まないためである。同じdigestは`run_live.ps1`で再生成できる。
- 環境: Windows 11上の一台の開発PC。`eki-control`はloopback（平文HTTP）、SQLiteの一時ファイル、Artifactの一時ディレクトリ、固定Bearer token一つ、Workerの試験profileで起動した。`dispatch`は有効にしていない。本番DB、外部サービス、実Providerへは触れていない。
- 実行: `run_live.ps1`（Windows PowerShell 5.1）。証拠は`live-run.json`、`trace-1.json`、`trace-2.json`、`probe.json`、`local-1..3.json`、`projection.json`。
- `lease_registry`を設定していないため、`eki-control`は起動時に`lease reclaim is disabled: no lease_registry is configured`と警告した。この配備ではLease失効の回収走査は動いていない。Lease失効の負例を実EKIで観測していない理由の一つである。

実行中、同じワークスペース内の別の作業が`tei-platform`のcheckoutを更新していた。そのため実行体のrevisionはcheckoutのHEADではなく、ビルド元のrevisionを`-TeiRevision b8cbd432a`として明示した。実行体のdigestも記録してある。

## 観測

### 1. 入力Artifactの経路は、実EKIで通しで動く

`trace-1.json`の`links.inputs`。

| 項目 | 値 |
|---|---|
| 送った本文のdigest | `4503dff3…`（14,507バイト） |
| ingest intent | 201、`declared_size_bytes`は14,507 |
| アップロード | 202、`artifact_id`は`4503dff3…`（送ったdigestと一致） |
| 取得して再測定したdigest | `4503dff3…`（一致） |
| `task_request.inputs[0].artifact_id` | `4503dff3…` |
| Taskの受理 | 202、`request_fingerprint`は`sha256:945e2d…` |

入力の同一性は、TEIが送った本文・EKIが名付けたdigest・Taskが参照するdigest・取得した本文の四か所で一致した。この範囲は実EKIで確認できた。

### 2. 実EKIでは、Taskの受理までで止まる

`trace-1.json`、`trace-2.json`、`probe.json`。

| 観測 | 値 |
|---|---|
| Taskの状態 | `queued`のまま（3秒間、6回の読み取り） |
| `attempt_count` | 0（または不在） |
| 結果 | 409 `RESULT_NOT_READY`（`retryable: true`） |
| 期限（要求） | `deadline`を過ぎても状態は変わらず、`terminal_code`も付かない |
| 取消 | 202、状態は`cancelled`、`terminal_code`は`CANCELLED` |
| 取消後の結果 | 409 `RESULT_NOT_AVAILABLE` |

実際のAttemptは作られていない。`dispatch`を有効にしていないため、Taskは受理されたがWorkerへ配送されない。EKIの公開状態が持つAttemptの情報は`attempt_count`だけで、LeaseとFenceは公開されない。したがって、この実行では「入力Artifact・実行体digest・Toolchain・要求条件・Task・Receipt」までは対応づけられるが、実際のAttemptと結果Artifactの対応は作れない。作れないことを成功として扱わない。

### 3. 同じ依頼の再送は、同じTaskへ収束する

`trace-2.json`。

| 項目 | 1回目 | 2回目 |
|---|---|---|
| `task_id` | `tsk_71ccb130…` | `tsk_71ccb130…`（同じ） |
| `replayed` | false | true |
| `attempt_count` | 0 | 0 |
| 結果 | 409 `RESULT_NOT_READY` | 409 `RESULT_NOT_READY` |

2回目の投入は新しいTaskもAttemptも作らなかった。`effect_mode: "none"`の操作では、この収束が重複実行の安全側の根拠になる。ただし、これは「二重に実行されない」ことの確認であり、実行が行われたことの確認ではない。

### 4. 拒否経路は、公開契約の範囲で判別できる

`probe.json`。12件が期待どおり、1件が契約と実装の不一致だった。

| 試し | 期待 | 実際 |
|---|---|---|
| 本文を送っていない入力を指定したTask | 422（入力が解決できない） | 422 `INPUT_ARTIFACT_UNRESOLVABLE` |
| 同じ冪等キー・同じ本文 | 202、`replayed: true`、同じTask | 一致 |
| 同じ冪等キー・違う本文 | 409 | 409 `IDEMPOTENCY_KEY_CONFLICT` |
| 同じアップロードsessionへ2回目 | 404（再開できない） | 404 `UPLOAD_NOT_FOUND` |
| 期限を過ぎたTask | 終端へ動かない | `queued`のまま、`terminal_code`なし |
| 取消 | `CANCELLED` | `cancelled` / `CANCELLED` |
| 結果がまだないTaskの結果取得 | 409 `RESULT_NOT_READY` | 一致（`retryable: true`） |
| 取消後の結果取得 | 409 `RESULT_NOT_AVAILABLE` | 一致 |
| 既に過ぎた期限で投入 | 422 | 422 `DEADLINE_IN_PAST` |
| 存在しないArtifact | 404 | 404 |

期限については二つに分かれた。投入時点で既に過ぎている期限は受理されない（`DEADLINE_IN_PAST`）。受理後に期限が過ぎても、Taskは終端へ動かない。TEIは前者を受理の拒否として`rejected`に、後者を`undetermined`に写す。

### 5. 契約と実装の不一致（2件）

いずれも外部契約を変更せず、Issueで扱う。

(a) `expected_digest`は強制されない。 ingest intentで`expected_digest`に`4503dff3…`を宣言し、それとは違う本文をアップロードしたところ、202で受理され、`artifact_id`は送った本文の実測digest `7d67252b…`になった。実装はアップロード時に期待digestを照合していない（`upload.go`が`h.sink.Put(tee, "", session.maxBytes)`と呼び、期待digestを渡していない）。契約上は宣言と本文の一致を強制するように読める。TEI側は、アップロード応答の`artifact_id`を自分が送るつもりのdigestと比較し、一致しなければそのdigestを入力に指定したTaskを送らない、という防御が必要になる。このSpikeはそうしている（`delegate.go`の`DigestAgreed`）。誤った本文を送った場合、その後のTaskは`INPUT_ARTIFACT_UNRESOLVABLE`で拒否される。

(b) `ArtifactDescriptor.digest`の型が契約と違う。 `openapi.json`は`Digest`オブジェクト（`algorithm`と`value`）を宣言しているが、実装は16進文字列を返す。`model.go`は両方を受け取る。Receiptの判断には影響しないが、契約どおりに実装する生成コードは失敗する。

また、入力が解決できない場合のコードは、契約に列挙がないまま、配備全体で入力を使わない場合の`ARTIFACT_NOT_AVAILABLE`と、解決に失敗した場合の`INPUT_ARTIFACT_UNRESOLVABLE`の二つがある。TEIから見ると同じ「入力が使えない」であり、どちらも`rejected`に写す。

### 6. EKIの往復の費用と、ローカル実行の比較

`trace-1.json`の`timings`と`local-1..3.json`。

| 経路 | 時間 |
|---|---|
| 入力のingestとアップロード（14,507バイト） | 43 ms |
| Taskの投入 | 5 ms |
| 状態の読み取り6回（うち意図的な待ち3,000 ms） | 3,038 ms |
| 結果の取得 | 2 ms |
| **待ちを除いた往復** | **88 ms**（12リクエスト） |
| ローカル実行 `tei validate` | 158 / 398 / 836 ms（3回） |

このホストでは、14.5KBの入力を渡してTaskを受理し、状態と結果を読む往復は約0.09秒だった。同じ操作のローカル実行は0.16〜0.84秒だった。この一回の測定だけを見ると、EKIの往復はローカル実行より小さい。

しかし、この比較は実行の比較ではない。EKIはこの操作を実行していない。入力の保管とTaskの受理、状態の投影だけを行った。実際に実行させるにはWorkerの配送と実行が必要で、その費用（転送、配置、実行、検証）はここに含まれていない。既存の[Workload Projection Spike](../tei-workload-projection/RESULTS_2026-10-19.md)では、ビルドがキャッシュの有無で0.8秒と12.5秒に分かれた。小さな検証一件では、往復の費用が仕事そのものより大きくなり得る。

ローカル実行の時間は同じホストでも大きく変動した。この実行の3回は158〜836 msだったが、作業中には同じコマンドが153 ms、3.3秒、9.3秒になることもあった。一件のサンプルから費用を結論にしない。 比較には複数回の測定と、キャッシュの状態、ホストの負荷を添える必要がある。

## モックと模擬で確かめた負例

実EKIでは観測できない、または実EKIで作れない条件は、モックと模擬で確かめた。実EKIの挙動の証拠ではない。

| 負例 | 入力 | TEI側の判定 | 場所 |
|---|---|---|---|
| 重複実行 | 同じAttemptの結果が2回届く | 1回だけ採用し、重複を抑止 | `simulate_test.go` |
| 期限切れ | 期限内に結果がなく、期限を過ぎた | `undetermined` | `delegate_test.go`、`simulate_test.go` |
| 結果未到着 | 状態は`verifying`、結果は409 `RESULT_NOT_READY` | `undetermined`（期限後は理由に期限を明記） | `delegate_test.go` |
| Lease失効 | Leaseの期限後に結果が届く | `rejected` | `simulate_test.go` |
| 古いAttempt | 現在のAttemptより前の結果が届く（Fence不一致を含む） | `rejected` | `simulate_test.go` |
| 部分的なArtifact受領 | Artifactは列挙されるが取得できない | `undetermined`（採用しない） | `delegate_test.go`、`simulate_test.go` |
| キャッシュ差異 | 結果のdigestがローカル基準と違う | `rejected`（キャッシュ・Toolchain・環境の差であり得る） | `delegate_test.go`、`simulate_test.go` |
| 結果にdigestもArtifactもない | 200だが比較対象がない | `undetermined` | `delegate_test.go` |
| 入力が未アップロード | 422 | `rejected` | `delegate_test.go` |

Lease・Fence・Attemptの判定は`simulate.go`の入力であり、EKIの公開契約には存在しない。「EKIが実際に古いAttemptの結果を拒否した」ことは、このSpikeでは確かめていない。 確かめたのは、TEI側がそのような結果を採用しないという規律である。

## 一般化できる範囲

- 入力Artifactの同一性は公開APIの範囲で追跡できる。送った本文、EKIが名付けたdigest、Taskが参照するdigest、取得した本文の四か所を突き合わせられる。ただし宣言した`expected_digest`は強制されないため、TEIが応答を検査する必要がある。
- 実行体のdigestとToolchainは、EKIでは保証できない。要求に欄がない。Receiptはこれらを「記録しただけ」と扱い、`not_checked`に残すべきである。
- 結果が得られないことを、失敗とも成功とも扱わない。期限内の`RESULT_NOT_READY`は`undetermined`、期限後のそれも`undetermined`、終端後の`RESULT_NOT_AVAILABLE`は`rejected`。この区別を潰すと、期限切れと実行失敗を同じ扱いにしてしまう。
- 重複の安全は`effect_mode: none`に依存する。副作用のある操作へ同じ構成を流用してはならない。
- 小さな決定的な処理を一件ずつ委任すると、往復が仕事より大きくなり得る。特に、今回のように実行そのものが未配線の段階では、EKIへ委任しても仕事は終わらない。ローカル実行の方が常に有利である。

## 一般化できない範囲（この実験の限界）

- 実際のAttempt、Lease、Fence、結果Artifactは観測していない。`dispatch`を有効にしていないため、Taskは配送されていない。
- 結果の受理（`completed`）は観測していない。独立した検証の入力が現行の起動経路にない（[#242](https://github.com/hat47x/eki-fabric/issues/242)）。
- 実行したのは`validate`だけで、ビルド、コード生成、テストは実行していない。
- ホストは一台、通信はloopback。実際のネットワーク越しの転送、Workerの配置、検証の費用は含まない。
- 時間の測定は同じホスト上の別の作業の影響を受けた。ローカル実行の時間は10倍以上変動した。
- EKIの契約と実装の不一致は、このrevisionでの観測である。`f3492f55`以降に修正されている可能性がある。
