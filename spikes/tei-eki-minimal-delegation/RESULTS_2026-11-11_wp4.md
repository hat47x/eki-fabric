[IMPLEMENTATION_PLAN.md](IMPLEMENTATION_PLAN.md)のWP-4（実際のAttemptを作る）を、Linux上のWSLで実行しました。この記録は[RESULTS_2026-11-11.md](RESULTS_2026-11-11.md)（当日の最初の実EKI観測）に対して、**後から追加された観測**です。前者は書き換えていません。

## 条件

- EKI（eki-fabric）: `feat/tei-eki-minimal-delegation-20261111`、`main` `f3492f5` に本PRの変更を加えたもの。
- TEI（tei-platform）: `b8cbd432a` からLinux向けに `-trimpath -buildvcs=false` でビルドした`tei`（`/tmp/tei`）。
- 実行環境: WSL2のUbuntu 22.04、Go 1.27.3（Linux amd64）。`eki-control`と`eki-agent`はLinux向けにビルドした実プロセス。
- 入力: `reference/workspace`を決定的なtar.gzにしたもの（5,627バイト）。
- 試験: `conformance/process/tei_validation_test.go` の `TestTEIValidationReachesARealAttempt`。環境変数 `TEI_EKI_TEI_BINARY`・`TEI_EKI_WORKSPACE`・`TEI_EKI_EXPECTED_SHA256` で外部のTEI実行体を受ける。未設定なら`t.Skip`する。

## 判明したこと: 入力経路に2つの未配線

WP-4を実行したところ、当初は**Agentが`input_unavailable`で割当を拒否**し、Attemptが終わりませんでした。ログには`remote error: tls: bad certificate`がありました。原因は2つです。どちらもEKI側の未配線で、修正はこのPRに含めています。

### 1. Worker Planeの取得口に本文が渡っていない

`internal/control/workerplane/mtls.go`の`MTLSConfig`には`Artifacts`の欄があり、`artifactfetch.go`も`OpenArtifact`を呼んでいます。しかし`internal/control/service/run.go`の`startWorker`が`NewMTLSHandler`へ`Artifacts`を渡しておらず、常に501 `artifacts_not_served` になっていました。さらに`internal/control/service/artifactsource.go`は`clientapi`向けの`Open`しか持たず、`workerplane.ArtifactSource`（`OpenArtifact`）を実装していませんでした。

修正:

- `internal/control/service/artifactfetch.go`（新規）: `artifactSource`に`OpenArtifact`を追加
- `internal/control/service/run.go`: `Artifacts: artifactSource{store: bodies}`を渡す

### 2. Agentの入力fetcherがWorkerの証明書を使っていない

`internal/agent/service/assignments.go`の`inputFetcher`が`HTTPFetcher{BaseURL: ...}`を作るとき、`Client`を設定していませんでした。`HTTPFetcher`は`Client == nil`のとき`http.DefaultClient`を使うため、mTLSのWorker Planeはハンドシェイクで接続を拒否します。

修正:

- `internal/agent/claimclient/http.go`: `RequestClient()`を追加（Workerが既に認証に使っているHTTPクライアントを返す）
- `internal/agent/service/assignments.go`: `inputFetcher`が`*http.Client`を受け、`HTTPFetcher.Client`に設定する
- `internal/agent/service/run.go`: `runAssignments`へ`api.RequestClient()`を渡す

この2件はEKI #763の完了報告（2026-11-10）の後も残っていました。完了条件「入力の取得が、配備の設定から有効になる」は、実際の`eki-control`では満たされていませんでした。**試験用profileの試験が`ArtifactBaseURL`を設定していなかったため、この穴は既存の試験では見えていませんでした。**

## 一般化できる範囲

- **入力Artifactの経路はEKIの実プロセスで通しで動く。** Client APIで投入した本文が、Workerの入力ディレクトリに`<digest>`の名前で置かれ、ラッパーがそれを読んで実行できる。
- **実行結果の一致（D2）は、実EKIで確認できる。** Agentの`OutputDigest`がTEIのローカル期待値と一致した。ただしこれは「同じ実行体・同じ入力・同じホスト」での一致であり、別ホストや別Toolchainでの再現性ではない。
- **未配線は、実プロセスを通すまで見えない。** 部品（`OpenArtifact`の口、`HTTPFetcher`の`Client`欄）は存在していたが、起動経路で繋がっていなかった。単体試験は通っていた。

## 一般化できない範囲

- D3（EKIの受理）とD4（`accepted`のReceipt）は観測していない。結果は`409 RESULT_NOT_READY`のまま。
- 実行したのは`validate`だけ。ビルド、コード生成、テストは実行していない。
- ホストは1台、通信はloopback。ネットワーク越しの転送と配置の費用は含まない。
- Windowsでは実行していない（固定コマンドがPOSIXのラッパーで、Runnerのプロセスツリー停止も#312で不安定）。

## 再現方法

```bash
# Linux（WSL2のUbuntu 22.04、Go 1.27.3）
cd <eki-fabric checkout>
go build -o /tmp/ekibin/eki-control ./cmd/eki-control
go build -o /tmp/ekibin/eki-agent ./cmd/eki-agent
# TEIの実行体はtei-platformからビルドする
#   cd <tei-platform> && CGO_ENABLED=0 go build -trimpath -buildvcs=false -o /tmp/tei ./cmd/tei

EKI_PROCESS_BIN_DIR=/tmp/ekibin \
TEI_EKI_TEI_BINARY=/tmp/tei \
TEI_EKI_WORKSPACE=<tei-platform>/reference/workspace \
TEI_EKI_EXPECTED_SHA256=<ローカル実行のstdout+stderrのSHA-256> \
go test ./conformance/process -run TestTEIValidationReachesARealAttempt -count=1 -v
```
