# Control Plane Authority Separation — 2026-09-18 初期観測

## 実行

```bash
go test ./...
```

## 結果

```text
ok  eki.local/control-plane-authority-spike
```

## 実証した境界

今回のSpikeでは、Schedulerを侵害されたComponentとして扱い、Scheduler Proposalだけでは次を成立させられないことをTestしました。

- Data Classを下げる
- Security要件未達WorkerへPlacement Approvalを作る
- Executor未承認Workerを承認する
- 任意Artifact Grantを発行する
- WorkOrderを署名する
- 他Worker向けWorkOrderを利用する

また、初期レビューで、

> Placement Guardの検証用Admission公開鍵を呼び出し側から渡してはいけない

という問題を検出し、Trust RootをGuard内部へ固定しました。

この修正後も全Testが通過しています。

## この結果の意味

確認できたのは、

> Componentごとに異なるAuthorityを持たせ、後段が前段の署名とbindingを再確認する構造を、比較的小さな実装でも成立させられる

という点です。

Microservice数やIdentity製品、署名方式を確定したわけではありません。

## 残る境界

- Placement Guard自体が侵害された場合
- Artifact Authority自体が侵害された場合
- WorkOrder root signing authorityが侵害された場合
- key rotation / revocation
- audit log耐タンパ性
- replay / nonce / Attempt ID
- multiple signer / threshold approval
- Federationした外部Authority
- 一つのBinary内で別Authorityを安全に保持する方法

これらは後続Spike / Architecture比較へ残します。
